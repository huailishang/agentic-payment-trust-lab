# AI治理问责与智能体审计/交易标准：项目影响分析

> 核验日期：2026-09-08  
> 适用项目：`agentic-payment-trust-lab`  
> 定位：外部参考与长期跟踪，不直接改变当前 `B-12 / H-18` 执行主线，不构成监管合规结论。

## 1. 一句话结论

这批材料值得重点关注，但必须分层：

```text
Sumsub AI Governance Benchmark
→ 证明“企业承担责任，但缺少可证明证据”的行业痛点

MAS SAFR
→ 给出金融 Agent 在“动作执行前”进行身份、授权、策略和审计控制的工程参考

GB/Z 185.1—185.7 + GB/Z 242-2026
→ 给出国内智能体基础、身份、交互和工具调用的标准化背景

GB/Z 185.8（智能体审计）+ GB/Z 185.9（智能体交易）
→ 与本项目后续 Evidence / Replay / Identity / Transaction 最直接相关，列为重点 WATCH
```

因此，**重点关注的不是 Sumsub 这一个厂商报告，而是它揭示的问题与 SAFR、国内审计/交易标准正在形成同一条外部趋势线：高风险 Agent 必须从“能执行”走向“执行前可治理、事后可证明”。**

## 3. Sumsub：真正应该吸收的不是百分比，而是问题定义

Sumsub 官方 APAC 页面给出的核心数据是：

- `95%` 的组织表示能够解释 AI 做了什么；
- 只有约 `1/3` 保存防篡改的决策记录；
- `99%` 表示愿意采用能够证明 AI 行为的机制；
- 调查覆盖 APAC 9 个市场、720 名 risk / compliance / technology / operations 专业人士。

这比单独记住“中国 97% / 29%”更适合作为项目长期依据。当前已核到的 Sumsub 新加坡一手发布明确写的是“94% 已使用或试用、29% 能提供证明决策的证据”；**中国细分数字如果只有转载，不进入项目基线，等一手 country table / 完整报告再补。**

### 对项目的启发

Sumsub 提出的 `Accountability Asymmetry（问责不对称）` 可以翻成项目语言：

```text
组织 / 人要为 Agent 的结果负责
        ≠
系统能够机械证明 Agent 当时为什么有权这么做、依据什么事实、最后发生了什么
```

本项目不需要再造一个“AI Governance 模块”，而应把现有能力收敛成一条可证明责任链。

## 4. MAS SAFR：比 Sumsub 更直接的工程参考

SAFR（Safeguards for Agentic Finance at Runtime）于 2026-07 由 MAS BuildFin.ai 与金融机构/支付网络参与者共同发布。其关键价值不是“又一套 AI 原则”，而是把治理放到 **Agent Action（智能体动作）与真实执行之间**。

可抽象为：

```text
Agent proposes Action
        ↓
Governance Envelope
        ↓
Agent Identity
        ↓
Controls Repository / Mandate
        ↓
Disposition Engine
        ↓
AUTO-EXECUTE / OBSERVE / ESCALATE / DENY
        ↓
Execution
        ↓
Audit Log
```

### 与本项目的对应关系

| SAFR | 本项目已有能力 | 判断 |
|---|---|---|
| Agent Identity | `Agent Identity / Executor`、P3 | 高度一致；当前主要到 `DECLARED / BOUND`，真实 `VERIFIED` 仍是边界 |
| Governance Envelope | `Governed Payment Action + Explicit Facts + Fact Lineage` | 结构上高度相似，但本项目更强调不同事实源不能混为同一可信等级 |
| Controls Repository / Mandate | `Delegated Authority + Context Policy` | 已有主体，不需要另建一套规则库 |
| Disposition Engine | `Runtime Authorization Gate` | 高度一致，是当前架构核心资产 |
| Audit Log | `Authoritative Trace + Replay + Evidence` | 已经具备 L1 追溯能力；防篡改和真实执行主体证明仍需分级 |

### 必须保留的差异

SAFR 的 `Action trace` 不应被简单理解成“保存模型思维链”。本项目长期坚持：

```text
不要保存 / 依赖模型内部 Chain of Thought（思维链）作为审计证据。

重点保存：
Actor + Authority + Action + Trusted Facts + Policy Version
+ Runtime Decision + Reason Codes + Side Effect + Outcome + Evidence
```

原因：模型自述的推理可以被提示注入、上下文污染或事后生成；真正可审计的是外部可观察、可验证的动作和证据。

## 5. 国内标准：后续真正需要盯的是 185.8 / 185.9

- `GB/Z 185.1-2026` 总体架构
- `GB/Z 185.2-2026` 身份码
- `GB/Z 185.3-2026` 身份管理

- `GB/Z 185.7-2026` 智能体工具调用

均于 `2026-05-22` 发布并显示为现行指导性技术文件。

另外，`GB/Z 242-2026《人工智能 智能体技术要求》` 于 `2026-08-27` 发布并现行，可作为通用智能体技术基线的新增 WATCH 项。

## 6. 对项目的核心吸收：Provable Accountability（可证明问责）

当前项目可以把长期价值进一步收敛为：

> **不是解释模型脑子里怎么想，而是让每个高风险 Agent Action 都能被独立回答：谁被授权、谁执行、执行什么、为什么被允许、产生什么副作用、最终结果是什么、用什么证据证明。**

对应责任证明链：

```text
Authority
→ Actor / Executor
→ Action
→ Trusted Facts / Context
→ Runtime Decision
→ Side Effect
→ Outcome / Finality
→ Evidence / Replay
```

这条链与当前已有的：

```text
Delegated Authority
+ Agent Identity
+ Governed Action
+ Runtime Authorization Gate
+ Fact Lineage
+ Action Origin
+ Authoritative Trace
+ Replay
```

是同一主线，不需要另起架构。

## 7. 后续证据强度分三级，不要笼统声称“可审计”

建议长期用以下分级描述：

### L1 TRACEABLE（可追溯）

能够机械还原：哪个 Actor / Agent / Executor、哪个 Authority、哪个 Order / Request / Payment、哪次 Gate Decision、哪些 reason codes，以及最终 payment / fulfillment / recovery 状态。当前项目已经较强。

### L2 TAMPER-EVIDENT（可检测篡改）

在 L1 基础上，历史 Evidence 被修改、替换或重排时能被检测。可能的机制包括签名、链式摘要、WORM / append-only audit store 等；**是否需要密码学链由真实威胁模型决定，不默认上区块链。** 当前项目只有部分 Hash / Binding 基础，不能整体声称达到 L2。

### L3 VERIFIED ACTOR（执行主体可验证）

Evidence 与真实运行实例、凭证、签名或 workload identity 绑定，而不只是两个字符串相等。当前项目主要到 `DECLARED / BOUND`，不能声称完整 `VERIFIED`。

## 8. 对当前主线的影响：不改 B-12 / H-18

当前 `B-12 Same-Journey Payment Lifecycle / Recovery Continuity` 正在回答：

```text
同一 autonomous journey 进入
UNKNOWN / trusted query recovery / fulfillment failed / status conflict
以后，责任链和支付生命周期证据是否还能保持连续？
```

这正是“可证明问责”进入异常生命周期后的真实验证，因此：

- 不因 Sumsub 新建治理任务；
- 不因 SAFR 新建平行 Runtime Gate；
- 不因 GB/Z 185.8 / 185.9 仍在起草就抢跑实现字段；
- 先完成 B-12 的实测，再由真实断点决定是否需要 Audit / Identity / Transaction Contract 补强。

## 9. 后续触发条件

只有出现以下情况之一，才把外部 WATCH 转成正式执行包：

1. `GB/Z 185.8` 或 `GB/Z 185.9` 进入征求意见 / 发布，出现可机械映射的对象或要求；
2. 当前 Trace / Replay 被实际反例证明“记录能回放，但无法检测篡改”；
3. 出现实测场景要求证明真实 Agent / Executor，而 `BOUND` 已不足；
4. SAFR 后续版本新增与支付场景直接相关、且本项目现有 Gate/Trace 无法表达的机制；
5. 银行/支付真实需求要求将争议、客诉、AML / fraud decision 等纳入同一 Responsibility Trace。

## 10. 当前明确不做

- 不保存模型内部 Chain of Thought 作为审计依据；
- 不因为“tamper-proof”就默认上区块链；
- 不把 Hash / Binding 通过写成业务合法或监管合规；
- 不为 Sumsub 单独实现第三方身份验证平台；
- 不把 SAFR 写成 MAS 强制监管要求；
- 不把正在起草的 GB/Z 185.8 / 185.9 写成现行标准；
- 不为尚未发布的标准提前堆字段。

## 11. 后续跟踪优先级

```text
P0  GB/Z 185.9 智能体交易
P0  GB/Z 185.8 智能体审计
P1  MAS SAFR 后续版本 / pilot / sandbox
P1  GB/Z 242-2026 智能体技术要求正式全文映射
P2  GB/Z 185.1—185.7 与项目 Identity / Tool / Interaction 的最小差距映射

```
