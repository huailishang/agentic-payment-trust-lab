## 4. P9 之后候选：机器资源商业闭环、Cross-Rail 与 Cross-Protocol

以下方向只作为**后续候选**记录，不改变当前 P9 / WebShop / B-04 主瓶颈，也不立即开发稳定币、链上钱包、真实支付 SDK 或更多协议 Adapter。

### 4.1 Cross-Rail Payment（跨支付轨道支付）

触发前提：P9 已形成可重置、可检查的多步骤商务环境，并且当前同轨道支付链已经能够稳定回放。

第一版只验证一个问题：

> 同一个 Task / Mandate（任务 / 委托）里，Agent 先购买机器资源、再完成商户购买，即使两段支付使用不同 Rail（支付轨道），是否仍然共享同一套身份、授权、总预算、绑定、幂等、最终性和 Evidence / Replay（证据 / 回放）约束？

建议最小场景：

```text
用户总预算 = 500 USD
    ↓
Agent 购买 API / 数据 / 算力
    -> 多笔小额机器支付
    -> x402 / stablecoin rail（仅模拟或离线）
    ↓
Agent 完成商品 / 服务购买
    -> card / account rail（模拟）
    ↓
统一验证
    -> cumulative budget
    -> authority scope
    -> identity / executor binding
    -> retry / idempotency
    -> payment finality
    -> service / merchant fulfilment
    -> evidence / replay
```

机器资源支付第一版补充观察字段：`pricing_unit`、`quantity`、`quote_expiry`、`spent_amount`、`pending_amount`、`window_count`、`retry_count`、`service_receipt_ref`。重点覆盖“小额 × 高频 × 自动重试”的累计超支、重复扣款、报价漂移和付费未交付。

成功标准不是证明某一种 Rail 更先进，而是证明现有 Trust Control（信任控制）在 Rail 切换后仍然有效。若必须为某 Rail 写大量专用授权逻辑，说明当前协议中立边界仍需调整。

### 4.2 Metering → Settlement → Fulfillment（计量 → 结算 → 履约）

触发前提：

- B-04 已至少形成可复现的真实 Autonomous Agent 行为证据；
- 机器资源购买有明确的真实外部参考或 fixture；
- 现有字段确实无法机械回答“授权多少、用了多少、扣了多少、交付多少”。

第一版只验证一个问题：

> Agent 为完成任务购买 API / 数据 / 算力时，最高授权额度、实际用量、实际扣款、结算最终性、服务交付和失败补救能否形成同一条可回放经济链。

建议冻结的最小不变量：

```text
actual_charge <= authorized_cap
usage evidence exists
pricing rule is referenced
settlement_pending != terminal failure
same authorization cannot double-settle
payment success != service success
failed / partial service can enter recovery
all stages share stable evidence refs
```

第一轮继续采用离线 / 模拟方式，不把真实 x402 testnet 转账当作优先成功标准。

### 4.3 Cross-Protocol Invariance（跨协议判断不变量）

触发前提：

- 至少有 2 个协议 Adapter 能表达同一类业务事实；
- 已有稳定 Canonical Facts 和 Shared Trust Decision；
- 目标是发现协议差异是否污染核心规则，而不是增加协议覆盖率。

第一版冻结一个业务 Case，并对 2～4 个代表协议比较：

```text
same authority
same agent
same transaction object
same amount / payee
same mutation / failure
        ↓
protocol representations
        ↓
Adapters
        ↓
Canonical Facts diff
        ↓
Trust Decision / reason diff
```

等价事实必须得到等价裁决；协议确实缺少表达能力时，必须显式输出 unsupported / missing evidence，并保留原始协议证据。不得为了让结果“看起来一致”在 Adapter 中偷偷补业务规则。

该方向验证的是 Semantic Interoperability（语义互操作），不宣称实现行业级协议互联互通或统一技术标准。

## 5. 当前明确不做

- 不按顺序继续铺开 S14—S20。
- 不一次性创建所有可信执行模块。
- 不提前设计大而全的协议/支付/身份字段模型。
- 不在主 UI 堆协议字段、证据对象和原始 JSON；技术内容默认折叠为开发者信息。
- 不直接克隆和运行所有外部 benchmark；先借案例、Schema 和评分方法。
- 不在没有明确消费者前抽成公共开发工具包（SDK）或远程服务。
- 不引入真实支付凭证、生产密钥、真实资金或主网操作。
