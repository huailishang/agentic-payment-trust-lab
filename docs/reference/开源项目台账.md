# 外部项目与开源参考台账

> 更新时间：2026-07-27
>
> 用途：把评测、协议、攻击和沙箱项目放在一个地方。以后先按模块归类，再决定是否深入或接入。

## 1. 对应当前五个模块

```text
M1 交互式实验台
M2 内部回归集
M3 外部挑战集
M4 协议集成集
M5 统一评测器

横向：攻击覆盖层
后续：电商 / 银行业务沙箱环境
```

原则：**先借案例和评测方法，不先搬完整框架。**

## 2. Agent 身份 / 运行时授权专项参考

2026-07-29 新增专项台账：[Agent 身份与运行时授权开源项目参考](Agent身份与运行时授权开源项目参考_20260729.md)。

该专项不再按 M1—M5 组织，而按当前 P1—P5 能力链组织，重点跟踪：AARM、Microsoft Agent Governance Toolkit、SPIFFE/SPIRE、Cedar、OPA、OpenFGA，以及 RFC 8693 / AAuth 等开放标准方向。

核心吸收结论：

```text
P1 Delegation
+ P2 Binding
+ P3 Identity
+ P4 Context / Trust Source / Policy
        ↓
Runtime Authorization Gate
        ↓
P5 Receipt / Replay
```

当前仍坚持“参考优先、依赖后置”，不立即把这些外部框架装进主工程。

## 4. 这些项目分别怎么用

### PayBench：拿案例和评分

2026-07-27 扫描时，官网 Phase 1 仍为模拟评测，公开 50 个锁定场景，正式结果尚未发布。官方仓库许可证已核对为 MIT。

本项目固定到上游提交：

```text
f052ab411f28e79c73f3897029a017f29f5cd4e2
```

第一批只吸收 A1 / B1 / C1 / D1 / E1 五组危险案例（Trap）与安全对照（Lookalike），共 10 题：

```text
危险案例（Trap） <-> 安全对照（Lookalike）
错误放行 + 安全场景误拒绝分开统计
允许多个安全答案
```

本地快照位于 `samples/external/paybench/`，只复制最小题目合同和评分所需字段，不引入完整运行时。其模拟结果不能证明真实支付安全；本地 `local_*` 字段属于本项目适配语义，不是 PayBench 官方字段。

### AP2：拿真实协议对象和流程

官方仓库明确包含规范、SDK、Web Client 和整理好的 Samples。本项目 M4 固定到：

```text
Release：v0.2.0
Commit：b4587ac
许可证：Apache-2.0
```

该版本已经包含 Human-Not-Present（HNP）样例和 Python SDK，并更新 Human-Present（HP）样例。

当前只做两个最小流程：

```text
HP：交易时用户在场确认
HNP：用户提前授权，条件满足后 Agent 执行
        ↓
AP2 Flow Adapter
        ↓
本项目协议中立模型
        ↓
现有 Validator
```

本地固定快照：

```text
samples/protocol_snapshots/AP2_v020_HP_cards.json
samples/protocol_snapshots/AP2_v020_HNP_cards.json
```

当前不安装完整 AP2 SDK / ADK / Gemini，不接真实卡、真实密钥和真实资金；不验证签名，也不声明 AP2 Conformance。接入继续固定具体提交或 Release，不自动追随 `main`。

### AgentDojo：拿攻击覆盖层

2026-07-28 再次核对官方仓库：仓库为 MIT License；当前 Release 页面显示最新版本 `v0.1.35`，提交 `a75aba7`。官方说明 API 仍可能变化。默认任务套件含 `banking`、`workspace`、`slack`、`travel`、`webbase`。

本项目不安装该运行时，只固定其方法参考版本。Attack Overlay v1 已落地为“正常支付场景 + 不可信内容 + 越权字段改写尝试 + M5 评测”。

我们先借：

```text
原始场景 + Injection Overlay -> 同一评测器
```

而不是复制它的完整 Agent runtime。

### τ³-bench：拿银行任务和状态评测

2026-03-18 的 v1.0.0 发布增加 `banking_knowledge`：97 个任务、698 份政策/流程文档，覆盖账户管理、信用卡、争议、转账等，并把知识检索和工具操作放在一起评测。

仓库标注 MIT。完整运行通常需要 LLM；当前只研究其任务、政策、工具和 evaluator 组织方式。

### CFAgentBench：拿“禁止副作用”评测

论文报告 1,014 个可机器评分任务规格和 35 个 mock 应用；其中大量高风险动作要求停下来等待人工批准。

最值得借：

```text
执行前状态
    -> 系统动作
    -> 执行后状态
    -> state diff + forbidden side effects + required outputs
```

本轮仅核到论文；代码和许可证在正式接入前继续核对。

### Alipay-PIBench：拿评测分层

论文包含 9 个产品项目、18 个任务，分 Basic 功能完成和 Advanced 风险加固，并结合静态、单元、集成、端到端与语义检查。

我们只借“分层评分”思想，不照搬支付宝业务实现。

### WebShop / ShopGym：留给后面的真实交互环境

- WebShop：MIT License，约 118 万商品、12,087 条购物指令；完整安装需要较重的数据和环境。
- ShopGym：论文报告 6 个沙箱商城和 224 个任务，核心价值是把真实商城结构变成可重置、可检查的沙箱。

当前都不接入代码。

## 7. 后续搜索方式

以后不是“搜到好项目就加”，而是按模块搜：

```text
M1：interactive payment sandbox / agent payment playground
M2：deterministic scenario replay / regression harness
M3：agent payment benchmark / delegated payment
M4：agent payment protocol / commerce protocol samples
M5：state-diff evaluation / side-effect checking / pass^k
攻击层：agent prompt injection benchmark / tool attack
环境层：e-commerce sandbox / banking agent environment
```

候选项目只有回答下面五个问题后才进入实验：

1. 它解决哪个模块的明确问题？
2. 要借的是案例、Schema、评分器还是完整环境？
3. 有没有固定版本、许可证和最小可运行切片？
4. 不接真实资金、真实卡和生产凭证时能否验证核心问题？
5. 引入后能产生新的可证伪结果，还是只增加复杂度？
