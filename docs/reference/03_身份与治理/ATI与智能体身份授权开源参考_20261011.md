# ATI 与智能体身份授权开源参考：支付可信项目交叉点（2026-10-11）

> 状态：**REFERENCE_ONLY / 候选瓶颈参考 / 未批准集成**。
> 目的：把智能体可信基础设施（ATI）及现成开源能力，映射到 Agentic Payment Trust Lab 的**真实缺口、复用边界和启动条件**；供以后评估者选题，不构成新任务派发。
> 相关资料：[既有 Agent 身份与运行时授权参考（2026-07-29）](Agent身份与运行时授权开源项目参考_20260729.md)、[项目瓶颈地图](../../01_项目现状/PROJECT_BOTTLENECK_MAP.md)、[F 阶段外部验证路线](../../02_未来规划/F阶段公开验证路线_20260917.md)。

## 一、先说明与当前项目的关系

- **A—D**：评测、授权/绑定、支付生命周期、审计/恢复的本地代表性链路已关闭，不因找到新框架而重开。
- **E / B-15**：已经借鉴 SPIFFE 的 X.509-SVID 语义，完成有界、**本地合成凭据**的身份与持有证明、重放等代表性验证。尚未验证真实 SPIRE 签发、运行实例 Attestation（证明进程/工作负载身份）、在线轮换或跨信任域接入；不要把“已用 SPIFFE 规范测试”说成“已接入 SPIRE”。
- **F / B-06**：战略缺口仍是**第二 Provider（支付宝 Sandbox）的有效 Payment-Proof、Provider 响应与交易绑定实证**，安全 fixture 路线尚受约束。身份/证书开源项目**无法替代支付 Provider 的付款凭证**。
- **B-16 / H42**：当前可执行的是 Agent-facing 输入污染到受治理动作的**离线测量**；以下候选不抢占 H42，不修改 `CURRENT.md`、合同、API 授权或项目瓶颈优先级。

一句话分工：**身份系统回答“哪个 Agent 在发请求”，授权系统回答“它按规则能不能执行”，本项目还要独立回答“用户是否真实授权了这笔具体交易、扣款结果是否可信、能不能追责”。**

## 二、五个候选项目的交叉点与复用判断

| 候选（原始入口） | 大白话作用 | 与本项目交叉点 | 现状与复用决策 | 何时才值得启动 |
|---|---|---|---|---|
| [SPIFFE / SPIRE](https://github.com/spiffe/spire)；[Workload API 规范](https://github.com/spiffe/spiffe/blob/main/standards/SPIFFE_Workload_API.md) | 给正在运行的服务/Agent 发可验证的“工作证”，支持身份认证、证书轮换、mTLS | P3 身份真实性、B-15 本地 SVID 实验、F3 真实身份提供者 | **优先级 P1，先做差距测量**。已有本地有界 X.509-SVID，不重做 verifier；未来重点验证真实签发、Attestation、轮换与撤销/过期后的 fail-closed | 有第二运行主体或外部环境，且本地合成身份已不足以提供所需证据；有隔离环境和明确授权 |
| [Open Policy Agent（OPA）](https://github.com/open-policy-agent/opa) | 把“允许付款吗、是否要人工确认”的规则放进独立策略引擎 | 现有 Runtime Authorization Gate / P4 Policy | **优先级 P1，策略对照参考**。先比较决策语义与错误路径，不直接替换已验证的支付 gate | 真实出现跨 Agent/跨业务复用的策略管理、版本治理或难解释的规则漂移 |
| [OpenFGA](https://github.com/openfga/openfga) | 记录“用户—Agent—账户/商户”之间谁被授予什么权限 | P1 委托关系、P3 Agent 主体关系 | **优先级 P2，复杂关系候选**。关系准许 != 支付时具体授权，也不负责金额/订单绑定 | 多主体、多级委托、资源级授权/撤销产生反复缺口，现有模型不能清晰表达 |
| **ATI 官方生态与接入 SDK**：[CNNIC 官方发布](https://www.cnnic.cn/n4/2026/0930/c326-11687.html)、[ATI MVP](https://www.cnnic.cn/n4/2026/0916/c326-11676.html) | 以 DNS + PKI 为 Agent 提供身份、发现和可信连接 | F3 对外身份发现、跨组织 Agent 可信连接；国内互联生态 | **优先级 P2，先核验公开接口/可用范围**。CNNIC 已发布平台，**不能据此认定其服务端完全开源，亦不能认定 ATI 与 SPIFFE 证书/身份语义直接兼容**。阿里云 ATI SDK 的公开下载、授权许可和具体接口需要独立复核 | 获得官方可复现 SDK/测试入口及受控接入资格，并且有支付 Agent 跨主体发现/互信需求 |
| [ACPs-community 智能体协作协议参考实现](https://github.com/AIP-PUB/ACPs-community) | 提供智能体注册、CA 证书、发现、SDK 与互联示例 | F3 多 Agent 可信注册/发现、异构协作适配 | **优先级 P2，规格/参考实现对照**。先测其注册与认证模型同现有 Canonical Identity 是否可映射；不引入整个基础设施 | 至少两个独立 Agent 需要跨域发现/协作，且测出 SPIFFE/ATI/现有接口解决不了的具体差距 |

**术语警告**：ACPs（Agent Collaboration Protocols，智能体协作协议体系）**不是**本项目所适配的 ACP（Agent Commerce/Payments 语境的支付协议）；两者不可混用字段或验收结论。ATI、ACPs 与 SPIFFE 在身份/证书机制上可能有重叠，但互通需要按证书链、标识格式、信任锚、发现/注册接口逐项测量，不能直接推断。

## 三、哪些东西能复用，哪些仍必须留在支付核心

```text
用户指令 / 用户委托
    ↓
[工作负载身份] SPIFFE/SPIRE；未来可测 ATI / ACPs 可信身份与发现
    ↓ 仅输出身份事实：是谁、凭据来源、信任锚、证书状态、持有证明
[授权决策] 现有 Runtime Gate；OPA / OpenFGA 仅做候选策略或关系事实
    ↓ 必须结合用户真实委托 + 动作 + 金额 + 收款方 + 订单版本 + 时效
[本项目 Payment Trust Core]
    ↓ 交易/请求绑定、确认、幂等/重放、状态、Provider Proof、审计/恢复
[真实或沙箱支付 Provider] 独立提供可信支付结果证据
```

不能混淆的四条边界：

1. **可信 Agent 身份 ≠ 用户授予付款权**。即使 mTLS 身份正确，也要有特定支付委托和执行前判断。
2. **策略允许 ≠ 支付已经成功**。OPA / OpenFGA 不签发 Provider Payment-Proof，不替代回调验签、主动查询或最终结算状态。
3. **传输连接可信 ≠ 交易对象未被替换**。仍须验证 order / amount / currency / payee / mandate / nonce、有效期和签名绑定。
4. **本地模拟 PASS ≠ 真实跨域互联或 Provider PASS**。证据级别要分开记录，不能从一个阶段自动晋级。

## 四、映射到未来“瓶颈候选”，不是立刻立项

| 观察到的新断点（暂不新编 B/H 号） | 候选外部参考 | 最小可复现测量 | 有价值的后续动作 |
|---|---|---|---|
| **F3：真实运行主体的签发、证明、轮换和信任域识别**（B-15 既有本地合成边界之外） | SPIFFE/SPIRE | 两个隔离 Agent/服务；正确签发/持有证明通过，伪造主体、错误信任锚、过期/轮换、身份重标记、重放均拒绝；记录真实 vs 合成边界 | 若命中真实差距，再提最小 Identity Provider Adapter；不重写支付规则 |
| **Policy：多个调用入口出现同一授权规则难以维护或漂移** | OPA（与既有 Cedar 参考对照） | 冻结相同输入、Policy 版本、ALLOW/DENY/CONFIRM/WAIT 和错误行为；比较原 gate 与候选引擎 | 仅在反复可证实的收益下外置策略；保持现有 gate 的支付绑定校验 |
| **Delegation：多用户、多 Agent、多账户的权限关系及撤销难以表达** | OpenFGA | 冻结三层委托与撤销场景；错误主体、越权资源、撤销后请求必须拒绝 | 只考虑关系事实查询层；不把关系许可升级为直接付款许可 |
| **Interoperability：跨组织发现/注册/身份认证成为真实外部阻塞** | ATI 官方接口、ACPs-community | 固定官方版本与证书/信任锚语义；模拟正常发现、错误域名/证书、错误代理及失效注册，逐项比对 | 若获得可靠官方接入条件，再开展受控兼容适配 |

**不变的阻塞项**：B-06 缺少的支付宝有效 Payment-Proof / Provider 绑定证据，不因以上任何实验成功而关闭；B-16/H42 也不因这份文档重新排序。

## 五、启动门与停止门

- 当前仅存档、核验官方接口与许可证，不安装依赖、不运行网络服务、不读取真实密钥、不进行 Sandbox 或真钱操作。
- 真正立项必须先：① 评估者确认**当前最前断点**及重复真实证据；② 对比现有实现的新增价值与成本；③ 冻结单一最小实验合同、输入、负例、独立检查器和回滚边界；④ 获得依赖/网络/API 的**单独明确授权**。
- 完成后由独立评估者判断 `CONTINUE / STOP / SWITCH`，不能以“成功跑起开源项目”代替项目有效性验收。
- 只有身份/策略机制被支付项目和**第二个独立消费者**（如 data-warehouse-agent）都证实需要，才评估抽取到公共 Enterprise Agent Control Plane；支付特有委托和交易生命周期继续留在本仓。
