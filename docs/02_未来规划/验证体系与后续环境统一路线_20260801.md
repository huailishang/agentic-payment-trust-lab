# 智能体支付验证体系与后续环境统一路线

> 日期：2026-08-01  
> 适用仓库：`agentic-payment-trust-lab`  
> 定位：统一整理规则实验、外部挑战、协议适配、模拟商城、测试网和银行沙箱之间的关系，并给出下一阶段优先级。

## 1. 一句话结论

当前项目已经完成了**离线规则、可信控制、协议样品和统一评测底座**，但还没有完成“Agent 在一个真实可操作的商务环境中执行完整购物任务”的环境层。

因此下一步不应继续机械增加 JSON 案例，也不应默认直接进入 x402 测试网；更合理的主线是：

```text
Princeton WebShop 外部商城
        ↓
Commerce Adapter + Buy Now拦截
        ↓
现有 Trust Control Plane
        ↓
本地 Payment / Fulfillment Sidecar
        ↓
M5检查完整动作链与最终状态
```

当前第一任务：

```text
P9-WEBSHOP-UPSTREAM-PREFLIGHT-V1
```

自建 MiniShop 降级为备用方案；只有 WebShop 无法提供稳定环境接点时才重新考虑。

## 2. 为什么容易把“离线测试完成”理解成“项目验证完成”

项目目前同时存在多种验证方式，它们解决的问题不同。

```text
规则实验台
    验证给定事实下应该 ALLOW / DENY / CONFIRM / INDETERMINATE

协议离线适配
    验证 AP2 / x402 等外部对象能否安全映射进内部模型

模拟商城环境
    验证 Agent 能否在多步骤商务任务中持续遵守授权和状态约束

公开测试网
    验证真实 SDK、签名、钱包、facilitator 和网络行为

银行业务沙箱
    验证信用卡、争议、转账、政策和工具操作等银行任务
```

P8-A 通过，只说明第二层中的 x402 离线适配已经完成，不等于第三、第四、第五层已经完成。

## 3. 统一验证分层

为避免与支付生命周期 L1—L9 混淆，本文使用 V1—V5 表示验证层级。

### V1：确定性能力与规则验证

目标：证明授权、绑定、身份、可信来源、状态恢复和回放等底层能力按预期工作。

已有组成：

- S01—S13 内部回归；
- M1 交互式实验台；
- M2 冻结回归基线；
- M5 统一评测器；
- P1 Delegated Authority；
- P2 连续 Binding；
- P3 Agent / Executor Identity；
- P4 Trust Source / Context Policy；
- P5 Evidence / Replay；
- P6 原交易绑定、最终性和状态冲突。

当前状态：**已完成第一轮稳定底座**。

它能证明：

```text
给定一组明确事实
→ 系统能够确定性判断
→ 并检查是否产生禁止副作用
```

它不能证明 Agent 在真实多步骤环境里不会走偏。

### V2：外部挑战与协议离线适配

目标：避免“自己出题、自己判卷”，并验证外部协议对象能否映射到协议中立模型。

已有组成：

- PayBench：8/10 可执行，剩余 D1 隐私披露两题未覆盖；
- AP2：Human-Present / Human-Not-Present 两个最小流程；
- Attack Overlay：正常文本、越权写入和合法提供方状态更新；
- x402：六类离线一致性案例和严格输入类型边界。

当前状态：**核心切片已完成，但不是所有协议和挑战都完成**。

P8-A 已证明：

```text
x402合成请求 / 付款要求 / 证明 / 状态 / 交付
        ↓
协议中立模型
        ↓
Binding / Idempotency / Finality / Conflict / Replay
```

可以在当前有限语义内工作。

尚未证明：

- 官方 wire format 完整兼容；
- 官方 SDK 行为；
- 密码学签名；
- facilitator 真实行为；
- 商户端实现；
- 网络、并发和链上最终性。

### V3：本地商务环境沙箱

目标：让 Agent 在一个可重置、可检查的模拟商城中真正执行多步骤任务。

文档中的外部参考：

- WebShop：模拟商品搜索、点击、选择和购买；
- ShopGym：可重置、可检查、稳定商城沙箱的方法；
- UCP / ACP：商品、购物车、结账、订单、履约和售后对象。

当前状态：**未实现**。

这层与现有 M1 实验台的区别：

| 现有 M1 交互实验台 | V3 模拟商城 |
|---|---|
| 人直接修改金额、商户等字段 | Agent 通过搜索、点击、加购和结账产生状态 |
| 单次规则计算 | 多步骤任务链 |
| 输入事实基本由测试者准备 | 事实来自商城页面、工具返回和状态变化 |
| 重点看裁决结果 | 同时看动作序列、最终环境状态和禁止副作用 |
| 不包含完整购物流程 | 包含商品、购物车、订单、支付和履约 |

模拟商城能暴露的真实问题包括：

- 商品页、购物车和结账价格不一致；
- 商品、商户或 payee 在不同页面被替换；
- 网页隐藏提示要求扩大用户授权；
- 同一购物任务被重复下单或重复付款；
- 支付返回超时后 Agent 盲目重试；
- 支付成功但商品未交付；
- 订单需要重新确认，但 Agent 继续执行；
- 商城索取与任务无关的个人数据。

### V4：公开测试网与真实外部基础设施

目标：验证真实网络、SDK、钱包、签名、facilitator 和测试币流程。

当前候选：

```text
P8-B x402 public testnet smoke test
```

当前状态：**等待人工授权**。

需要明确授权：

- 外部 HTTP / API；
- Base Sepolia 或 Solana Devnet；
- 临时测试钱包和本地签名；
- faucet / test token；
- 测试网交易。

这层适合验证机器或 API 付费，但不能替代模拟购物环境。它们是两条不同场景线：

```text
x402测试网
→ Agent / 服务购买 API、数据或算力

模拟商城
→ Agent 代表用户搜索、选择、下单和处理履约
```

### V5：银行与企业业务沙箱

目标：把相同可信控制能力放入信用卡、账户、转账、争议和企业付款任务中验证。

外部参考：

- τ³-bench banking knowledge；
- AgentDojo banking 方法；
- CFAgentBench 的状态差异和禁止副作用评测；
- 企业采购、发票、供应商和审批链样品。

当前状态：**未开始，仅保留为后续环境线**。

这层不应在模拟商城之前抢占主线，因为当前项目首先需要证明公共内核能够在一个完整环境中运行，而不是同时建设多个行业沙箱。

## 5. 现阶段真正缺少的能力

### 5.1 首要缺口：环境状态与动作链

目前系统能够判断“给定订单能不能付”，但还没有一个环境让 Agent 自己产生订单。

缺少：

```text
搜索结果
商品详情
购物车
结账对象
订单版本
支付尝试
履约状态
环境重置
动作日志
最终状态差异
```

没有这一层，就无法证明 Trust Control Plane 能够横切一个完整 Agent 任务链。

### 5.2 商务对象缺口

当前协议中立模型已有订单和支付骨架，但没有通过一个真实商城链路系统验证：

- 商品目录；
- 库存；
- 购物车；
- 优惠和价格有效期；
- Checkout；
- Order；
- Fulfillment；
- 售后状态。

不建议现在直接完整接入 UCP 或 ACP。应先由 WebShop 的真实商品选择和购买动作经过 Commerce Adapter 产生对象，再判断哪些字段确实需要协议适配。

### 5.3 数据最小化缺口

D1 没有完成，不是因为题目不重要，而是当前缺少统一的数据披露事实：

```text
请求了什么数据
谁请求
为了什么目的
任务是否必要
是否超过用户授权
是否真的发送出去
```

这更适合在后续 WebShop 商务扩展层的收货地址、联系方式、身份信息和推荐场景中验证，而不是继续用孤立 JSON 模拟。

### 5.4 真实身份和密码学缺口

P3 当前离线最高为 `BOUND`，尚未验证：

- 凭证持有证明；
- 签名有效性；
- Agent runtime 身份；
- 凭证撤销；
- 信任链。

这是真实缺口，但目前没有必要建设完整 PKI。应等测试网、外部商户或第二个真实消费者提出明确凭证要求后再做最小切片。

### 5.5 外部网络和真实协议行为缺口

x402 测试网能补：

- 官方 SDK；
- 真实签名；
- facilitator；
- 网络失败；
- 测试网结算。

但它主要验证机器支付基础设施，不能验证完整的人类代理购物链。

## 6. 下一步优先级判断

按“是否直接服务项目第一性原理、能否消费已有能力、是否需要外部授权、能否暴露新缺口”排序：

| 候选 | 业务价值 | 消费现有 P1—P6 | 外部授权 | 当前建议 |
|---|---:|---:|---:|---|
| WebShop 外部商城接入 | 高 | 全部消费 | 分阶段需要 | **第一优先；当前先做上游预检** |
| UCP / ACP 最小对象适配 | 高 | 主要消费订单与支付绑定 | 不需要 | WebShop对象映射稳定后再做 |
| D1 数据最小化 | 中高 | 消费授权、可信来源和证据 | 不需要 | 放在WebShop支付接入之后 |
| x402 测试网 | 中高 | 消费绑定、身份、状态和回放 | 需要 | 已暂缓，可选并行分支 |
| Agent VERIFIED / 签名体系 | 中 | 消费身份闸门 | 可能需要 | 等真实接入需求，不做完整 PKI |
| 银行业务沙箱 | 高但更远 | 可消费公共内核 | 可能需要模型/API | WebShop纵向链路成功后再启动 |
| 继续增加 S14—S20 | 低 | 局部 | 不需要 | 不建议机械扩展 |

### 7.3 为什么本包不直接安装

当前机器已有 Windows Conda 和 `agent` 环境，但 `agent` 使用 Python 3.12.13，缺少 Gym、Flask 和 Pyserini，不适合直接承载 WebShop 的 Python 3.8.13、Gym 0.24、Flask 2.1、Torch 1.11、spaCy 3.3 和 Pyserini 0.17 旧依赖组合。用户已允许在 P9-A2 新建独立 `webshop38` 环境，因此本包只做预检，不修改 `agent`。

直接安装会把以下问题混在一起：

```text
旧依赖兼容
商品数据下载
Lucene索引
Java / Pyserini
商城环境运行
本项目适配逻辑
```

P9-A1 只做上游和接点预检；P9-A2 才建立隔离环境并下载 small 数据。

### 7.4 后续必须接入的现有能力

P9-A1 不修改 P1—P6。后续阶段按以下顺序消费：

```text
P9-B：P1授权 + P2连续绑定 + P3身份 + P4可信来源

```

`click[buy now]` 没有执行，购买计数为 0。该结果只证明外部 WebShop 运行边界已建立，不代表 Trust Control Plane、支付或履约已经接入。

P9-B1 离线 Commerce Adapter 已通过独立复核：只接收内存中的固定 fixture，把原始指令与当前商品事实分开映射为 `Order + TransactionRequest`。它不读取 WebShop、本地文件或环境变量，不运行 Buy Now，不推断指令与商品匹配，也不产生授权、购买、支付或履约结论。

P9-B2 已形成离线 Runtime Authorization Gate 候选：显式消费授权、订单与执行绑定、Agent / Executor 身份和上下文来源事实。只有最终 `ALLOW` 才调用一次本地假 checkout callback；`DENY / CONFIRMATION_REQUIRED / INDETERMINATE` 均零回调。回调异常只尝试一次并失败关闭。真实 WebShop、真实 Buy Now、支付、履约、网络、环境和 UI 均未执行。

P9-B2-R 已通过独立复核：共享 Runtime Gate 已补齐稳定的阶段原因。当前动作错误会产生 `p4:current_action_mismatch`，来源摘要绑定到其他金额会产生 `p4:source_coverage_value_mismatch`；WebShop outcome 与 RuntimeGateRecord 透传同一组原因，原有决策和 callback 次数保持不变。

P9-C1 已形成离线 Sidecar 候选：通过显式支付、履约、查询/异步观察和已知尝试，复用现有恢复、冲突与生命周期规则，输出有效支付状态、重复付款阻断、离线重试候选、履约、任务与补救结果。全部是本地固定事实；没有运行真实支付、查询、异步回调、重试、履约或 UI。

兼容层偏差限定在 `webshop38`：NumPy 1.23.5、MKL 2021.4、Transformers 4.19.2、ONNX Runtime 1.12.1。主项目与共享 `agent` 环境不吸收这些旧依赖。

## 10. P9-A1 验收门

P9-A1 合同已经明确：

1. WebShop 是外部验证环境，不成为新业务内核；
2. 固定官方来源、提交和 MIT 许可证；
3. 通过源码检查验证文本环境和购买接点；
4. 第三方源码只放 Git 忽略目录；
5. 不运行或修改上游环境；
6. 不安装依赖和下载商品数据；
7. 不修改 P1—P6 或 UI；
8. 全量 280 项现有测试必须继续通过；
9. 只有 P9-A1 通过，才进入 P9-A2。

## 11. 最终结论

项目已经具备较完整的“可信支付裁判”，下一步需要把它接到一个已有的外部比赛场地。

```text
WebShop负责：商品、搜索、页面、选择、购买动作
本项目负责：授权、绑定、身份、可信来源、支付状态、履约和评测
```

因此当前不重新造商城，而是先建立一个可复现、可审计、不会污染主项目的 WebShop 接入口。
