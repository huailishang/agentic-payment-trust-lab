# 智能体支付实验项目中控

> 更新时间：2026-07-30

## 1. 一句话定位

本仓库不是生产支付系统，而是一个面向学习、实验和未来开发者验证的**智能体支付可信验证实验台**。公开展示名统一为 **Agentic Payment Trust Lab / 智能体支付可信实验室**：用协议中立模型、固定风险场景和外部挑战，验证智能体（Agent）代表用户下单、付款、履约、退款和恢复时，是否遵守委托、能否解释异常、能否留下可追溯证据。

项目能力不局限于信用卡，公开仓库名统一为 `agentic-payment-trust-lab`。项目不接真实卡、真实资金、生产商户、生产私钥、联机放行或清算网络。

## 2. 当前结构：一仓两域

唯一主仓库就是当前仓库根目录，仓库名为：

```text
agentic-payment-trust-lab
├── 支付域
│   ├── 委托 / 智能体意图
│   ├── 订单 / 支付请求
│   ├── AP2 / ACP 等适配器
│   ├── 允许（ALLOW） / 拒绝（DENY） / 需要确认（CONFIRMATION_REQUIRED） / 无法判定（INDETERMINATE）
│   ├── 支付执行 / 状态恢复
│   ├── 履约 / 退款 / 争议
│   └── 生命周期教学界面（UI）
│
└── 可信执行域
    ├── 规范化
    ├── 哈希 / 绑定
    ├── 后续签名 / 身份
    ├── 后续幂等 / 状态验证
    └── 后续审计 / 不变量
```

依赖方向只有：

```text
支付域
    -> 调用可信执行域
    -> 获得“对象是否一致、证据是否可信、是否存在重复或冲突”等确定性事实
    -> 支付域自己决定业务动作
```

可信执行域不得直接返回支付业务的 `ALLOW`、`DENY`、`CONFIRMATION_REQUIRED`、退款、争议或重试政策。

## 3. 当前已经做到哪里

### 支付域

当前代码已经覆盖 S01—S13：

- S01—S08：委托边界、预算、商户、品类、次数、过期、重复请求和人工确认。
- S09：订单价格、商品等变化与重新确认。
- S10：支付成功但履约失败。
- S11：退款、部分退款与争议，并区分争议结案和经济补救完成。
- S12：支付状态 `UNKNOWN` 时先查询原交易，再决定恢复动作，禁止盲目重复扣款。
- S13：声明 Agent 标识与委托中的预期标识不一致时拒绝，但不把“标识一致”宣称为真实身份认证。

S01—S13 固定场景已经形成可回放闭环。2026-07-27 已完成 TP-22 / S12 正式复评：S12 专项 9/9 PASS，TE02 改造前全量 104/104 PASS；S13 随后也已接入当前回归集。

正式界面（UI）已收敛为支付生命周期 L1—L9 的唯一主入口；可信执行学习沙盘只保留为历史教学原型，不再建设第二套正式界面（UI）。

### 可信执行域

当前真正落地的稳定能力仍很小：

```text
src/agentic_payment_experiment/trusted_execution/
├── __init__.py
├── hashing.py
├── binding.py
└── execution_facts.py
```

已有 TE01 哈希（Hash）、TE02 规范化、TE03 绑定与 TE04 执行事实能力。S09 已真实消费订单绑定事实；S12 已真实消费状态观察与幂等事实；S13 已让付款前委托验证消费“声明标识绑定事实”。最关键的边界仍保持：Binding `INVALID` 不自动等于 `DENY`，Idempotency `VALID` 不自动等于允许再次扣款，声明标识 `VALID` 也不等于真实身份已认证。

S13 已完成，但当前主线不再默认进入 S14。项目先从“继续堆场景”切换到**模块化实验与评测闭环**：先把现有逻辑做成可交互实验台，引入外部挑战和统一评分，再让外部失败结果反推 S14—S20 哪些真的值得开发。

2026-07-30 已落地 P1.1 的最小可信事实：`ConfirmationRecord` 保存用户确认时的订单关键内容摘要、授权与订单版本、确认时间与失效时间；`verify_confirmation_binding()` 在执行前重新计算当前订单摘要，并返回 `VALID / INVALID / MISSING_EVIDENCE` 与失效原因；`execute_with_confirmation_gate()` 只在 `VALID` 时调用支付回调。它没有接真实支付，也没有把业务裁决下沉到可信执行域。当前仍是**P1 部分完成**：`IntentMandate` / `Order` 尚未正式承载 authority version，S08/S09 尚未把确认记录接入主验证路径，故不能宣称整条 P1 已验收通过。详见 [P1 执行记录](../04_验证体系/P1授权绑定与执行前核验执行记录_20260730.md)。

## 4. 当前最重要的判断

现在最缺的不是更多字段或更多场景，而是**独立于实现代码的验证环境**。当前全量 `186/186 PASS` 能证明回归测试通过，但不能单独证明规则在现实里合理。

下一阶段采用五模块结构：

```text
M1 交互式实验台
    -> 用户修改少量关键条件，后端真实重新计算

M2 内部回归集
    -> S01—S13 保留，防止已有能力回归

M3 外部挑战集
    -> 第一批吸收 PayBench，减少“自己出题、自己判卷”

M4 协议集成集
    -> 第一批接 AP2 官方 Samples，验证系统能吃外部协议对象

M5 统一评测器
    -> 不只看最终枚举，还看错误放行、错误拒绝、漏确认和禁止副作用

Attack Overlay
    -> 把不可信网页/工具内容叠加到正常支付场景，验证它不能直接改写可信支付输入
```

Attack Overlay v1 已完成：1 个正常对照 + 4 个攻击共 5/5 PASS，4 个越权改写尝试全部被阻断，0 决策漂移、0 可信状态变更；当前仍是确定性信任边界实验，不代表真实 LLM Prompt Injection 防御已经成立。

统一主实验台入口也已完成：运行 `python run_experiment.py --serve --open` 时，后端会统一计算 S01—S13、PayBench、AP2 HP/HNP、Attack Overlay 和 M5 评测。正式网页现在使用“模块下拉 + 场景/流程下拉”联动：M2 对应 S01—S13，M3 对应 A1—E1，M4 对应 HP/HNP，M5 展示各模块统一评测，Attack Overlay 对应 A00—A04；只在 M2 下继续展开原有交互实验、生命周期矩阵和关键环节，不恢复大块静态“模块总览”。当前 PayBench 为 8/10 可执行，PARTIAL 只来自 D1 隐私披露的 2 个未覆盖挑战。WebShop、ShopGym、τ³-bench 等更重环境继续后置。

当前开发顺序已经重新定标，并于 2026-07-29 完成第一轮能力归位：

```text
M1 / M2 / M3 / M4 / M5 / Attack Overlay 第一轮【已完成】
    ↓
停止继续堆 S 编号 / 异常案例 / UI 入口
    ↓
Architecture Rebaseline v1【能力归位已完成】
    ├─ A. 成熟支付交易底座：已有最小骨架，继续对齐行业
    ├─ B. Agent Trust Control Plane：已识别核心能力与 P0/P1 缺口
    └─ C. 现有代码：已映射为成熟支付 / Agent 新增 / 测试工具 / 案例
    ↓
Agent Trust Control Plane 最小领域模型【已完成】
    ↓
第一条纵向切片【当前下一步】
P1.1 确认绑定与执行前核验【已完成】
    ↓
P1.2 接入主领域模型、S08/S09 与 M5【当前下一步】
    ↓
再决定 P2 连续 Binding 到 Payment
```

当前明确不继续 D1 / S14，也不立即搬代码目录或重做 UI。能力归位与缺口结论见 [能力归位与缺口分析 v1](../03_架构设计/能力归位与缺口分析_v1.md)，最小领域模型见 [Agent Trust Control Plane 最小领域模型 v1](../03_架构设计/Agent_Trust_Control_Plane_最小领域模型_v1.md)；最高层约束仍以 [智能体支付架构基线 v1](../03_架构设计/智能体支付架构基线_v1.md) 为准。

2026-07-29 外部信源复核后，P1—P5 新增一条横切主线 `Runtime Authorization Gate`：P1 提供授权、P2 提供连续绑定、P3 提供执行身份、P4 提供上下文 / Trust Source / Policy 输入，最后在真正产生支付副作用前统一裁决；P5 负责 Receipt / Replay。它不是新增阶段，当前仍先执行 P1。外部项目与开放标准参考见 [Agent 身份与运行时授权开源项目参考](../reference/Agent身份与运行时授权开源项目参考_20260729.md)。

M1 已让 S01—S13 在现有正式 UI 中各自暴露最多 3 个关键条件；通过 `python run_experiment.py --serve --open` 修改后，会调用本地 Python 后端重新计算，并同步刷新决策结果、生命周期矩阵、当前关键环节和订单差异，不再出现“上面结果变了、下面矩阵还是旧场景”的割裂。详细见 [M1 交互式实验台执行记录](../04_验证体系/M1交互式实验台执行记录_20260727.md)。

后续整体修正顺序统一以 [整体修正执行计划](../02_未来规划/整体修正执行计划_20260729.md) 为唯一主计划；当前阶段施工细节见 [第一纵向切片：Delegated Authority v1](../02_未来规划/第一纵向切片_Delegated_Authority_v1.md)。模块化实验与评测路线继续作为测试体系参考，外部项目统一维护在 [外部项目与开源参考台账](../reference/开源项目台账.md)。

这样推进的价值是：**先让系统接受外部问题和外部协议的检验，再补详细设计；不是先把架构和字段想得很完整，再证明自己设计是对的。**

## 5. 当前不做

- 不重新建立 `financial-agent-trusted-execution` 独立开发主线。
- 不建设第二套正式教学界面（UI）。
- 不一次性实现签名、区块链、智能合约、共识、审计全家桶。
- 不为了协议覆盖率同时接入 AP2、ACP、UCP、x402 的完整开发工具包（SDK）。
- 不接真实支付、真实卡、生产凭证、主网资产或生产放行规则。
- 不把 哈希/签名验证通过写成“业务合法”“支付安全”或“监管合规”。
