# Robinhood Agentic Trading / Agentic Credit Card：金融 Agent 权限边界参考

> 调研：2026-11-15；状态：REFERENCE_ONLY；仅作为后续瓶颈评估输入，不重开已关闭的 H-* 包，不扩大预算或付款授权。
> 来源等级：企业官方产品公告、帮助中心与 CEO 访谈（产品事实以官方帮助中心为优先；规模数据属于公司/高管自报）。
> 本项目仍只进行本地/离线/已批准沙箱的 Trust Contract 验证，不接入 Robinhood 账户、MCP 凭据、真实交易或生产资金。

## 1. 原始信源与事实分层

- Robinhood 官方公告：《Robinhood is Now Open to Agents》（2026-05-27）：https://robinhood.com/newsroom/robinhood-is-now-open-to-agents/
- Robinhood 官方帮助中心：《Onboarding an external agent》：https://robinhood.com/us/en/support/articles/agentic-trading-overview/
- Robinhood 官方帮助中心：《Setting up an agent》：https://robinhood.com/us/en/support/articles/setting-up-an-agent/
- Robinhood 官方公告：《Robinhood Puts the Power of Hedge Funds in Every Trader's Pocket》（2026-09-29）：https://robinhood.com/newsroom/hood-summit-2026/
- No Priors / Vlad Tenev 访谈（2026-11-05，28:49 附近谈 Agentic Trading）：https://www.youtube.com/watch?v=yULk8eNa2mg

**已核实的产品机制（官方资料）**：Robinhood Trading MCP 支持外部 Agent 连接交易账户；下单被限定于独立的 Agentic 交易账户，资金来自用户单独划拨；内建 Agent 使用单独账户、可选择模型、默认启用交易批准（用户可在了解风险后选择关闭）；账户活动和交易可见，支持停止/断开。**重要例外**：外部 Trading MCP 文档说明 Agent 的*读取范围*可能覆盖用户全部 Robinhood 账户信息，不能把“下单限定于独立账户”误写为“所有信息均隔离”。

**与支付更直接的产品机制（官方资料）**：Agentic Credit Card 通过 Banking MCP 将 Agent 绑定到专用虚拟卡，用户设置支出限额，选择是否启用逐笔手动审批；默认虚拟卡不暴露主卡号和其他账户信息，可查看记录并停用/删除。**注意**：交易账户与信用卡属于不同产品，资金限额、确认默认值、法律责任及撤销时效不能混用。

**团队自报而非安全证明**：2026-11-05 访谈称超过 15 万名客户开设 Agentic Trading 账户，工具调用约每天 3000 万次；这是开户与调用规模，不是活跃交易人数、真实成交笔数、安全攻击通过率或收益率。9 月官方发布也重复类似数字。

## 2. 对本项目有意义的信任链

    用户授权（用途 / 范围 / 金额 / 次数 / 时效）
      → 专用 Agent 权限与资金容器（账户 / 虚拟卡）
      → 可见、可撤销的 MCP 工具入口（读写权限分离）
      → 每笔工具请求的真实执行前约束（对象 / 金额 / 交易类型 / 确认）
      → 执行、账务或交易状态
      → 活动记录 / 对账 / 异议 / 恢复

**本质**：模型决定“建议做什么”与金融机构执行“实际允许做什么”必须隔离；隔离账户只是资金损失上限控制之一，不能替代单笔交易绑定与风险决策。MCP 是工具协议，不自动保证授权、资金限额、抗重放或争议处理。

| 外部机制 | 对本项目已有链路的映射 | 尚未被外部资料证明 |
|---|---|---|
| 专用 Agent 资金账户 | Delegated Authority / Scope / Limit / Spending Envelope | 账户资金限制是否等于跨交易累计授权、并发抢额与退款恢复正确 |
| 虚拟卡 + 支出限额 | Agent→Payment Instrument 绑定；单笔/累计金额约束 | 商户、商品、税费、汇率变化是否逐次触发可信再确认 |
| 可选择审批 | Confirm Gate / Consent Version / Human-in-the-loop | 无人批准模式下的风险分层与撤销竞态是否全覆盖 |
| 单独下单权限、可见广范围读权限 | Principal / Agent / Tool 读写权限分离 | 数据泄露控制；不能因为写权限小就断言读权限也小 |
| 交易活动记录与停用 | Audit / Revocation / Recovery | 断开后在途请求、交易所已受理订单或已结算资金是否可撤销 |
| 高频工具调用 | Idempotency / Rate Limit / Replay / Observation | 3000 万次调用不等于 3000 万笔支付或交易执行 |

## 3. 批判性判断：不能照搬的部分

1. **证券交易≠消费者支付**：证券订单可能部分成交/撤单/波动成交；购物支付涉及商户、订单、履约、退款、争议。共用授权与治理思想，不复制交易状态机到订单支付。
2. **“隔离账户”不等于可信意图**：损失可控≠资金划拨合法；多步骤代理仍可能被恶意上下文诱导偏离用户要买的商品。
3. **有活动日志不等于可复核证据**：必须绑定原始用户指令、Agent 身份、授权版本、工具参数、支付结果与履约事实。
4. **撤销不是原路撤回**：禁用 Agent 只控制后续权限，已受理、在途及已结算操作仍可能需要查询、冲正、退款或人工处理。
5. **官方风险披露**：Robinhood 明确指出投资可能亏损、AI 会误读信息、第三方 AI 提供方数据风险与用户责任；不得把官方营销语句当成独立安全评测。
6. **外部 MCP 不等于本地测试能力**：需账号、权限及真实外部依赖；当前项目没有相应授权，不能作为当前主线执行环境。

## 4. 后续探索触发条件（不形成执行任务）

| 条件 | 可先做的最小离线反例 | 验收方式 | 不做什么 |
|---|---|---|---|
| 已有授权绑定链出现“单笔通过但多笔累计超限”的真实缺陷 | 两个并发授权各自合法、总和超限的合成输入 | 拒绝超额且保留原始请求、额度消耗与复核证据 | 不新建真实资金账户 |
| 工具权限边界成为待验证瓶颈 | 允许查询受限摘要，但拒绝越权读取/交易；读与写分别判定 | 强制工具端权限拦截、负例可重复 | 不接真实 MCP 凭据 |
| 用户撤销与在途执行竞态被实际发现 | 撤销前发起、撤销后执行/查询/重试的离线状态序列 | 执行前再核对当前授权，已受理状态按真实事实恢复 | 不将“停用”等于“退款成功” |
| 订单/商户/额度动态变化出现负例 | 授权旧金额/旧对象、实际付款新金额/新对象 | Binding 与 Confirmation Gate 拒绝不匹配，恢复不重复结算 | 不增加无证据的全场景矩阵 |

## 5. 吸收结论

- **ABSORB（方法）**：独立 Agent 资金/权限范围、交易级审批、读写权限区分、撤销与活动可追溯。
- **REFERENCE_ONLY（产品）**：Robinhood 的 MCP 产品、内建 Agent、用户规模、策略交易和产品商业模式。
- **REJECT（当前实现方向）**：直接连接生产证券/信用卡、自动真实交易、把证券收益或开户数当信任能力验证指标。
