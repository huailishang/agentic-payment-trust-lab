# 智能体支付实验项目中控

> 更新时间：2026-08-03

## 1. 一句话定位

本仓库不是生产支付系统，而是一个面向学习、实验和未来开发者验证的**智能体支付可信验证实验台**。公开展示名统一为 **Agentic Payment Trust Lab / 智能体支付可信实验室**：用协议中立模型、固定风险场景和外部挑战，验证智能体（Agent）代表用户下单、付款、履约、退款和恢复时，是否遵守委托、能否解释异常、能否留下可追溯证据。

项目能力不局限于信用卡，公开仓库名统一为 `agentic-payment-trust-lab`。项目不接真实卡、真实资金、生产商户、生产私钥、联机放行或清算网络。

## 2. 当前结构：一仓两域

唯一主仓库就是当前仓库根目录，仓库名为：

```text
agentic-payment-trust-lab
├── 支付域
│   ├── 委托 / 智能体意图
│   ├── 订单 / 支付请求
│   ├── AP2 / ACP 等适配器
│   ├── 允许（ALLOW） / 拒绝（DENY） / 需要确认（CONFIRMATION_REQUIRED） / 无法判定（INDETERMINATE）
│   ├── 支付执行 / 状态恢复
│   ├── 履约 / 退款 / 争议
│   └── 生命周期教学界面（UI）
│
└── 可信执行域
    ├── 规范化
    ├── 哈希 / 绑定
    ├── 后续签名 / 身份
    ├── 后续幂等 / 状态验证
    └── 后续审计 / 不变量
```

依赖方向只有：

```text
支付域
    -> 调用可信执行域
    -> 获得“对象是否一致、证据是否可信、是否存在重复或冲突”等确定性事实
    -> 支付域自己决定业务动作
```

可信执行域不得直接返回支付业务的 `ALLOW`、`DENY`、`CONFIRMATION_REQUIRED`、退款、争议或重试政策。

## 3. 当前已经做到哪里

### 支付域

当前代码已经覆盖 S01—S13：

- S01—S08：委托边界、预算、商户、品类、次数、过期、重复请求和人工确认。
- S09：订单价格、商品等变化与重新确认。
- S10：支付成功但履约失败。
- S11：退款、部分退款与争议，并区分争议结案和经济补救完成。
- S12：支付状态 `UNKNOWN` 时先查询原交易，再决定恢复动作，禁止盲目重复扣款。
- S13：声明 Agent 标识与委托中的预期标识不一致时拒绝，但不把“标识一致”宣称为真实身份认证。

S01—S13 固定场景已经形成可回放闭环。2026-07-27 已完成 TP-22 / S12 正式复评：S12 专项 9/9 PASS，TE02 改造前全量 104/104 PASS；S13 随后也已接入当前回归集。

正式界面（UI）已收敛为支付生命周期 L1—L9 的唯一主入口；可信执行学习沙盘只保留为历史教学原型，不再建设第二套正式界面（UI）。

### 可信执行域

当前真正落地的稳定能力仍很小：

```text
src/agentic_payment_experiment/trusted_execution/
├── __init__.py
├── hashing.py
├── binding.py
└── execution_facts.py
```

已有 TE01 哈希（Hash）、TE02 规范化、TE03 绑定与 TE04 执行事实能力。S09 已真实消费订单绑定事实；S12 已真实消费状态观察与幂等事实；S13 已让付款前委托验证消费“声明标识绑定事实”。P3 候选实现新增 `IdentityAssuranceLevel`、可回放的 Agent / executor 绑定事实和支付回调前身份闸门。最关键的边界仍保持：Binding `INVALID` 不自动等于 `DENY`，Idempotency `VALID` 不自动等于允许再次扣款，`BOUND` 也不等于真实身份已认证。

S13 已完成，但当前主线不再默认进入 S14。项目先从“继续堆场景”切换到**模块化实验与评测闭环**：先把现有逻辑做成可交互实验台，引入外部挑战和统一评分，再让外部失败结果反推 S14—S20 哪些真的值得开发。

2026-07-30 P1 Delegated Authority v1 已验收：`IntentMandate.authority_version`、`Order.authority_version_ref` 和 `ConfirmationRecord` 已进入主领域与场景加载；`verify_confirmation_binding()` 在执行前重新计算当前订单摘要，返回 `VALID / INVALID / MISSING_EVIDENCE` 与多字段失效原因；`validate_request()` 已消费该事实，缺证据时 fail-closed；`execute_with_confirmation_gate()` 只在 `VALID` 时调用支付回调。S08 继续验证确认阈值，S09 已使用保存的确认记录验证具体交易内容变化。它没有接真实支付，也没有把生产安全、身份认证或防篡改存储能力写进 P1。详见 [P1 执行记录](../04_验证体系/P1授权绑定与执行前核验执行记录_20260730.md)。

2026-07-30 P2 连续 Binding 到 Payment 已验收：`TransactionRequest` 已显式引用订单、授权版本与收款方，`PaymentExecutionRecord` 已显式引用授权、Agent 和交易对象；`verify_payment_execution_binding()` 同时核验两段引用、金额、币种、payee、执行标识和时序；`execute_with_payment_binding_gate()` 只有在上游 `ALLOW` 且 P2 为 `VALID` 时才调用支付回调。S10—S12 已真实消费 P1 + P2 连续证据，S12 原有 UNKNOWN / Idempotency 恢复语义保持不变。详见 [P2 执行记录](../04_验证体系/P2连续支付绑定执行记录_20260730.md)。

2026-07-31 P3 Agent / Executor Identity v1 已由独立评估者验收：`DECLARED / BOUND / VERIFIED` 是封闭保证等级；当前离线核验最多返回 `BOUND`，凭证引用本身不会升级为 `VERIFIED`。详见 [P3 执行者记录](../04_验证体系/P3_Agent_Executor_Identity_执行记录_20260731.md)。

2026-08-01 P4—P8-A 已完成独立评估：可信来源与上下文策略、证据回放、原交易绑定、支付最终性与状态冲突、按业务能力组织的 UI，以及 x402 离线一致性适配均已通过；当前全量测试基线为 `280 tests OK`。P8-A 只证明有限 x402 合成对象能够安全进入协议中立模型，不代表模拟购物环境、真实 x402 测试网、UCP / ACP 商务流程、真实签名或银行沙箱已经完成。

## 5. 当前最重要的判断

截至 2026-08-03，项目已经有一套可运行的“可信支付裁判”：规则实验台、P1—P6 Trust Control Plane、P7 能力导航、PayBench / AP2 / Attack Overlay，以及 P8-A x402 离线适配均已形成闭环。当前最主要的缺口不再是继续增加固定 JSON 案例，而是缺少一个让 Agent 自己产生商品、购物车、订单、支付和履约状态的完整环境。

```text
当前已有
规则 + 协议样品 + 可信控制 + 统一评测
        ↓
当前缺少
可重置、可检查的多步骤商务环境
        ↓
推荐下一步
P9 WebShop 外部商城接入
```

P8-B x402 测试网继续保留为可选分支，需要网络、钱包、签名和测试币的单独授权。P9 改为优先复用 Princeton WebShop：第一包只固定官方上游提交、核验文本环境和 `click[buy now]` 购买接点，不安装依赖或下载商品数据；后续再以独立环境运行 small 模式，并在外层接入 P1—P6 与 M5，不重新建设商品库和商城主体。

统一分层与环境方向见 [验证体系与后续环境统一路线](../02_未来规划/验证体系与后续环境统一路线_20260801.md)；WebShop 具体接入和分包见 [WebShop 外部商城接入分析与分批执行路线](../reference/04_商城与外部环境/WebShop外部商城接入分析与分批执行路线_20260801.md)。整体执行顺序仍以 [整体修正执行计划](../02_未来规划/整体修正执行计划_20260729.md) 为准。

## 6. 当前不做

- 不重新建立 `financial-agent-trusted-execution` 独立开发主线。
- 不建设第二套正式教学界面（UI）。
- 不一次性实现签名、区块链、智能合约、共识、审计全家桶。
- 不为了协议覆盖率同时接入 AP2、ACP、UCP、x402 的完整开发工具包（SDK）。
- 不接真实支付、真实卡、生产凭证、主网资产或生产放行规则。
- 不把 哈希/签名验证通过写成“业务合法”“支付安全”或“监管合规”。
