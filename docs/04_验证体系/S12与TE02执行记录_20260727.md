## 3. TE02 外部规范核对

本轮只做有范围的规范核对，不克隆、不安装、不接入外部实现，也不新增第三方运行依赖。

| 来源 | 版本 / 日期 | 本项目采用点 | 不直接采用点 |
|---|---|---|---|
| RFC 8785，JSON Canonicalization Scheme（JCS） | RFC 8785，2020 | 哈希前必须先形成稳定表示；对象属性需确定性排序；数组元素顺序不应被规范化器擅自改变 | 本项目不声明 JCS 兼容；Python `json` 的字符串/数字规则并非完整 JCS，实现还主动做 Unicode NFC，这与 JCS 的“字符串保持原样”不同 |
| Unicode Standard Annex #15 | Unicode 17.0.0，Revision 57，2025-07-30 | 采用 NFC，把规范等价文本收敛为同一二进制表示 | 不使用 NFKC/NFKD，避免兼容性归一化抹掉潜在业务差异 |
| Python `datetime` 文档 | Python 3.14.6 | 只接受带时区（aware）的 `datetime`；同一时刻统一转换为 UTC | 不接受 naive `datetime`，避免本地时区解释进入摘要 |
| Python `decimal` 文档 | Python 3.14.x | `Decimal` 用十进制精确语义，等价值去除无意义尾零 | 不直接调用受当前上下文舍入影响的 `normalize()` 作为哈希契约，而是按 `as_tuple()` 精确生成规范文本 |
| Python `dataclasses` 文档 | Python 3.14.6 | 数据类按字段名展开，支持真实 `Order` / `OrderItem` 等对象进入规范化 | 不把支付域类名写入摘要，避免可信执行域反向依赖支付模型 |

访问日期：2026-07-27。

许可证与运行要求：本轮没有把外部代码或开发工具包（SDK）引入仓库，仅参考公开标准与 Python 官方文档；因此没有新增许可证、凭证、网络运行或生产密钥要求。

当前消费者：TE02 直接面向下一阶段 S09 订单绑定；S12 暂不消费 TE02，后续由 TE04 接入执行身份、状态观察和幂等事实。

## 4. TE02 已冻结的规范化契约

新增：

```text
canonicalize(value) -> JSON 兼容的规范化值
canonical_json(value) -> 稳定字符串
canonical_hash(value) -> 摘要
verify_hash(expected_hash, value) -> bool
```

当前规则：

| 类型 / 问题 | 规则 |
|---|---|
| `Decimal` | 等价值去除无意义尾零；`100.00`、`100`、`1.0000E+2` 等价；以类型标签与普通字符串区分；拒绝 NaN/Infinity |
| `datetime` | 必须带时区；统一转 UTC；固定到微秒精度；同一时刻不同 UTC offset 等价 |
| `list` / `tuple` | 两者等价；元素顺序保留 |
| missing / `null` | 字段缺失与字段存在但值为 `None` 不等价 |
| Unicode | 字符串值和映射键统一 NFC；若两个键归一化后冲突则拒绝 |
| 映射键顺序 | 不进入摘要语义，稳定排序后序列化 |
| `items` 顺序 | TE02 不擅自解释支付业务语义，当前仍属于序列顺序，因此调换位置会改变摘要；若 S09 认定商品排列不属于业务变化，应在 TE03 的支付域投影中显式处理 |
| 版本字段 | 数据类字段默认全部进入摘要，因此 `order_version` 会改变摘要 |
| `float` | 拒绝，避免二进制浮点隐式进入金融对象摘要 |
| `set` / `frozenset` | 作为无序集合规范排序，并使用集合类型标签 |
| `$type` | 保留给规范化器内部类型标签；业务输入映射出现同名键时直接拒绝，避免与 `Decimal`、`datetime`、集合等规范化类型发生标签碰撞 |

## 5. TE02 测试

第一轮自查：可信执行哈希专项 18/18 PASS。

覆盖：

- 字典键顺序不影响摘要。
- 篡改值改变摘要。
- `Decimal` 等价表示一致。
- `Decimal` 与普通文本不混淆。
- 非有限 `Decimal` 拒绝。
- 同一时刻不同 timezone 表示一致。
- naive `datetime` 拒绝。
- `list` / `tuple` 等价但顺序保留。
- missing 与 `null` 区分。
- Unicode NFC 等价。
- Unicode 键归一化冲突拒绝。
- 业务映射使用保留键 `$type` 时拒绝。
- `float` 拒绝。
- 真实 `Order` 数据类可直接规范化。
- `order_version` 进入摘要。
- `Order.items` 当前顺序进入摘要。

第二轮自查：全量回归 118/118 PASS。

## 6. 当前边界与下一步

TE02 只证明：

> 受支持的 Python 业务对象能够稳定转换为本项目定义的规范化表示，并用于重复计算摘要。

它不证明：

- 对象在业务上合法。
- 支付应该允许或拒绝。
- 哈希等于身份验证或签名。
- 当前实现已经达到跨语言生产签名标准。

下一步进入 **TE03 绑定接口 + S09 首个跨域接入**：

```text
授权订单
    -> canonical_hash
    -> expected_digest

最终订单
    -> verify_binding(expected_digest, actual_object)
    -> VALID / INVALID / MISSING_EVIDENCE

S09 支付域
    -> 继续基于实际变化字段决定是否重新确认 / 拒绝 / 继续
```

TE03 必须重点处理一个边界：**哈希不同只代表规范化对象不同，绝不能自动映射为 `DENY`。**
