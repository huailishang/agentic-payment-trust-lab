# MoltsPay项目借鉴分析

## 1. 结论

MoltsPay与本项目不是同类替代关系。MoltsPay主要解决智能体如何发现付费服务、选择支付轨道、签名或付款、验证结算并取得服务结果；本项目主要解决付款前后的委托边界、订单变化、证据充分性、失败恢复和责任解释。

更合理的组合是：

```text
智能体提出购买
  -> 本项目的授权与证据判断
  -> 协议中立PaymentInstruction
  -> MoltsPay类执行适配器
  -> x402、链上、支付宝、微信或余额轨道
  -> PaymentReceipt归一化
  -> 本项目继续判断履约、退款和恢复
```

因此，MoltsPay当前只作为执行层实现样本，不作为核心依赖，也不改变“I2先完成中立订单和S09”的顺序。

## 2. 项目对比

| 维度 | MoltsPay | 本项目 | 判断 |
|---|---|---|---|
| 核心目标 | 将Skill/API变成可收费服务并完成付款 | 判断请求是否仍符合用户委托并生成证据 | 上下游互补 |
| 核心对象 | Service、Wallet、Rail、Facilitator、Payment Session | Mandate、Order、支付请求、Decision、证据 | 需要中立接口衔接 |
| 协议与轨道 | x402、MPP、EVM/Solana、支付宝、微信、托管余额 | 协议中立，当前仅有AP2教学适配器（Adapter） | 不追随其多轨覆盖面 |
| 决策 | 执行或报支付错误 | `ALLOW`、`DENY`、`CONFIRMATION_REQUIRED`、`INDETERMINATE` | MoltsPay不能替代授权判断 |
| 优势 | SDK/CLI/MCP、真实状态、恢复和开发者体验 | 授权边界、对抗样品、四态语义和字段证据 | 可用其执行状态补强S10—S12 |
| 主要风险 | 钱包、密钥、第三方Facilitator、托管余额和生产支付责任 | 尚未验证真实执行与异步生命周期 | 当前只抽固定样品和状态语义 |

## 3. 可吸收设计

### 3.1 支付会话与恢复

MoltsPay的微信轨道保存支付会话和外部订单号，支持轮询、中断后查询、继续履约和幂等返回。S12应吸收以下中立字段：

- `payment_session_id`
- `external_payment_ref`
- `idempotency_key`
- `payment_status`
- `last_verified_at`
- `fulfilment_status`
- `refund_ref`

这些字段只描述状态和证据，不携带真实凭证。

### 3.2 支付、履约和任务结果分离

余额轨道展示了“扣款、执行服务、失败退款”的工程顺序。项目应坚持：

```text
支付成功 != 履约成功 != 用户任务成功
```

S10不能只覆盖同步函数报错，还要覆盖已支付后超时、异步任务稍后失败、结果质量争议和退款未完成。

### 3.3 统一执行接口

未来可用以下协议中立对象隔离上层授权与下层轨道：

```text
PaymentInstruction -> PaymentChallenge -> PaymentProof -> PaymentReceipt
```

`PaymentInstruction`由本项目在授权判断后生成；适配器只能转换和执行，不能放宽Mandate或改写Order。

### 3.4 危险操作拆分

MoltsPay的MCP接口将状态查询、服务发现、限额配置和实际付款分开，并提供dry-run与确认门。未来工具接口也应拆成只读查询、预览、确认和执行四类，实际付款不能与服务发现合并成一个万能工具。

### 3.5 幂等与审计

除当前重复`request_id`判断外，S10—S12应分别验证请求、外部结算、履约和退款的幂等键，并保留状态转换证据。不能用一个ID推定所有阶段都已防重。

## 4. 不直接照搬的部分

- 单笔与单日限额不能替代商户、品类、收款方、订单版本、报价变化和委托范围判断。
- “一个JSON即可收费”解决接入便利，不解决谁授权、为何付款和谁承担争议责任。
- 自托管Facilitator不等于没有单点或审查风险；服务器、RPC、稳定币发行方、密钥和网络仍构成信任依赖。
- “支付后服务调用成功”不能证明异步履约完成，更不能证明服务质量符合用户目标。
- 余额轨道存在强认证可关闭、管理端点需要额外保护、部分充值路径依赖运营方信任等边界，不能作为生产安全基线。
- 多链、主网钱包、真实资金、密钥托管和Gas优化均超出当前实验授权。

## 5. 回写任务包

| 当前任务 | 吸收内容 | 明确不做 |
|---|---|---|
| TP-10 中立订单 | `service_id`、明确收款方、金额Decimal字符串、币种、报价有效期、候选轨道 | 不加入链地址和某条链专属字段 |
| TP-11 S09 | 比较授权订单快照与402最终挑战中的金额、币种、收款方和服务 | 不签名、不付款 |
| TP-12 适配器选择 | ACP/UCP仍按订单表达能力二选一；MoltsPay仅保留一个固定402执行样品 | 不安装开发工具包（SDK）或启动真实服务 |
| TP-20 S10 | 区分支付、履约、任务结果和补救状态 | 不把自动退款当作全部售后 |
| TP-21 S11 | 串联原支付、退款、部分退款和争议引用 | 不调用真实退款接口 |
| TP-22 S12 | 支付会话、外部引用、多阶段幂等、查询与恢复 | 不连接主网或生产网关 |
