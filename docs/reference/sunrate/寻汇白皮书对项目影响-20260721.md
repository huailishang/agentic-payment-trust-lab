# 《定义智能体驱动的全球支付》对项目影响分析

- 评估日期：2026-07-21
- 来源：寻汇 Sunrate × Mastercard 联合白皮书
- 原文：公开仓库不再分发 PDF；来源与 SHA-256 见 [`source/README.md`](source/README.md)，本地原件位于 Git 忽略目录 `local_sources/third_party/sunrate/`
- 资料级别：**C 级——企业联合白皮书 / 行业研究资料**
- 使用边界：可用于需求发现、场景设计、行业趋势判断和产品假设；**不得直接作为监管、协议、卡组织规则或生产支付控制依据**。

## 一、结论

这份白皮书对本项目的影响不是“推翻现有架构”，而是：

1. **进一步证明项目现在的“双域设计”方向是对的。**
   - 支付域负责业务流程、协议适配、订单、履约、退款和争议。
   - 可信执行域负责身份、意图、授权、预算、绑定关系、幂等、状态真实性和审计证据。

2. **给项目补充了一条更有商业价值的企业间业务（B2B）场景线。**
   当前项目以个人或零售支付实验为主；白皮书系统覆盖供应商引入、采购、应付账款、跨境支付、外汇、资金管理、对账、欺诈和争议等企业场景。

3. **强化“KYA / 意图 / 授权 / 证据链”能力优先级。**
   白皮书强调智能体可以编排支付，但必须在人的控制、明确政策和可审计链路中工作。这与项目的可信执行方向一致。

4. **当前开发主线不应因此被打断。**
   先完成既定的规范化（Canonicalization）、绑定接口、S09 / S12 等基础闭环，再将企业间业务（B2B）场景作为后续纵向场景包，而不是现在临时扩成“大而全的企业支付平台”。

## 二、白皮书内容与项目架构的映射

| 白皮书概念 | 本项目对应模块 | 项目应采用的更严格边界 |
|---|---|---|
| 人控自主 | 人工确认、允许（ALLOW） / 拒绝（DENY） / 需要确认（CONFIRMATION_REQUIRED） / 无法判定（INDETERMINATE） | 人始终可以设限、确认、撤销和接管 |
| KYA、身份与意图 | `trusted_execution` 的身份、意图、授权与策略判断 | 不能只信自然语言；必须绑定主体、用途、金额、对象、期限和证据 |
| 凭证保护 | 令牌化、最小权限、敏感字段隔离 | 智能体不能直接持有完整卡号、密钥或长期支付凭证 |
| 信任层 | 可信执行域 | 输出可验证事实，不替支付业务作最终业务决策 |
| 智能体体验层 | 支付域、场景编排和教学界面（UI） | 负责流程编排与解释，但不绕过规则执行器 |
| 专业化模型 / 多智能体 | 场景智能体（Agent）、协议适配器（Adapter）、检测与恢复组件 | 每个组件职责单一；禁止一个通用智能体（Agent）同时审批、执行、记账和自证 |
| 全球支付生态 | AP2 / ACP / UCP 等协议适配层及传统支付网络 | 协议适配与资金清算分层，不能把“智能体协议”误当成“资金结算网络” |

## 三、对支付生命周期 L1—L9 的具体补充

| 企业场景 | 建议映射环节 | 关键可信执行检查 |
|---|---|---|
| 供应商发现与准入 | L1—L3 | KYB、受益所有人、制裁名单、账户归属、准入审批 |
| 采购订单生成 | L2—L4 | 采购意图、预算、商品、供应商、数量和审批链绑定 |
| 发票与订单匹配 | L3—L5 | PO—发票—收货三单匹配，防止金额、币种和收款方漂移 |
| 支付方式与路径选择 | L4—L6 | 通道可用性、手续费、汇率、到账时效与政策约束 |
| 外汇与跨境支付 | L4—L7 | 报价有效期、币种、金额、目的地、合规资料和重复执行 |
| 资金管理与付款时点 | L3—L6 | 预算上限、账户余额、付款窗口和人工授权；预测结果只作建议 |
| 对账与异常定位 | L6—L9 | 请求、授权、清算、入账和银行流水的状态一致性 |
| 欺诈、退款和争议 | L4—L9 | 风险信号、证据完整性、退款去向、责任归属和恢复动作 |
| 支付服务商（PSP） / 银行接入 | 横跨 L1—L9 | 适配器字段映射、错误码语义、回调真实性、幂等与状态恢复 |

## 四、最值得吸收的三个产品信号

### 1. 企业支付更适合验证“可信执行”的价值

消费支付通常流程短、人工参与少；企业支付涉及采购、发票、审批、预算、外汇、收款账户和对账，任何字段漂移都可能造成真实损失。因此，可信执行模块在企业间业务（B2B）场景中更容易体现价值：

- 智能体是否理解了正确的业务意图；
- 执行对象是否仍是原供应商与原账户；
- 金额、币种、报价和订单是否仍有效；
- 是否具备完整审批和审计证据；
- 异常后能否安全停止、恢复或转人工。

### 2. 项目可从“支付演示”升级为“支付前验证实验室”

后续产品定位可以从“展示智能体如何支付”，逐步升级为：

> 在支付真正进入银行、卡组织或支付服务商（PSP）之前，对智能体的身份、意图、权限、交易绑定、状态一致性和恢复能力进行可重复验证。

这比直接建设支付通道更适合个人开发者，也更符合当前项目不接真实资金、不保存真实凭证的边界。

### 3. 多智能体不等于多个智能体都能付款

白皮书案例中的采购、合规、外汇、付款和对账可以分别由专用智能体协作，但项目应坚持：

- 分析智能体可以提出建议；
- 编排智能体可以组织步骤；
- 规则与验证组件给出确定性事实；
- 只有经过授权、绑定和状态检查后，执行组件才生成受控动作；
- 任何高风险或不确定状态都必须转人工确认。

## 五、建议新增的后续企业间业务（B2B）场景包

以下仅进入 backlog，不立即插入当前主线：

| 建议编号 | 场景 | 要验证的问题 |
|---|---|---|
| S21 | 供应商 KYB 信息冲突 | 名称、注册号、受益所有人或收款账户不一致时是否阻断 |
| S22 | 采购订单与发票不匹配 | 商品、数量、金额、币种或税额变化时是否要求重新确认 |
| S23 | 外汇报价过期 | 智能体是否会使用过期汇率或静默接受价格变化 |
| S24 | 支付路径被替换 | 支付服务商（PSP）、银行通道或收款账户变化后原授权是否仍被错误复用 |
| S25 | 重复发票 / 重复付款 | 重试、回调延迟和网络中断时是否发生双付 |
| S26 | 对账状态冲突 | 支付服务商（PSP）成功、银行未入账或回调缺失时是否错误宣布完成 |
| S27 | 争议证据不完整 | 订单、授权、履约、退款和通信证据缺失时是否错误自动结案 |

## 六、实施顺序

1. **保持当前主线不变**：先完成规范化、绑定接口、S09 / S12 的实现与验证。
2. **补一个企业间业务（B2B）字段模型草案**：供应商、采购订单、发票、报价、付款指令、通道、对账记录和证据引用。
3. **从 S21—S27 中只选一个场景做纵向闭环**：建议优先 S22“订单—发票—付款绑定”，它最能复用现有绑定和可信执行能力。
4. **闭环通过后再增加第二个场景**，避免一次把采购、资金、外汇、风控和对账全部铺开。

## 七、不应直接采纳的内容

- 白皮书中的市场规模、增长率和厂商能力属于行业研究或营销口径，需要独立核验。
- “智能体自主支付”不能被理解为模型可绕过人工授权、规则校验和支付网络要求。
- 供应商提供的 KYA 或信任层概念不能替代监管要求、卡组织规则或银行内部控制。
- 预测、推荐和风险评分不能直接成为资金划转的唯一依据。
- 本项目不因此接入真实银行卡、真实企业账户、生产密钥或真实资金。
