# 产品权威轨迹最小合同 v1

## 1. 核心结论

产品权威轨迹不是评测器事后拼装的 Replay，也不是重新执行一遍业务规则。它是产品在真实本地调用链中，把已经产生的 Authority、Order、Request、Action、Decision、Payment、Policy、Lineage 和 Result 事实按统一合同输出。

当前基线保持不变：

```text
product-observed authoritative trace = 0/12 VALID
GESR = 0/12
```

落地必须拆成两个阶段：

```text
阶段 A：测量适配（maintenance）
旧 runner → 支持读取和校验新 envelope
产品仍不产出 trace → 重新冻结 0/12 BEFORE 和新 runner hash

阶段 B：单一产品能力实验
同一阶段 A runner + 旧产品行为 → BEFORE
同一阶段 A runner + 仅 T10 产品 trace → AFTER
```

不得在同一 capability experiment 中同时修改 runner 和产品 trace 产出。

## 2. 来源边界

### 2.1 Product-observed

必须同时满足：

1. 轨迹由产品调用路径在返回 outcome 前生成；
2. outcome 直接暴露 `authoritative_trace`；
3. `source = PRODUCT_OBSERVED`；
4. 事件只引用本次调用中已经生成的不可变对象或事实；
5. runner 只读，不补事件、不改 ref、不重新判业务规则。

### 2.2 Evaluator replay

runner、测试或评估者根据 outcome 事后构造的 `ReplayEvent` 只能用于诊断：

```text
evaluator-synthesized replay ≠ product-observed trace
```

即使 replay 完整，也不能把产品轨迹状态从 `NOT_AVAILABLE` 改为 `VALID`。

## 3. Envelope 合同

```text
ProductAuthoritativeTrace
- schema_version: product-authoritative-trace/v1
- source: PRODUCT_OBSERVED
- profile: closed profile name
- trace_ref: stable technical ref
- completeness_status: VALID | INVALID | INDETERMINATE
- reason_codes: tuple[str, ...]
- events: tuple[ProductTraceEvent, ...]
```

`completeness_status` 由 trace validator 根据结构、顺序、角色、引用和 profile 规则计算。产品不得自行填绿色状态绕过校验。

## 4. Event 合同

```text
ProductTraceEvent
- sequence_no: int, from 1, continuous
- event_type: closed enum
- entity_type: closed enum
- entity_role: closed enum
- entity_ref: stable ref
- source_object_type: closed type name
- source_object_ref: stable ref
- relations: tuple[TraceRelation, ...]
- decision: closed Decision | null
- status: closed status string | null
- reason_codes: tuple[str, ...]
- native_occurred_at: ISO-8601 | null
```

排序以 `sequence_no` 为权威。只有源对象原生具有固定时间时，才填 `native_occurred_at`；不得调用 `now()` 给历史事实补时间。

### 4.1 Relation

```text
TraceRelation
- relation_type: closed enum
- target_entity_type
- target_entity_role
- target_ref
```

最小关系类型：

```text
BOUND_TO
DERIVED_FROM
VALIDATED_AGAINST
OBSERVED_BY
BLOCKED_BY
MEMBER_OF
PRODUCED_RESULT
```

## 5. 关闭的实体角色

至少冻结：

```text
AUTHORITY
AUTHORIZED_ORDER_SNAPSHOT
CURRENT_ORDER_SNAPSHOT
CURRENT_REQUEST
GOVERNED_ACTION
ACTION_BINDING_FACT
PREPAYMENT_VALIDATION
CONFIRMATION_BINDING_FACT
CURRENT_PAYMENT_CANDIDATE
HISTORICAL_SUCCEEDED_PAYMENT
KNOWN_PAYMENT_PREFLIGHT_FACT
RUNTIME_GATE_OBSERVATION
PAYMENT_EXECUTION_OUTCOME
CONTEXT_POLICY_FACT
FACT_LINEAGE_RESULT
FULFILMENT_OUTCOME
RECOVERY_OUTCOME
STATUS_CONFLICT_OUTCOME
FINAL_OUTCOME
```

一致性键从旧 replay 的“同类字段全链必须相同”改为：

```text
(entity_type, entity_role)
```

同一键的非空 `entity_ref` 必须一致；不同角色可以合法引用不同的同类实体。例如 T10 可以同时包含当前候选 Payment 和历史成功 Payment。

## 6. 稳定引用规则

### 6.1 有原生 ID

```text
<type>:<native-id>[:<version>]
```

示例：

```text
IntentMandate:mandate-1
Order:order-1:webshop-v1
TransactionRequest:request-1
GovernedPaymentAction:action-1
PaymentExecutionRecord:payment-1
```

### 6.2 无原生 ID 的不可变对象

```text
<type>:sha256(canonical-json({
  "projection_schema": "<object>-ref/v1",
  "value": <primitive projection>
}))
```

canonical JSON 固定为：

- UTF-8；
- object key 字典序；
- 无多余空格；
- primitive-only；
- Enum 转 `.value`；
- datetime 使用对象原生 ISO-8601，不生成当前时间；
- tuple 转 array；
- 禁止内存地址、随机值、文件路径和运行时当前时间。

### 6.3 指定对象投影

| 对象 | projection schema | 投影 |
|---|---|---|
| `RuntimeGateRecord` | `runtime-gate-record-ref/v1` | `to_dict()` |
| `GovernedActionBindingFact` | `governed-action-binding-fact-ref/v1` | `to_dict()` |
| `KnownPaymentAttemptPreflightFact` | `known-payment-preflight-fact-ref/v1` | `to_dict()` |
| `ValidationResult` | `validation-result-ref/v1` | decision、issues、evidence、rule_version、limitations、order_differences 的 primitive projection |
| 产品 outcome | `<outcome>-ref/v1` | outcome primitive projection，明确排除 `authoritative_trace` |

### 6.4 RESULT 循环引用处理

```text
outcome 包含 authoritative_trace
→ RESULT_RECORDED 需要引用 outcome
→ RESULT ref 只 hash outcome projection excluding authoritative_trace
```

轨迹永远不进入自己的 RESULT ref 输入，因此不存在循环 hash。

结构化样例：

`P9_PRODUCT_AUTHORITATIVE_TRACE_MINIMUM_CONTRACT_REPAIR_V1/evidence/EV-06-stable-ref-examples.json`

## 7. 事件 taxonomy

```text
AUTHORITY_RECORDED
ORDER_RECORDED
REQUEST_RECORDED
ACTION_RECORDED
PREPAYMENT_DECISION_RECORDED
ACTION_BINDING_DECISION_RECORDED
KNOWN_PAYMENT_PREFLIGHT_RECORDED
RUNTIME_DECISION_RECORDED
PAYMENT_OUTCOME_RECORDED
POLICY_DECISION_RECORDED
LINEAGE_DECISION_RECORDED
FULFILMENT_OUTCOME_RECORDED
RECOVERY_OUTCOME_RECORDED
STATUS_CONFLICT_RECORDED

```

每个 profile 只要求与该路径有关的事件，不要求所有路径都出现全部类型。

## 8. 决策解释规则

每个任务的最终 decision 至少由一个真实产品决策事件直接解释，不能只把中间 ALLOW 记为结构化事件，再靠 RESULT 文本解释最终 DENY 或 INDETERMINATE。

### 8.1 T05/T06

```text
PREPAYMENT_DECISION_RECORDED
source = ValidationResult
decision = ALLOW

ACTION_BINDING_DECISION_RECORDED
source = GovernedActionBindingFact
INVALID          → DENY
MISSING_EVIDENCE → INDETERMINATE
VALID            → 继续执行，不等于最终支付已允许
```

轨迹只记录既有 `GovernedActionBindingFact.status`，不得重新运行 binding。

## 9. 双订单快照规则

T02—T04 必须记录：

```text
ORDER_RECORDED
role = AUTHORIZED_ORDER_SNAPSHOT
ref = Order:<order_id>:webshop-v1

ORDER_RECORDED
role = CURRENT_ORDER_SNAPSHOT
ref = Order:<order_id>:<mutation-specific-v2>
```

两个快照分别与 `ValidationResult` 建立 `VALIDATED_AGAINST` 关系。

T04 的真实依据是：

- authorized/current Order；
- `ValidationResult`；
- `ValidationResult.evidence`；
- confirmation/order binding evidence。

T04 的 `order_differences` 为空，不得把不存在的 `OrderDifference` 写成 source object。

## 10. T10 双 Payment profile

T10 profile：`WEBSHOP_DUPLICATE_PREFLIGHT_BLOCK_V1`。

```text
ACTION_RECORDED
entity_role = CURRENT_PAYMENT_CANDIDATE
payment_ref = GovernedPaymentAction.payment_ref
payment_ref = execution_candidate.payment_id
request_ref = current request

PAYMENT_OUTCOME_RECORDED
entity_role = HISTORICAL_SUCCEEDED_PAYMENT
payment_ref ∈ KnownPaymentAttemptPreflightFact.related_attempt_refs
status = SUCCEEDED
request_ref = current request relation from preflight fact
```

允许两个 payment ref 不同。validator 只比较现有 action、execution、preflight fact 的 ref，不重新执行 payment binding。

结构化样例：

`P9_PRODUCT_AUTHORITATIVE_TRACE_MINIMUM_CONTRACT_REPAIR_V1/evidence/EV-06-t10-dual-payment.json`

## 11. Profile 一致性与失败关闭

`VALID` 必须同时满足：

1. `source = PRODUCT_OBSERVED`；
2. schema/profile 已知；
3. sequence 从 1 连续且无重复；
4. profile 必需事件完整；
5. 每个事件的 entity role 合法；
6. 同一 `(entity_type, entity_role)` ref 一致；
7. relation target 存在且 role/ref 一致；
8. final decision 有直接决策事件；
9. source object ref 可按冻结规则重算；
10. RESULT ref 不包含 trace 自身。

判定：

```text
缺事件、缺 ref、缺 profile 事实 → INDETERMINATE
矛盾 ref、错误顺序、错误 role、伪造来源 → INVALID
产品未暴露 authoritative_trace → NOT_AVAILABLE（runner 外层状态）
```

任何 `INVALID / INDETERMINATE / NOT_AVAILABLE` 都不得被 evaluator replay 补成 `VALID`。

## 12. 不复制业务规则

轨迹层只能：

- 序列化现有对象；
- 生成技术 ref；
- 校验结构、role、relation 和 profile 完整性；
- 核对事件值与既有 fact 输出一致。

轨迹层不得重新判断：

- 金额、币种、payee 是否授权；
- Agent / Executor 是否可信；
- Payment 是否允许执行；
- Context / Lineage 是否有效；
- 是否需要重试、退款或履约。

这些结论必须来自现有 `ValidationResult`、`GovernedActionBindingFact`、`RuntimeGateRecord`、`KnownPaymentAttemptPreflightFact`、Policy / Lineage / Recovery / Conflict outcome。

## 13. 阶段化落地

```text
设计修复（本任务）
→ 测量适配 maintenance
→ 评估者接受新 runner + 重新冻结 0/12 BEFORE
→ 条件解锁 T10 capability experiment
→ T10 NOT_AVAILABLE → VALID
→ 再决定是否扩展其他任务
```

本任务只修设计，不实现类型、validator、runner 或任何产品 outcome。
