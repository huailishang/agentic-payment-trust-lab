# Payment 跨项目联动边界

## 1. 项目自己的主线

`agentic-payment-trust-lab` 仍然是支付可信执行领域项目，当前第一瓶颈仍由 `docs/01_项目现状/PROJECT_BOTTLENECK_MAP.md` 决定。

核心链保持：

```text
用户授权
→ Governed Action（受治理动作）
→ Explicit Facts（显式事实）
→ Binding（绑定）/ Source Registry（来源注册）/ Fact Lineage（事实血缘）
→ Policy / Runtime Authorization Gate（策略 / 运行时授权门禁）
→ ALLOW / DENY / CONFIRMATION_REQUIRED / INDETERMINATE
→ Controlled Action Seam（受控执行缝）
→ Authoritative Trace / Replay（权威轨迹 / 回放）
```

## 2. 当前映射到 Platform 的一级能力槽位

机器可读清单见 `config/runtime-capability-profile.json`。当前只登记已经能对应到标准一级槽位的实现：

```text
HAR-G 策略门禁
→ payment.governance / runtime-authorization-gate

HAR-G 审批门禁
→ payment.approval / human-confirmation-gate

HAR-V 校验器
→ payment.validation / governed-action-validator

HAR-O 轨迹输出器
→ payment.trace / authoritative-trace

HAR-L 恢复器
→ payment.recovery / query-and-recovery
```

Payment Binding、Fact Lineage、Payment Finality、Merchant / Mandate 规则继续作为 Domain extension（领域扩展），当前不单独升格为 Platform 一级能力槽位。

## 3. 领域实现与未来 Contract（契约）观察

### 策略门禁

Payment 已经有最成熟的“副作用前判定”链，是 HAR-G Governance（治理）最有价值的验证场。

候选公共形状：

```text
action
+ facts
+ policy
+ actor / authority context
→ decision
→ reason codes
→ evidence refs
→ required next action
```

支付金额、商户、mandate（授权委托）、支付状态等领域规则继续留在 Payment。

### Trace Contract（轨迹契约）

Payment 已经形成 Product Authoritative Trace（产品权威轨迹）、Consumer（消费者）、Player（播放器）和 Journey Read Model（旅程只读模型）。

最值得跨项目比较的是：

```text
event identity
+ source identity
+ relation
+ timestamp
+ decision / result
+ evidence refs
```

这部分未来可和 FinDocQA 的 evidence lineage（证据血缘）、数仓 Agent 的 validation evidence（校验证据）比较。

### Fact Lineage Contract（事实血缘契约）

公共层只考虑“事实从哪里来、经过什么派生、能否回指来源”的结构，不抽支付对象模型。

## 3. 与其他项目的联动

| 联动项目 | 可比较能力 | 当前判断 |
|---|---|---|
| `FinDocQA` | Source identity（来源身份）、Evidence lineage（证据血缘）、fail-closed（失败关闭） | 可以共享“来源不可丢失”的验证思想，但不能共用支付 Gate |
| `data-warehouse-agent` | Rule / Validator（规则 / 校验器）、Finding（发现项）、Trace / Evidence（轨迹 / 证据） | **很可能形成第二消费者**。研发合规扫描同样需要“规则→判定→证据→结论” |
| `agent-runtime-platform` | Permission（权限）、Lifecycle（生命周期）、Trace hook（轨迹挂点）、Capability Registry（能力注册） | Payment 可作为 Governance Capability（治理能力）的首个强验证场 |

## 4. 可能形成公共 Contract 的两条线

### A. Decision / Finding 统一最小结构

Payment：

```text
Gate
→ decision + reason + evidence
```

数仓 Agent：

```text
Rule / Analyzer
→ finding + severity + evidence + verdict
```

两者未必共用同一个业务接口，但可以比较是否需要统一的：

```text
subject
+ rule / policy id
+ outcome
+ reason
+ evidence refs
+ source
+ timestamp
```

### B. Trace / Evidence Envelope（轨迹 / 证据信封）

Payment 的 Authoritative Trace 已经证明“来源分类不能扁平化”。这个原则可以反哺 FinDocQA 和数仓 Agent：不同来源证据必须保留 source class（来源类别）和 provenance（来源链）。

## 5. 当前不做

- 不把 Payment 的四态决策强行推广成所有 Validator 的统一状态机；
- 不把 Binding / Payment Finality 等领域模型搬进 Platform；
- 不因为 Trace 很成熟就立即抽独立 Trace 平台；
- 不影响当前 B-10 Journey UI 主线；
- 只有第二个项目真正出现同类数据结构和运行需求，才进入 Platform 公共 Capability。
