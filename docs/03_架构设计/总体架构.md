# 智能体支付可信验证实验台：总体架构

> 更新时间：2026-07-28

## 1. 项目定位

本项目不是支付通道、购物智能体（Agent）、企业付款平台，也不是区块链钱包。

它是一个面向学习、实验和未来开发者验证的**智能体支付可信验证实验台**，核心问题是：

> 当智能体代表个人或企业执行下单、付款、履约、退款、恢复等支付相关动作时，如何保证它只能在明确意图、有效授权、可控权限、正确交易对象和可追溯证据的边界内行动，并能够正确处理重复执行、状态不确定和异常恢复。

当前只使用模拟身份、模拟订单、固定协议样品和合成支付状态，不接真实卡、真实资金、生产商户、生产私钥、联机放行或清算网络。

## 2. 一个公共内核，多种场景

本项目不分别建设“个人智能体支付内核”和“企业智能体支付内核”。

个人支付和企业支付面对的底层问题高度相似：主体是谁、智能体是否获得授权、执行对象有没有变化、金额和收款方是否仍在边界内、是否重复执行、真实状态是什么、事后能否还原证据。

因此长期架构采用：

```text
一套智能体支付公共内核
        │
        ├── 个人场景包
        │   ├── 订票 / 购物
        │   ├── 订阅
        │   └── 退款 / 争议
        │
        ├── 企业场景包
        │   ├── 采购 / 发票
        │   ├── 跨境 / 外汇（FX）
        │   └── 付款 / 对账
        │
        └── 其他可验证场景
```

场景层可以不同，但不重复建设两套授权、绑定、幂等、状态真实性和证据能力。

## 3. 一仓两工程域，三类公共能力

为避免“一仓两域”和“三个公共核心域”两个说法互相混淆，统一定义如下。

### 3.1 一仓两工程域

公开展示名与仓库名统一为 **Agentic Payment Trust Lab / 智能体支付可信实验室**：

```text
agentic-payment-trust-lab
```

仓库内只有两个工程责任域：

```text
支付域
    │
    │ 单向调用
    ▼
可信执行域
```

### 支付域

负责支付业务语义：

- 用户委托与智能体行动意图；
- 订单、报价和支付请求；
- AP2 / ACP / UCP / x402 等协议适配器（Adapter）；
- `ALLOW / DENY / CONFIRMATION_REQUIRED / INDETERMINATE`；
- 支付执行状态、履约、退款、争议和异常恢复；
- L1—L9 生命周期教学界面（UI）。

### 可信执行域

负责通用确定性验证事实：

- 规范化（Canonicalization）；
- 哈希（Hash） / 绑定（Binding）；
- 后续身份（Identity） / 签名（Signature）；
- 幂等（Idempotency） / 执行身份；
- 状态观察（State Observation） / 状态验证；
- 证据 / 审计（Audit） / 不变量（Invariants）。

可信执行域不直接决定支付业务应该 `ALLOW`、`DENY`、重新确认、退款、争议或再次扣款。

### 3.2 三类公共能力

从产品和业务视角，公共内核包含三类能力：

```text
智能体支付公共内核
        │
        ├── 1. 支付生命周期
        │      L1—L9 / 状态 / 异常恢复
        │
        ├── 2. 可信执行
        │      意图 / 授权 / 策略
        │      绑定 / 幂等 / 状态真实性 / 证据
        │
        └── 3. 协议适配
               AP2 / ACP / UCP / x402
               支付服务商（PSP） / 银行 / 支付网络接口语义
```

这里的“三类能力”不是三个代码仓库，也不是三个平级工程包；工程实现仍遵循“一仓两域”。

## 4. 支付生命周期：L1—L9 统一业务主线

个人和企业场景都映射到同一条生命周期，不各自发明一套流程。

| 阶段 | 含义 | 典型问题 |
|---|---|---|
| L1 | 用户/主体授权 | 谁授权、授权什么、有效期和权限边界是什么 |
| L2 | 智能体决策与意图 | 智能体准备代表主体做什么 |
| L3 | 订单 / 报价 | 商品、供应商、金额、币种、报价是否变化 |
| L4 | 付款前检查 | 委托、订单、政策和支付请求是否一致 |
| L5 | 支付执行 | 请求是否唯一、是否可能重复执行 |
| L6 | 支付状态 | 成功、失败、处理中（PENDING）、未知（UNKNOWN）到底如何确认 |
| L7 | 履约 | 支付成功是否等于用户任务成功 |
| L8 | 补救 / 售后 | 退款、争议、冲正或其他补救如何关联原交易 |
| L9 | 归档 / 证据 | 是否能够回放、审计和追责 |

异常统一通过生命周期位置、异常类型、检测方、判断依据、处理方、恢复动作和证据进行表达。

## 5. 支付域当前实现

当前固定样品已经覆盖 S01—S13：

```text
S01—S08
委托边界 / 预算 / 商户 / 品类 / 次数 / 过期 / 重复请求 / 人工确认

S09
订单价格或商品变化与重新确认

S10
支付成功但履约失败

S11
退款、部分退款、争议与经济补救

S12
支付状态未知（UNKNOWN） / 处理中（PENDING）后查询原交易并防止盲目重复扣款

S13
声明 Agent 标识与委托预期标识不一致；只验证标识引用绑定，不宣称真实身份认证
```

当前正式教学界面（UI）以 **L1—L9 支付生命周期异常矩阵**为唯一主入口。

界面（UI）原则：

```text
先看：问题发生在哪个生命周期环节
再看：支付主线发生了什么、谁检测、谁处理
同时看：可信执行侧支能验证什么、不能决定什么
需要时：展开技术字段 / 协议映射 / 判断证据 / 原始 JSON
```

不恢复第二套可信执行域顶层正式界面（UI）。

## 6. 可信执行域当前实现

当前稳定落地仍保持最小、可消费的范围：

```text
src/agentic_payment_experiment/trusted_execution/
├── __init__.py
├── hashing.py
├── binding.py
└── execution_facts.py
```

已有：

- **TE01 Hash**：稳定摘要与摘要验证；
- **TE02 Canonicalization**：处理 `Decimal`、`datetime`、Unicode、容器和字段顺序等规范化语义；
- **TE03 Binding**：返回 `VALID / INVALID / MISSING_EVIDENCE` 等对象绑定事实，S09 已真实消费；
- **TE04 Execution Facts**：执行身份、状态观察与幂等边界事实，S12 已真实消费；
- S13 继续消费最小“声明标识绑定事实”，但不把标识引用一致宣称为真实身份认证。

最关键的工程边界保持不变：可信执行只返回事实，不把 `Binding INVALID` 自动变成 `DENY`，也不把 `Idempotency VALID` 自动变成“允许再次扣款”。

## 7. 协议适配层

AP2、ACP、UCP、x402 以及未来支付服务商（PSP）、银行或支付网络接口都属于适配或外部基础设施层。

统一原则：

> **协议适配器负责把外部表达映射到项目内部共同语义；协议本身不重新定义项目核心业务规则。**

不同协议最终都需要映射回项目内部的：

```text
意图
授权
订单
支付请求
绑定
执行
状态
证据
```

当前已使用 AP2 和 ACP 固定样品进行轻量映射验证；协议数量不是进展指标。只有一个新协议能够回答现有模型无法回答的问题时，才增加适配器。

### 7.1 两个新增验收维度：横向协议不变量 + 纵向商业闭环

2026-09-02 根据人民银行副行长陆磊关于智能体支付协议 / 技术标准竞争与兼容问题的公开讲话，以及 Apify 对 x402 按量计费的实际接入说明，当前架构**不新增顶层模块**，只补两个可测试的验收维度。

#### 横向：Cross-Protocol Invariance（跨协议判断不变量）

```text
同一业务事实
    ↓
AP2 / ACP / UCP / x402 / Future
    ↓
各自 Adapter
    ↓
Canonical Facts
    ↓
Shared Trust Control
    ↓
Decision + Reason + Evidence
```

目标不是实现行业级协议互联互通，而是验证：

- 等价授权不能因协议变化而扩大或缩小；
- 等价 Agent / Transaction / Amount / Payee 应映射为等价核心事实；
- 等价事实应得到等价 Trust Decision；
- 协议本身缺少表达能力时必须显式返回 unsupported / missing evidence，不能静默猜测；
- 原始协议字段与 Adapter 映射证据必须保留，便于解释差异来自协议、适配器还是业务规则。

#### 纵向：Commercial Closure（商业闭环）

机器资源支付除了“是否付款”之外，还必须验证：

```text
Task Budget / Authority
    ↓
Pricing Rule / Authorized Cap
    ↓
Usage Evidence
    ↓
Actual Charge
    ↓
Settlement / Finality
    ↓
Service Fulfillment
    ↓
Refund / Recovery
    ↓
Evidence / Replay
```

该维度复用现有 Transaction Object、Payment Execution、Fulfillment、Remediation 和 Evidence / Fact Lineage，不新增第 7 个领域对象。机器资源支付所需的 `pricing_unit / authorized_cap / usage_quantity / actual_charge / service_receipt_ref` 等字段，只有在后续 Contract、Checker 和 Evidence 实际消费时才进入代码。

两个维度都属于现有架构的**验收方式**，不改变“一仓两域”和 L1—L9 生命周期。

## 8. 两域边界

判断能力归属时只问两个问题。

```text
“接下来业务应该做什么？”
    -> 支付域

“这些对象、状态和证据是否一致、唯一、未被替换、可追溯？”
    -> 可信执行域
```

例如：

| 问题 | 责任域 |
|---|---|
| 订单涨价后是否要求重新确认 | 支付域 |
| 授权订单与最终订单是否仍绑定同一对象 | 可信执行域 |
| 未知（UNKNOWN）后等待、查询还是人工介入 | 支付域 |
| 查询结果是否可靠绑定原交易 | 可信执行域 |
| 是否允许发起退款或争议 | 支付域 |
| 后续动作是否正确引用原交易 | 可信执行域 |

详细接口边界见 [支付与可信执行模块边界](支付与可信执行模块边界.md)。

## 9. 下一阶段技术路线

TE01—TE04 与 S09 / S12 / S13 的首轮跨域消费已经完成。当前不再让支付域单纯增加场景，也不让可信执行域独立堆技术组件，而是进入“**外部失败反推最小能力**”阶段：

```text
内部 S01—S13 回归
    +
PayBench 外部挑战
    +
AP2 协议样品
    +
Attack Overlay
        ↓
M5 统一评测
        ↓
暴露真实能力缺口
        ↓
M3-C：先接 E1 提示注入挑战
        ↓
再补 D1 数据最小化 / 隐私披露事实模型
        ↓
再决定下一批场景或可信执行能力
```

每新增一个可信执行域能力，都必须至少由一个真实支付域场景或外部失败证明其必要性，并同时有负向测试。

具体执行顺序见 [后续任务包](../02_未来规划/后续任务包.md) 和 [模块化实验与评测路线](../02_未来规划/模块化实验与评测路线.md)。

## 10. 个人场景与企业场景

公共底层稳定后，可以通过不同场景包验证，而不是拆成两套产品内核。

| 公共能力 | 个人场景 | 企业场景 |
|---|---|---|
| 主体与智能体身份 | 是否代表本人 | 是否代表该企业/部门 |
| 意图 | 购买某张机票 | 支付某张采购发票 |
| 授权 | 最多支付 5000 元 | 某角色最多支付某预算额度 |
| 策略 | 商户、金额、时间限制 | 预算、供应商、审批链限制 |
| 绑定 | 航班/订单/商户/金额 | 采购订单（PO）/发票（Invoice）/供应商/账户 |
| 幂等 | 防止重复下单/扣款 | 防止重复发票付款 |
| 状态真实性 | 到底扣款成功没有 | 到底付款、到账、对账成功没有 |
| 证据 | 为什么智能体帮我付款 | 谁授权、依据什么规则、支付给谁 |

企业场景目前只作为后续场景线，不因为加入企业间业务（B2B）研究就把项目扩成采购、资金管理、跨境和对账全平台。

## 11. 开发者与创业假设

个人开发者不适合直接建设新的支付通道、清算网络、真实钱包或行业标准治理体系。

更现实的切入口仍是：

> 为准备接入智能体支付的开发团队提供协议适配、风险场景回放、支付前验证、状态恢复验证、证据审计和兼容性测试能力。

潜在使用者包括：

- 开发购物智能体、采购智能体或付费接口（API）智能体的团队；
- 准备支持 AP2、ACP、UCP 或 x402 的商户与平台开发者；
- 支付机构、银行、卡组织的创新、架构和风险研究团队；
- 需要在真实接入前验证委托、绑定、幂等、退款和审计设计的企业。

这个假设必须通过真实开发者试用和可运行样品验证，不能因为行业白皮书或协议热度默认市场成立。

## 12. 项目明确不做

当前阶段明确不做：

- 不接真实银行卡、真实企业账户或真实资金；
- 不保存生产私钥、助记词、真实卡号（PAN）/安全码（CVV）或真实客户身份；
- 不自建清算、结算网络或钱包基础设施；
- 不把哈希、签名、幂等或状态机验证通过写成“业务合法”“生产安全”或“监管合规”；
- 不让可信执行域反向定义支付域的业务政策；
- 不机械铺开 S14—S20，也不一次性建设一整套密码学/区块链组件；
- 不为了协议覆盖率完整接入 AP2、ACP、UCP、x402 全部开发工具包（SDK）；
- 不在出现第二个真实消费者前抽成公共开发工具包（SDK）、独立服务或第二仓库。
