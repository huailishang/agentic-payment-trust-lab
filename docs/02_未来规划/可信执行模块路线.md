# 可信执行域模块路线

> 更新时间：2026-07-28

## 1. 模块目标

可信执行域不负责回答“这笔支付业务应该怎么处理”，只负责提供可复用的确定性验证事实：

```text
对象是否稳定
对象是否被替换
身份和引用是否一致
同一金融动作是否可能重复执行
状态观察是否可信绑定原交易
状态迁移是否符合给定规则
审计记录是否被篡改
```

这些事实供支付域使用，但不能替代支付域的业务裁决。

## 2. 当前已有能力

当前已落地 TE01—TE04，并已由 S09 / S12 / S13 形成真实跨域消费：

```text
src/agentic_payment_experiment/trusted_execution/
├── __init__.py
├── hashing.py
├── binding.py
├── execution_facts.py
├── confirmation.py
└── payment_binding.py
```

已有：

- **TE01 Hash**：确定性摘要与摘要验证。
- **TE02 Canonicalization**：把 `Decimal`、带时区 `datetime`、tuple/list、dataclass、映射等转换为冻结的 JSON 兼容规范值。
- **TE03 Binding**：验证授权对象与实际对象是否仍绑定，S09 已消费该事实。
- **TE04 Execution Facts**：验证执行身份、状态观察与幂等边界，S12 已消费该事实。
- **P1 Confirmation Binding**：确认记录在付款前重新绑定当前授权版本与订单内容。
- **P2 Continuous Payment Binding**：验证 Order → Payment Request → Payment Execution 的连续引用、关键字段、执行标识与时序，S10—S12 已消费该事实。
- S13 使用最小声明标识绑定事实检查委托中的预期 Agent 引用，但明确不等同真实身份认证。

当前全量自动化回归为 `210 tests OK`。TE01—TE04、P1 Confirmation Binding 与 P2 Continuous Payment Binding 只证明确定性事实接口、连续绑定和现有消费者没有回归，不代表生产身份、签名、确认记录或支付记录防篡改、合规或真实支付安全已经成立。

## 3. 下一阶段路线

### TE02 规范化契约【已完成】

先定义“同一个业务对象”在进入哈希前如何稳定表示。

必须明确：

```text
`Decimal`
`datetime` / `timezone`
`list` 与 `tuple`
字段缺失（missing）与空值（null）
Unicode 规范化
映射键顺序
`items` 顺序
版本字段
```

目标是避免：

> 业务对象没有变化，却因为 Python 表示方式或序列化顺序不同产生不同摘要。

TE02 只解决规范化，不改变任何支付业务结果。

### TE03 绑定（Binding）【已完成】

在规范化（Canonicalization）稳定后提供最小绑定验证：

```text
预期摘要
+ 实际对象
-> 有效（VALID） / 无效（INVALID） / 证据缺失（MISSING_EVIDENCE）
```

首个消费者：S09 订单变化，已于 2026-07-27 完成真实接入。

当前 S09 已把 `authorized_order_digest`、`final_order_digest`、`order_binding_status`、`order_binding_reason` 作为可信执行证据，同时继续由支付域判断涨价、换商品、非关键字段变化分别应该继续、确认还是拒绝。具体见 [TE03 绑定与 S09 接入执行记录](../04_验证体系/TE03绑定与S09接入执行记录_20260727.md)。

### TE04 执行身份 / 状态观察 / 幂等（Idempotency）【已完成】

第二个消费者：S12 支付状态恢复。

逐步提供：

```text
verify_execution_identity()
validate_status_observation()
check_idempotency()
```

只验证请求（request）/ 支付（payment）/ 支付服务商引用（provider reference）/ 订单（order）/ 幂等（idempotency）之间的关系和重复风险。

2026-07-27 已完成 S12 接入：状态观察绑定由 TE04 返回结构化事实，FAILED 恢复分支由 TE04 整理幂等边界与同请求相关尝试；支付域继续决定等待、查询、安全重试候选或人工介入。具体见 [TE04 执行事实与 S12 接入执行记录](../04_验证体系/TE04执行事实与S12接入执行记录_20260727.md)。

**P3 最小 Agent / Executor Identity 是当前下一步，但不等于自动建设完整 TE05 签名体系。** P3 先冻结 `DECLARED / BOUND / VERIFIED` 等保证等级、证据缺失和 fail-closed 边界；只有明确场景证明密钥签名是最小必要能力时，才进入完整签名与凭证实现。

### TE05 签名（Signature） / 身份（Identity）

只有在出现明确的签署者、授权对象版本和密钥关系实验后才进入。

签名有效只能证明：

> 某个密钥对某段确定消息完成了可验证签署。

不能自动证明智能体（Agent）正确理解用户，也不能证明授权范围业务上合理。

### TE06 状态验证 / 审计（Audit） / 不变量（Invariants）

按具体支付问题逐项进入，不一次性铺开：

- 通用确定性状态迁移验证。
- 原交易与后续动作绑定。
- 链式审计事件与篡改检测。
- 数学和业务不变量。

只有已有场景需要这些能力时才实现。

## 5. 安全边界

本项目是 Control Plane 当前最严格的高风险 Security（安全）验证场，但只验证支付 / 交易场景已经出现的真实安全问题，不建设“网络安全全家桶”。当前已验证重点包括 Identity Binding / Identity Assurance（身份绑定 / 身份保证）、Authorization / Delegation（授权 / 委托）、Context / Tool Integrity（上下文 / 工具完整性）、Transaction Binding / Integrity（交易绑定 / 完整性）、Replay / Idempotency（重放 / 幂等）、Audit / Recovery（审计 / 恢复）。Strong Authentication（强认证）、Credential / Key Governance（凭据 / 密钥治理）和 Cryptographic Signature Verification（密码学签名验证）属于后续候选，当前不得表述为已覆盖。

- 默认本地离线和合成数据。
- 不保存生产私钥、助记词、真实卡凭证或客户身份。
- 不进行主网资产操作。
- 不把哈希、签名、状态机或审计验证通过表述为业务合法、生产安全或监管合规。
- Blockchain（区块链）只作为 Wallet / Key、Signature + Transaction Binding、Nonce / Replay Protection、Verifiable Transaction / Finality、跨主体 Audit / Settlement Evidence 等具体机制的外部参考或实验来源。
- 如果普通数据库审计日志、签名、幂等键或现有支付网络已经足以解决问题，默认不用链。
- 不因为区块链技术存在，就默认需要共享账本、Token、DeFi、共识、智能合约或全量上链。
