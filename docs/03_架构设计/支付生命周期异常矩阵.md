# 支付生命周期异常矩阵

## 1. 文档目的

本项目后续不再把 S01、S02、S03……理解为一组彼此独立的“支付流程”。

统一采用下面三个维度组织智能体支付异常：

```text
维度一：生命周期阶段（Stage）
回答：问题发生在哪里？

维度二：异常类型（Failure Type）
回答：这是什么性质的问题？

维度三：处理链——责任与恢复（Responsibility / Recovery）
回答：谁提供事实、谁检测、依据什么、谁处理、怎么恢复、留下什么证据？
```

S 系列只作为测试案例放入这个框架，用来验证同一套支付生命周期和异常处理机制在不同故障下是否工作。

本框架是本项目的协议中立实验模型，不等同于任何单一支付协议、卡组织规范、银行生产系统或监管分类标准。

---

## 2. 维度一：支付生命周期

当前统一采用九个阶段：

| 阶段 | 中文含义 | 核心问题 |
|---|---|---|
| L1 用户授权（Mandate） | 用户允许智能体（Agent）做什么 | 权限边界是什么 |
| L2 智能体决策 / 意图 | 智能体准备执行什么 | 智能体的计划是否符合用户目标 |
| L3 订单 / 报价（Order） | 买什么、向谁买、多少钱 | 订单对象是否稳定、可绑定 |
| L4 付款前检查（Pre-payment Validation） | 当前请求是否允许继续 | 是否越权、缺失、需要确认 |
| L5 支付发起 / 执行（Payment Execution） | 向支付能力发起执行 | 执行请求是否成功送达和处理 |
| L6 支付状态确认（Payment State） | 到底有没有支付成功 | 成功、失败、处理中还是未知 |
| L7 履约（Fulfillment） | 商品或服务是否交付 | 支付成功是否真正完成用户任务 |
| L8 补救 / 售后（Remediation） | 出问题后如何处理 | 重试、退款、争议、人工处理 |
| L9 任务结束 / 证据归档（Closure） | 交易最终如何结束 | 最终状态和责任证据是否完整 |

这九个阶段描述“事情发生在哪里”，不等于九个固定软件组件。同一个阶段可能由智能体、商户、支付服务商、银行、卡组织或其他基础设施共同参与。

---

## 3. 维度二：异常类型

当前统一采用八类异常：

| 类型 | 中文含义 | 典型问题 |
|---|---|---|
| F1 权限与规则异常 | 本来就不允许做 | 超预算、商户越权、品类越权、次数超限、授权过期、需要重新确认 |
| F2 身份与绑定异常 | 对象是不是同一个、关系是否可信 | 智能体身份不一致、收款方变化、订单与支付绑定错误 |
| F3 数据与完整性异常 | 数据是否缺失、变化或不一致 | 订单涨价、商品变化、币种变化、字段缺失、协议映射缺口 |
| F4 重复、并发与幂等异常 | 同一动作是否执行多次 | 重复请求、重复扣款、重复退款、并发执行 |
| F5 状态、时序与一致性异常 | 当前到底处于什么状态 | 未知（UNKNOWN）、处理中（PENDING）过久、回调延迟、乱序、两边状态冲突 |
| F6 执行与外部依赖异常 | 应执行的动作是否失败 | 支付失败、网络失败、银行不可用、商户接口失败、履约失败 |
| F7 安全、欺诈与合规异常 | 请求是否真实、安全、合规 | 冒用、签名异常、篡改、欺诈、敏感数据过度索取、合规检查失败 |
| F8 补救、退款与争议异常 | 出事后的处理本身是否异常 | 退款失败、部分退款错误、争议、冲正、拒付、人工处理失败 |

异常类型描述“问题是什么性质”，与发生阶段分离。

同一种异常可以出现在不同生命周期阶段。例如“身份与绑定异常”既可能发生在智能体决策阶段，也可能发生在订单、支付或履约阶段。

## 4. 维度三：处理链

每个异常案例都必须补齐下面六项处理信息：

| 字段 | 回答的问题 |
|---|---|
| 事实来源（Source） | 谁提供异常事实 |
| 检测组件（Detector） | 谁负责检测或判断 |
| 判断依据（Basis） | 根据什么数据、规则或状态判断 |
| 处理器 | 谁负责接手处理 |
| 恢复动作（Recovery） | 下一步怎么恢复、终止或升级 |
| 证据 | 需要留下什么证据 |

完整表达方式：

```text
阶段（Stage）
+ 失败类型（Failure Type）
+ 故障（Fault）
+ 事实来源（Source）
+ 检测组件（Detector）
+ 判断依据（Basis）
+ 处理组件（Handler）
+ 恢复动作（Recovery）
+ 证据
```

例如 S10：

```text
阶段（Stage）       = L7 履约
异常类型 = F6 执行与外部依赖异常
故障（Fault） = delivery_failed
事实来源（Source）      = 商户履约系统
检测组件（Detector）    = 生命周期管理器（Lifecycle Manager）
判断依据（Basis）       = fulfillment_status=失败（FAILED） + order_id 绑定一致
处理组件（Handler）     = 补救管理器（Remediation Manager）
恢复动作（Recovery） = 重新履约 / 退款 / 争议 / 人工处理
证据    = order_id + payment_id + receipt + fulfillment_id + failure_code
```

## 5. S01—S20 映射矩阵

S 系列是本矩阵的测试案例，不是主架构。

| S | 场景 | 生命周期 | 异常类型 | 主要检测者 | 主要处理方向 |
|---|---|---|---|---|---|
| S01 | 正常合规支付 | L4 付款前检查 | 基线对照，无异常 | 委托验证器（Mandate Validator） | 允许进入后续模拟 |
| S02 | 超预算 | L4 付款前检查 | F1 权限与规则 | 委托验证器（Mandate Validator） | 阻止，要求新授权 |
| S03 | 品类越权 | L4 付款前检查 | F1 权限与规则 | 委托验证器（Mandate Validator） | 阻止 |
| S04 | 委托过期 | L4 付款前检查 | F1 权限与规则 | 委托验证器（Mandate Validator） | 阻止，取得新委托 |
| S05 | 重复请求 / 重放 | L4-L5 检查至执行前 | F4 重复、并发与幂等 | 幂等 / 请求验证器（Request Validator） | 查询原结果，禁止直接重复执行 |
| S06 | 商户越权 | L4 付款前检查 | F1 权限与规则 | 委托验证器（Mandate Validator） | 阻止 |
| S07 | 超次数 | L4 付款前检查 | F1 权限与规则 | 委托验证器（Mandate Validator） | 阻止并核对累计次数 |
| S08 | 达到人工确认阈值 | L4 付款前检查 | F1 权限与规则 | 委托验证器（Mandate Validator） | 转用户确认 |
| S09 | 下单后价格或商品变化 | L3-L4 订单至付款前 | F3 数据与完整性 | 订单验证器（Order Validator） | 展示变化并重新确认；明确越权时阻止 |
| S10 | 支付成功但履约失败 | L7 履约 | F6 执行与外部依赖 | 生命周期管理器 | 进入补救流程 |
| S11 | 退款、部分退款或争议 | L8 补救 / 售后 | F8 补救、退款与争议 | 补救 / 争议管理器 | 关联原交易后退款、争议或人工处理 |
| S12 | 实时结算期间规则 / 服务故障 | L5-L6 支付执行与状态确认 | F5 状态、时序与一致性 + F6 执行异常 | 支付状态/恢复管理器 | 先查状态，再恢复，禁止盲目重扣 |
| S13 | 智能体身份与委托主体不一致 | L1-L2 授权与智能体决策 | F2 身份与绑定 + F7 安全 | 身份（Identity） / 委托验证器（Mandate Validator） | 阻止并核实身份链 |
| S14 | 商户别名或聚合商导致对象不一致 | L3-L5 订单至支付执行 | F2 身份与绑定 | 商户/收款方绑定验证器（Merchant/Payee Binding Validator） | 核实真实收款主体及映射 |
| S15 | 币种或汇率变化导致金额越界 | L3-L4 订单至付款前 | F3 数据与完整性 + F1 权限规则 | 订单/金额验证器（Order/Amount Validator） | 重新计算边界并按需确认或阻止 |
| S16 | 部分履约、拆单或多次扣款 | L5-L7 支付至履约 | F4 幂等 + F5 状态一致性 | 支付/生命周期管理器 | 校验累计金额、次数和订单绑定 |
| S17 | 用户撤销或缩小委托 | L1-L4 授权至付款前 | F1 权限与规则 + F5 时序一致性 | 委托状态验证器（Mandate State Validator） | 使后续请求失效，已执行部分单独处理 |
| S18 | 多智能体转委托或代理链 | L1-L2 授权与智能体决策 | F2 身份与绑定 + F7 安全 | 转委托/身份验证器（Delegation/Identity Validator） | 禁止未授权转授，保留委托链 |
| S19 | 支付请求索取过量个人信息 | L2-L4 智能体到付款前 | F7 安全、欺诈与合规 | 数据策略/隐私验证器（Data Policy/Privacy Validator） | 阻止或进入复核，执行数据最小化 |
| S20 | 网络超时、状态未知后重试 | L5-L6 支付执行与状态确认 | F5 状态、时序与一致性 + F4 幂等 | 支付状态/恢复管理器 | 先查询原状态，确认失败后才允许安全重试 |

注意：一个场景可以同时属于多个异常类型。矩阵的作用不是强行“一题一类”，而是确保每个问题都有稳定坐标。

## 6. 协议、支付组件和矩阵的关系

以后增加 AP2、ACP、UCP、x402、支付服务商接口（API）、银行接口或其他框架时，不重新设计异常体系，而是回答三件事：

```text
1. 它覆盖生命周期的哪些阶段？
2. 它提供哪些异常检测所需的数据或动作？
3. 它能否映射到项目的协议中立模型？
```

例如：

```text
AP2
-> 主要给授权、智能体意图、支付请求等阶段提供表达对象

ACP
-> 主要给结账（Checkout）、订单、履约、售后等阶段提供表达对象

支付服务商接口（API）
-> 主要给支付执行、支付状态、退款等阶段提供实际能力
```

协议主要负责“参与方如何表达和交换信息”，不自动等于异常检测器或异常处理器。

## 7. 界面（UI）中自定义字段到底有什么价值

### 7.1 当前问题

当前 `run_experiment.py` 打开的教学界面（UI）使用大量项目自己定义的协议中立字段，例如：

```text
mandate_id
max_amount
merchant
category
request_id
order_id
payment_id
fulfillment_status
```

如果这些字段只是为了页面好看而临时增加，那么用户的质疑成立：

> 今天可以增加一个字段，明天也可以再增加十个字段；如果没有外部协议或稳定规则约束，它们只是项目自己草拟的 JSON，没有强制意义。

### 7.2 字段真正有价值的条件

协议中立字段只有同时满足以下条件才有长期价值：

```text
稳定语义
+ 明确类型
+ 必填 / 可选规则
+ 版本管理
+ 适配器映射
+ 验证器 / 状态机实际消费
+ 测试场景验证
+ 证据链引用
```

例如 `order_id` 有价值，不是因为我们在 JSON 里写了这个字段，而是因为：

```text
ACP 适配器可以映射到它
支付记录需要绑定它
履约记录需要绑定它
生命周期管理器（Lifecycle Manager）会检查它
S10 测试会故意制造绑定错误验证它
```

这时它才成为一个“协议中立契约”。

### 7.3 界面（UI）的真正作用

因此界面（UI）不应该以“展示我们自己设计了哪些字段”为核心。

界面（UI）的长期价值应当是帮助学习者看懂：

```text
当前在哪个生命周期阶段
        ↓
这一阶段需要哪些中立语义
        ↓
当前数据来自哪个协议 / 商户 / 支付组件
        ↓
适配器如何映射为中立字段
        ↓
哪个验证器 / 管理器消费这些字段
        ↓
发现什么异常
        ↓
路由给谁处理
```

如果某个字段没有被适配器（Adapter）、验证器、生命周期或测试真正使用，就不应该因为“以后可能有用”而不断加入界面（UI）。

## 8. 对现有界面（UI）的下一步原则

下一轮界面（UI）改造不应继续堆字段，而应先对齐本矩阵。

固定展示：

```text
生命周期阶段（Stage）
异常类型（Failure Type）
当前故障（Fault）
事实来源（Source）
检测组件（Detector）
判断依据（Basis）
处理组件（Handler）
恢复动作（Recovery）
证据
```

中立字段只作为“判断依据”和“协议映射”的展开详情，不再作为页面主角。

对于没有真实协议绑定的字段，界面（UI）必须明确标记：

```text
来源：项目协议中立实验模型
状态：非某协议官方字段
用途：供统一验证器 / 生命周期 / 测试使用
```

对于已经通过适配器映射的字段，应同时显示：

```text
协议原字段
    ↓ 适配器
中立字段
    ↓ 验证器 / 管理器
决策或状态
```

这样界面（UI）才能回答“这个字段为什么存在”，而不是只展示一组可以无限扩张的自定义参数。

## 9. 后续改造顺序

建议按以下顺序推进：

```text
第一步
冻结本生命周期 × 异常类型 × 处理链框架

第二步
给 S01—S20 补齐标准元数据
阶段（Stage） / 失败类型（Failure Type） / 事实来源（Source） / 检测组件（Detector） / 判断依据（Basis） / 处理组件（Handler） / 恢复动作（Recovery） / 证据

第三步
将现有 run_experiment 教学界面（UI）对齐矩阵
让用户先看到生命周期和异常路由，再展开字段

第四步
继续 S11、S12 等新场景
新场景必须先落入矩阵，再决定是否需要新增模型字段或组件

第五步
新增协议或支付组件
只增加适配器和能力映射，不重新定义主框架
```

核心原则：

> 项目的长期资产不是 S 编号，也不是不断增加的自定义字段，而是稳定的支付生命周期、异常分类、责任恢复模型，以及能够被不同协议和组件映射、验证和回放的协议中立契约。
