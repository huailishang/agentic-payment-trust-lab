# APASS / KYA 智能体持续信任：项目影响分析

> 日期：2026-09-12  
> 定位：外部行业信号与架构校准材料。用于判断支付宝 APASS / KYA 对 `agentic-payment-trust-lab` 的战略影响，不作为生产接入证明，也不自动触发执行包。

## 1. 一句话结论

APASS 对本项目最大的意义，不是提供了一个新的支付通道，而是从真实产业侧进一步验证了本项目当前的核心判断：

> **智能体支付真正新增的难题不是“Agent 能不能把钱付出去”，而是“用户、商家和支付机构为什么敢让 Agent 代表主体持续执行高风险交易”。**

因此，本项目继续定位为 **高风险交易 / 智能体支付信任验证场**。当前主线 `B-15A Signed Instruction Verification（签署指令验证） / H-25` 不切换；APASS 主要影响 H-25 之后阶段 E 的能力展开和后续瓶颈排序。

## 2. 外部信号

支付宝 APASS 官方页面把能力归为四组：

```text
可信身份
→ 持续核身
→ 意图安全
→ 可信存证
```

并把交易治理放在完整生命周期中：

```text
交易前：身份 + 授权核验
→ 交易中：运行状态 + 意图 + 风险持续判断
→ 交易后：证据留存 + 审计 + 责任追溯
```

官方页面同时强调三层身份：静态身份、运行时身份、责任主体身份；凭证由颁发方签发、Agent 持有和出示、验证方校验并进行风险分级。

这意味着行业正在把传统一次性 `KYC / KYB` 向 `KYA（Know Your Agent，了解你的智能体）` 和 `Continuous Trust（持续信任）` 延伸：一次注册、一次绑定或一次授权都不足以证明后续每次 Agent 行为持续可信。

## 3. 与本项目现有能力的映射

| APASS 能力 | 本项目已有能力 | 当前判断 |
|---|---|---|
| 可信身份 | P3 Agent / Executor Identity、`DECLARED / BOUND / VERIFIED` 分层、当前 B-15 | 已有领域边界，但真实 `VERIFIED` 仍缺 credential / possession / signature 证据 |
| 持续核身 | Binding、Context Policy、Runtime Gate、Fact Lineage | 已有运行时治理骨架，但还没有完整的运行实例证明、凭证有效性 / 持有证明、撤销与动态信任状态 |
| 意图安全 | User Intent、Delegated Authority、Confirmation Policy、WebShop 行为与规格落地 | 已能检查大量显式授权边界，但“形式上有权限却偏离原任务”的 Intent Drift（意图偏离）尚未形成独立通用能力 |
| 可信存证 | Action Origin、Authoritative Trace、Consumer / Read Model / Player、Lifecycle / Recovery、Remediation | 当前最成熟的一组，已形成较强的可消费责任证据链 |

因此，APASS 没有暴露出一个完全陌生的新方向；它主要把我们已经分散验证过的 `Identity / Authority / Runtime Gate / Trace` 串成了一个更清楚的产业级“持续信任”叙事。

## 4. 对阶段 E 的结构性影响

当前全局六阶段仍保持：

```text
A. 评测与治理底座
→ B. 授权、绑定、来源、执行前治理
→ C. 支付生命周期、恢复、补救证据链
→ D. 责任归因与可消费审计链
→ E. 主体真实性 / 凭证 / 签署指令
→ F. 外部真实协议 / SDK / 网络接入
```

但阶段 E 后续应按“持续信任”理解，而不是只做一次验签：

```text
E1 Signed Instruction Verification（签署指令验证）
   指令 / Webhook / Mandate 的签署者和内容未被伪造或篡改
   当前：H-25

E2 Credential / Possession Verification（凭证 / 持有证明验证）
   当前 Agent / Executor 真正持有有效凭证或密钥控制证明

E3 Runtime Identity Continuity（运行时身份连续性）
   当前运行实例、环境、关键组件仍与被信任实例一致

E4 Continuous Authorization（持续授权）
   授权是否仍有效、是否被撤销 / 缩小 / 换主体，关键变化后是否需要重新确认

E5 Intent Continuity（意图连续性）
   当前动作即使形式上未超出金额 / 商户等 scope，也不能明显偏离用户原始任务目标
```

这五项是阶段 E 的内部分析视角，不新增五套平行架构，也不要求一次性全部实现。

## 5. 对当前 B-15 / H-25 的判断

### 不切换当前第一瓶颈

当前 `B-15A Signed Instruction Verification（签署指令验证）` 仍然优先，因为项目已经有直接、重复、可执行的证据：AP2 HP、AP2 HNP、ACP 三个入口都存在 `signature/authenticity not_verified` 表面；H-25 又已经冻结为第一个真实能力实验。

APASS 的出现反而提高了这一方向的外部合理性：真实产业方案同样把身份凭证、签名验签、来源校验作为“敢让 Agent 付”的基础能力。

### H-25 后才重新排序

H-25 完成后，再比较以下方向的 `expected project value（预期项目价值）`：

```text
AP2 second consumer
vs
B-15B Credential / Possession
vs
Continuous Trust 的最小运行时 / 撤销切片
vs
Intent Continuity 的可测量缺口
```

不因为一篇行业文章直接创建新执行包；必须继续遵守“真实瓶颈 + 重复消费者 / 失败 + 同基线可测量增益”的项目门禁。

## 6. 对领域模型的影响

### 不新增“APASS 对象”或“KYA 对象”

当前六个核心对象仍足够：

```text
User Intent
Delegated Authority
Agent Identity / Executor
Transaction Object
Payment Execution
Evidence / Replay Event
```

`Continuous Trust（持续信任）` 更适合作为这些对象之间的持续验证关系：

```text
User Intent
→ Delegated Authority 当前仍有效
→ Agent / Executor 当前仍可验证
→ Transaction Object 仍来自授权链
→ Runtime Gate 在每个关键副作用前重新取证和裁决
→ Payment Execution
→ Evidence / Replay 记录每次信任状态变化
```

只有未来某类 `Trust Credential / Runtime Attestation / Risk Signal` 出现独立生命周期、多个真实消费者和独立治理需求时，才考虑升级成新的领域对象。

## 7. 需要特别吸收的 Intent Safety（意图安全）

本项目现有授权检查大多擅长回答：

> “这个动作有没有超过明确权限？”

但 Agent 商业还需要回答：

> “这个动作虽然没有形式越权，是否仍然在完成用户原始任务？”

例如：用户允许“为制作演示文稿购买必要素材，预算不超过 3000 元”，Agent 购买 2000 元耳机。金额可能没有越界，但动作可能明显偏离任务目标。

未来若该缺口进入主线，应优先验证：

```text
User Intent
→ Delegated Authority
→ Current Task Context
→ Proposed Action
→ Intent Continuity / Drift Check
→ ALLOW / CONFIRMATION_REQUIRED / DENY
```

它不能简单由 LLM 自述“我认为符合意图”完成，必须有可复核的事实、规则、理由码和反例。

## 8. 明确不吸收的内容

本轮不因为 APASS：

- 接入生产支付宝、真实资金或生产密钥；
- 建设完整 PKI / DID / VC / 区块链体系；
- 新增一个 APASS Adapter 作为展示功能；
- 宣称项目兼容、符合或复现 APASS；
- 把厂商产品能力当成正式监管标准；
- 打断当前冻结的 H-25；
- 把 KYA 做成“大而全身份平台”。

## 9. 对项目总定位的更新性表述

后续可以用下面这句话解释本项目的长期价值：

> **本项目不是研究“AI 怎么付款”，而是用支付这个高风险场景验证 Agent Commerce Trust（智能体商业信任）：谁被授权、谁在执行、当前动作是否仍忠实于用户意图、是否允许产生副作用，以及全过程能否追溯和问责。**

支付通道、清算、退款、对账等成熟机制继续优先复用现实支付体系；本项目创新主线仍聚焦 Agent 进入交易链路后新增的信任问题。
