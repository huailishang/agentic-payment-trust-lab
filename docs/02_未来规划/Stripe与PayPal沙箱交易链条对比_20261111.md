# Stripe 与 PayPal 沙箱：交易链条比较补充

- 日期：2026-11-11；公开官方资料复核，未创建环境或执行 API/支付。
- 全局依据：地图 r110；A–D 本地关闭、E 受控本地闭合、F 当前；B-21 仍是外部可执行环境与治理/恢复接缝就绪。
- 本轮目标：区分完整交易链能力与低门槛接入，避免把上一轮最小付款恢复方案误当作平台能力上限。H67 及攻击扩展保持延期。

## 1. 判断

**PayPal 对“可登录买家账户 → 批准付款 → 商户收款”的双边角色体验更自然；Stripe 完整沙箱也能承载从商品明细、结账页到付款、查询、通知和退款的长流程，不是只模拟资金。**

上一轮 Stripe 排第一主要依据匿名入口的接入门槛，并非链条覆盖比 PayPal 更完整；所提付款对象最小试验也不代表 Stripe 的完整 Checkout（托管结账）能力。若将独立测试买家/商户账户的批准与收款作为下一轮主要观察对象，PayPal 更匹配，应优先核其实用资格；若主要验证商户结账、订单付款绑定及恢复，Stripe Checkout 同样适合。

这些是文档能力比较，不是任一沙箱在本项目中的运行成绩。尚未冻结平台选择，也不同时建设两套适配。

## 2. 按交易环节比较

| 环节 | Stripe 完整沙箱 + Checkout | PayPal Sandbox + Orders |
| --- | --- | --- |
| 商户上下文 | 商户测试环境及凭证 | Business 商户测试账户及凭证 |
| 买家 | 可用 Customer 记录关联测试支付方式；不要求建立可登录的买家钱包账户 | Personal 买家测试账户，可登录并批准付款 |
| 商品和订单映射 | 商品/价格/数量、Checkout Session、内部购物车或订单引用 | purchase_units（购买单元）、商品/金额、支付订单及商户引用 |
| 买家结账 | 托管支付页、测试支付方式、完成/取消返回 | PayPal 页面或弹窗，买家登录、批准/取消 |
| 批准与收款分离 | 支持适用支付方式的预授权和后续收款 | 支持授权/收款，买家批准与商户收款是不同步骤 |
| 查询恢复 | 查询结账会话及关联付款、收款状态 | 查询订单、授权、收款和退款状态 |
| 事件及售后 | 业务事件回调、退款；具体能力受方式和权限影响 | 业务事件回调、退款；具体能力受方式和权限影响 |
| 库存、完整商户订单、发货或资源交付 | 由商户系统承担；支付成功不等于履约 | 同样由商户系统承担，支付订单不等于完整商城 |

Stripe 官方[托管结账流程](https://docs.stripe.com/payments/checkout/how-checkout-works?payment-ui=stripe-hosted)明确从创建会话、跳转支付页到交易后事件的流程；[会话对象](https://docs.stripe.com/api/checkout/sessions/object)可关联内部购物车/客户引用、付款对象及状态。[测试环境说明](https://docs.stripe.com/testing-use-cases)允许创建测试商品和价格。字段存在不构成授权或订单绑定已验收的证明。

Stripe 的[授权后收款说明](https://docs.stripe.com/payments/place-a-hold-on-a-payment-method)明确支持通过 Checkout 配置手动收款；[退款接口说明](https://docs.stripe.com/refunds)提供付款后的退款路径。不能将平台一般能力外推为当前匿名密钥具有全部权限。

PayPal 官方[测试账户说明](https://developer.paypal.com/sandbox-testing/accounts)明确区分个人买家与商户，并提供各自测试登录信息。[标准结账集成](https://developer.paypal.com/studio/checkout/standard/integrate)从商户购物车数据创建订单，再处理买家批准及商户收款；[Orders API（支付订单接口）](https://developer.paypal.com/api/orders/v2)和[Payments API（支付接口）](https://developer.paypal.com/api/payments/v2)列出订单、授权、收款和退款查询能力。典型双账户体验更明确，不代表两个真实独立主体或真实身份已被验证。

## 3. 两个平台都不会替我们提供完整商城

下单应拆成：商户系统的业务订单，以及支付平台的结账/支付订单对象。PayPal 对象名叫 Order，不意味着它承担商品搜索、库存预留、商户订单事务或商品交付；Stripe 的 Checkout Session 同样不是完整商户订单。

对本项目合适的链是：

```text
现有商户订单/数字资源与用户授权
→ 本仓执行前治理
→ Stripe Checkout 或 PayPal Orders
→ 买家完成/批准
→ 查询实际付款/收款状态
→ 商户订单状态更新与交付
→ 恢复、防重与审计
```

这里复用已有商户和支付生命周期，不建设第二个商城。外部事实负责证明付款平台状态；商户订单与交付分别留证。两种沙箱都不移动真实资金，也都不能把登录/支付成功替代本仓的委托授权。

Stripe [履约指南](https://docs.stripe.com/checkout/fulfillment?ui=full-page)要求商户自己执行交付，并指出返回成功页可能丢失、交付函数可能重复或并发调用。平台回调或跳转不自动完成可靠履约。

## 4. 匿名入口与完整平台能力必须分开

本项目已核实 Stripe 有匿名创建入口和发布实现；尚未实际验证该临时密钥能否创建所需 Checkout、使用特定付款方式、完成事件与退款等全部链路。[官方 CLI 文档](https://docs.stripe.com/cli#sandbox)的七天临时环境不是长期账户方案。不能基于一般沙箱文档声称当前匿名环境全部运行就绪。

PayPal 的一般沙箱功能有明确依据，但本项目开发者入口、买卖测试账户、应用权限和本机流程同样未验证。不能因为文档有双账户就直接判定接入成本更低。

## 5. 对下一步的影响

- 若以买家/商户账户、买家批准到收款的交互链为主要目标：优先核验 PayPal 的账户及应用资格；Stripe Checkout 作对照候选。
- 若以较低门槛验证外部结账、绑定和响应丢失恢复为主要目标：保留 Stripe 候选，但使用 Checkout 层设计长流程，不把纯付款 API 小试验宣称为完整购物链。
- 若采用更长链条，须在现有 DRAFT_CONTRACT（合同草案）内重新明确订单、浏览器交互、回调/查询和预算；不能沿用原60分钟/20请求的小切片上限而默默扩范围。

本轮未改变地图 revision、平台权限或任务状态；候选排序的适用目标已澄清，没有产品成熟度变化。只有实际获得授权并验证环境，才能形成运行结果。H67不重启，也不因比较增加攻击案例。
