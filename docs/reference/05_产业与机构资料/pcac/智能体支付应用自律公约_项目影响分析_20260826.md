# 《智能体支付应用自律公约》对项目影响分析（修订版，2026-08-26）

## 1. 文档定位

2026 年 8 月 24 日，中国支付清算协会印发《智能体支付应用自律公约》（以下简称《公约》），共八章 34 条。

本文的用途不是把《公约》简单转成“合规功能清单”，也不是因为出现行业规则就把项目收窄成单一产品形态，而是把它作为 `agentic-payment-trust-lab` 的一条重要外部验收基线：

```text
公开行业要求
  -> 项目适用性判断
  -> 架构能力映射
  -> 测试 / Evidence（证据）
  -> 缺口
  -> 后续执行包优先级
```

需要特别说明两点：

1. 《公约》属于行业自律文件，不等同于新的行政许可法规；正式业务仍应以适用法律法规、监管规则和机构合规意见为准。
2. APOP 此前已经进入本项目研究材料，银联资料也已有独立参考目录；本次不把国内协议方向包装成“新发现”。对 ACT，当前仓库与 Git 历史中未检索到此前独立落盘的专门资料，因此这里只把它作为外部协议参考保留，不宣称项目此前已经完成 ACT 专项沉淀。

---

## 2. 对项目定位的修正

此前表述“项目不应做自己经营智能体支付，而应收敛到 Agent Payment Trust Infrastructure（智能体支付信任基础设施）”过于绝对，需要改成：

> **当前项目的研发主轴应放在智能体支付新增的信任、授权、控制、证据和验证层；不把账户管理、资金托管、收单、清结算等持牌支付核心环节作为当前个人创业切入点。**

这和“项目未来只能做 Trust Infrastructure（信任基础设施）”不是一回事。

更准确的边界是：

```text
当前主轴
  KYA / Identity
  Authorization
  Binding
  Policy
  Governed Action
  Evidence / Trace / Replay
  Security / Compliance Evaluation

继续保留研究接口
  AP2 / ACP / UCP / x402
  APOP / ACT
  Commerce Adapter
  Payment Orchestration
  Agent Commerce

暂不把自己当作业务主体建设
  支付账户
  客户资金托管
  收单经营
  清结算网络
  生产级支付牌照能力
```

也就是说，**Trust Control Plane（信任控制面）是当前最适合验证的技术主轴，不应被写成项目永久、唯一的商业定位。**

---

## 3. 《公约》真正给项目带来的变化

《公约》的价值不只是增加一个 KYA 概念，而是第一次较完整地把智能体进入支付链路以后需要面对的对象串在一起：

```text
Agent 身份
  -> Agent 风险分级
  -> Agent 与用户对应关系
  -> 全链路身份传递
  -> 外部 Agent / Provider 管理
  -> 用户授权
  -> 支付意愿核验
  -> 授权执行与撤销
  -> 资金限额
  -> 可信存证
  -> 模型风险
  -> 注入攻击 / 指令篡改 / 越权交互
  -> 数据最小化与全生命周期保护
  -> 三反 / 反诈
  -> 跨 Agent 与大额交易
  -> 上线前评估
  -> 监控 / 应急 / 回退
  -> 投诉 / 查询 / 一键关闭
  -> 用户可理解展示
```

因此，后续不能只问：

> “KYA 有没有做？”

而要问：

> **“从 Agent 接入，到用户授权，到支付执行，到事后争议，这条链有没有可验证的控制和证据？”**

## 4. 与项目现有能力的关系

项目现有主线没有走偏：

```text
Protocol / Commerce Adapter
  -> Canonical Facts
  -> Identity / Trust Source
  -> Authorization
  -> Binding
  -> State / Finality
  -> Policy
  -> Governed Action
  -> Authoritative Trace
  -> Fact Lineage
  -> Replay / Evaluator
```

现有强项主要集中在：

- Authorization Binding（授权绑定）
- Payment Request / Order Binding（支付请求 / 订单绑定）
- Agent / Executor Identity（智能体 / 执行者身份）
- Request Identity（请求身份）
- Hash / Signature（哈希 / 签名）
- Idempotency（幂等）
- UNKNOWN Payment Recovery（未知支付状态恢复）
- Context Rewrite Defense（上下文改写防护）
- Prompt Injection（提示注入）攻击实验
- Payment Fact Lineage（支付事实血缘）
- Authoritative Trace（权威轨迹）
- Replay（回放）
- Evaluator / Regression（评测 / 回归）

这些能力与《公约》第 9—21 条、第 25—28 条形成明显交集。

但不能因此说“项目已经覆盖《公约》”。大量要求目前仍只有局部机制，或者根本属于机构级治理范围。

---

## 5. 完整缺口：不止 KYA、撤销和合规评测

下面将缺口分为 12 个能力族。后续开发应以“能力族 + 条款 + Evidence（证据）”为单位，不再按零散 Case 推进。

### G1. KYA 与 Agent 生命周期

需要补的不只是一个 `agent_id`，而是：

- Agent 身份识别与验证；
- Developer / Provider（开发者 / 服务提供者）来源；
- 模型来源与版本；
- Runtime Identity（运行时身份）；
- Agent 风险等级；
- 权限边界；
- API / Tool 调用范围；
- Agent 与用户对应关系；
- Agent 生命周期状态；
- Agent 信息在支付链路上的传递。

候选对象：

```text
KYAProfile
AgentIdentityAssertion
AgentRiskTier
AgentUserBinding
AgentLifecycleStatus
```

对应《公约》第 9—12 条。

### G2. 外部 Agent / Provider 风险与来源追溯

现有 `Trust Source` 还不足以覆盖：

- 外部 Agent 开发者是谁；
- 服务提供者是谁；
- 哪个模型 / Runtime 产生了动作；
- 合作方发生变化后是否重新评估；
- 是否存在未登记、未授权或来源不明 Agent；
- Provider / Developer / Model / Runtime 之间的 Provenance（来源追溯）。

这类能力不等于项目自己做供应商尽调系统，但至少要能承载相关事实，并在验证时拒绝“来源未知仍继续支付”。

对应第 10—12 条。

### G3. Delegated Authorization（委托授权）完整生命周期

现有 Mandate / Authorization Binding 应继续向完整授权合同演进：

```text
CREATE
  -> CONFIRM
  -> ACTIVE
  -> SUSPENDED
  -> REVOKED
  -> EXPIRED
```

授权至少应表达：

- 交易限额；
- 扣款账户；
- 账户优先级；
- 有效期；
- 允许动作；
- 数据访问权；
- API 调用权；
- 商户 / 品类 / 商品范围；
- 次数；
- 高风险二次确认规则；
- 版本；
- 撤销状态。

对应第 13—16 条。

### G4. User Intent / Payment Intent Verification（用户意愿核验）

项目现在更强的是“对象绑定正确”，但还需要区分：

```text
授权存在
!= 当前交易意愿仍然成立
!= 当前交易不需要再次确认
```

需要补：

- 用户真实意思表示与结构化授权的对应；
- 高风险场景二次确认；
- Order / Amount / Merchant 等关键变化后是否要求重新确认；
- Human-Not-Present（用户不实时在场）与 Human-Present（用户实时在场）的确认策略；
- 可证明“为什么这次没问用户”。

对应第 14—15 条。

### G5. Funds Safety / Transaction Guardrail（资金安全与交易护栏）

不能只有 `amount_limit`。

至少要覆盖：

- 单笔限额；
- 累计限额；
- 次数；
- 时间窗口；
- 账户选择；
- 账户优先级；
- 商户 / 品类；
- 大额交易；
- 重复执行；
- 跨 Agent 调用；
- 组合动作导致的隐性超额；
- 撤销竞态。

对应第 17、25 条。

### G6. Evidence Chain（关键节点证据链）

现有 Payment Fact Lineage 是项目最值得继续强化的主线。

《公约》要求关注的关键过程至少包括：

```text
User Authorization
Model Decision
Payment Instruction
Risk Control
```

项目应进一步保证：

- 每个关键事件来源明确；
- 父子关系明确；
- 可验证；
- 可追溯；
- 关键内容不可静默篡改；
- 争议时可回放；
- 模型输出和最终支付动作能够关联；
- Policy Decision（策略决策）有理由、有输入、有版本。

对应第 18 条。

### G7. Model Risk Governance（模型风险治理）

这是昨天缺口清单里明显遗漏的一大块。

需要建立“模型风险不是 Prompt Injection 的同义词”的认识，至少覆盖：

- Robustness（稳健性）；
- Transparency（透明性）；
- Traceability（可追溯性）；
- Output Reliability（输出可靠性）；
- Hallucination（幻觉）；
- 黑箱风险；
- 模型 / Prompt / Policy 版本；
- 模型决策与确定性支付规则的边界；
- 高风险支付不得只凭无法解释的模型结论直接执行。

对应第 19 条。

### G8. Model / Instruction Security + Continuous Monitoring（模型/指令安全与持续监测）

现有 Attack Overlay 主要是离线攻击验证，还需要补运行时控制视角：

- Prompt Injection（提示注入）；
- 交易指令篡改；
- 越权交互；
- Tool / API 越权；
- 可疑交易；
- 异常指令执行；
- Runtime Alert（运行时告警）；
- Continuous Monitoring（持续监测）；
- 风险事件处置；
- 监测结果进入 Evidence / Trace。

对应第 20 条。

### G9. Data Minimization / Privacy（数据最小化与隐私）

这是另一个不能只靠支付 Binding 解决的缺口。

至少需要形成数据事实和检查接口：

- 收集是否最小必要；
- Agent 是否读取了超出授权的数据；
- 数据从哪里来；
- 传给了谁；
- 是否跨 Provider；
- 保存多久；
- 是否允许重放时展示敏感原文；
- Evidence 保存和隐私最小化之间如何平衡；
- 日志 / Trace 脱敏。

对应第 21 条。

### G10. AML / CFT / Anti-Fraud / Anti-Gambling Policy Hook（三反与反诈策略接口）

项目不需要自己建设银行级 AML / 反诈平台，但要明确 Runtime 不能绕过这些外部风险系统。

架构应支持：

```text
Agent Payment Decision
  -> Trust / Authorization Gate
  -> Institution Risk / AML / Fraud Gate
  -> Payment Action
```

后续至少验证：

- 风险系统返回拒绝时 Agent 不能绕过；
- Agent 不能通过拆单规避规则；
- 风险状态和最终动作进入 Evidence；
- 需要人工处理时不重复支付。

对应第 23 条。

### G11. Incident / Rollback / Recovery（应急、回退与恢复）

项目已有 UNKNOWN Recovery，但“支付状态恢复”不等于完整应急机制。

还需补：

- Emergency Stop（紧急停止）；
- Agent Disable（一键关闭）；
- Authorization Revocation（授权撤销）；
- Runtime Kill Switch（运行时停止开关）；
- 大规模异常时停止自主支付；
- 安全降级到 Human Confirmation；
- 回退到人工 / 非 Agent 支付；
- 事件证据冻结；
- 恢复后如何防止重复执行。

对应第 24、26、28 条。

### G12. Consumer Protection / Explainability / Dispute（消费者保护、解释和争议）

实验 UI 后续不能只展示“PASS / FAIL”。

应验证用户至少能看懂：

- Agent 做了什么；
- 用了什么授权；
- 为什么执行 / 为什么拦截；
- 任务最终结果；
- 如何查询；
- 如何撤销；
- 如何关闭；
- 如何投诉 / 争议；
- 特殊人群是否有更严格权限和提示。

对应第 27—30 条。

## 6. 哪些要求不应该误做成项目代码

《公约》有一部分属于机构级责任，不应看到条款就写一个同名模块。

### 机构级 / 组织级要求

例如：

- 支付牌照与主体责任；
- 合作方正式尽职调查；
- 科技伦理正式审查；
- AML / CFT 制度建设；
- 舆情监测组织机制；
- 投诉责任部门；
- 消费者教育；
- 特殊人群运营服务；
- 向协会正式报备。

项目更合理的角色是：

```text
提供技术事实
提供验证 Evidence
提供可执行 Test
提供能力接口
提供 Requirement Mapping
```

而不是声称：

```text
“项目已经完成监管合规”
```

## 7. APOP / ACT 的处理方式修正

APOP 此前已经在项目研究材料中出现，银联资料也已有独立参考目录，因此不再使用“新增 APOP 国内一等参考”这种表述。ACT 在当前仓库与 Git 历史中没有检索到此前独立落盘的专项资料，所以这里不虚构既有沉淀，只把它保留为可继续核验的外部协议参考。

正确表述改成：

> **继续把已有 AP2、ACP、UCP、x402、APOP 等协议 / 产业资料作为对照；ACT 可作为后续外部协议参考补充。《公约》新增的是国内行业治理基线，用于检查这些协议对象映射到项目内部以后，身份、授权、执行和证据链是否满足现实支付治理要求。**

三者关系可以理解为：

```text
AP2 / ACP / UCP / x402 / APOP / ACT
  = 外部协议 / 商业协作参考

《智能体支付应用自律公约》
  = 国内行业治理与验收参考

agentic-payment-trust-lab
  = 协议中立 Facts + Trust / Policy / Evidence / Evaluation
```

不能把协议支持数本身当作项目成熟度。

## 8. 将《公约》变成后续开发的重要指标

建议建立一套 `PCAC-AGENTPAY` Requirement Profile（要求画像），但不把 34 条机械地全部转成代码任务。

### 8.1 每条要求先做适用性分类

```text
CORE
  项目应直接具备并验证的核心能力

ADAPTER
  项目应承载事实 / 接口，但能力主要来自外部机构或系统

EVIDENCE_ONLY
  项目不执行该职责，但应能够保留证据

REFERENCE_ONLY
  组织、法律、运营要求，仅作为设计审查参考

OUT_OF_SCOPE
  明确不属于实验项目建设范围
```

### 8.2 每个适用要求记录成熟度

```text
M0 MISSING
  没有对象 / 没有设计

M1 MODELLED
  已有领域对象或合同

M2 IMPLEMENTED
  已有实现

M3 TESTED
  已有确定性测试

M4 EVIDENCED
  端到端可以产生 Evidence / Trace

M5 REGRESSION_GATED
  已进入持续回归和变更门禁
```

### 8.3 项目级关键指标

建议后续在中控中至少跟踪：

| 指标 | 含义 |
|---|---|
| `applicable_requirement_count` | 与项目真正相关的要求数 |
| `modelled_requirement_rate` | 已形成领域模型 / 合同的比例 |
| `tested_requirement_rate` | 有确定性测试的比例 |
| `evidenced_requirement_rate` | 端到端能产出证据的比例 |
| `regression_gated_rate` | 已进入持续回归门禁的比例 |
| `critical_gap_count` | 高风险且仍缺失的要求数量 |
| `cross_agent_gap_count` | 跨 Agent 调用相关未覆盖数量 |
| `revocation_recovery_gap_count` | 撤销、关闭、应急、恢复缺口数量 |
| `model_risk_gap_count` | 模型风险治理缺口数量 |
| `data_privacy_gap_count` | 数据最小化 / 隐私缺口数量 |

这里最重要的不是追求“100% 条款覆盖率”，而是：

> **每一个被标成 CORE 的关键要求，都必须能回答“代码在哪里、测试在哪里、Evidence 在哪里”。**

## 9. 对后续任务包的约束

从现在开始，新任务包如果涉及支付可信执行，应增加一项：

```text
External Requirement Impact
```

至少回答：

1. 是否关联《公约》某个能力族；
2. 对应哪些 Requirement ID；
3. 当前成熟度从 M? 提升到 M?；
4. 新增了什么 Test；
5. 新增了什么 Evidence；
6. 是否引入新的风险或越权能力；
7. 是否改变协议适配边界；
8. 是否需要回归已有 AP2 / ACP / UCP / x402 / APOP / ACT 场景。

这样《公约》才能真正成为开发指标，而不是只躺在 reference 里。

## 10. 当前优先级判断

按目前项目能力，建议优先顺序不是“把 34 条全部实现”，而是：

### P0：把现有强项接成可核验要求

优先：

```text
Authorization
Binding
Identity
Fact Lineage
Evidence
Replay
Attack Overlay
```

先建立 Requirement ID + Test + Evidence 映射。

### P1：补真正影响支付可信链的公共缺口

候选：

```text
KYA Lifecycle
Authorization Revocation
Agent Risk Tier
End-to-End Identity Propagation
Model Risk Gate
Continuous Monitoring Facts
Cross-Agent Risk
Emergency Stop / Fallback
```

### P2：建立外部系统接口边界

例如：

```text
AML / Fraud
Privacy / DLP
Institution Risk
Complaint / Dispute
Ethics Review
Regulatory Filing
```

项目只提供 Adapter / Fact / Evidence，不重复建设机构级系统。

## 11. 最终判断

《公约》对项目最重要的影响不是“金融机构才能做，所以个人创业没方向”，也不是“我们以后只能做 Trust Infrastructure”。

更准确的结论是：

> **持牌支付核心环节仍由持牌机构承担；智能体进入支付链路以后新增的大量身份、授权、控制、证据和验证问题，正是当前项目最值得研究和验证的部分。**

因此：

```text
不去抢“钱从哪里划、谁来清算”
重点研究“为什么允许 Agent 划、如何限制、如何证明、出错如何停和追责”
```

这应成为当前研发主轴。

未来商业形态仍可以是：

- Trust Infrastructure（信任基础设施）；
- Security / Compliance Evaluation（安全 / 合规评测）；
- Agent Payment Gateway 上层控制；
- Payment Orchestration 的 Trust Layer（信任层）；
- 银行 / 支付机构 Agent Runtime 的 Policy / Evidence 组件；
- Agent Commerce 的授权与支付控制组件。

当前不需要过早锁死最终创业产品形态。
