# Agent 身份与运行时授权开源项目参考

> 更新时间：2026-07-29
> 用途：为 Agentic Payment Trust Lab 的 P1—P5 提供外部实现与规范参考。
> 原则：先借架构、接口、测试方法和边界，不因为找到成熟项目就立即引入依赖。

## 1. 为什么单独建这份参考

当前项目已经把 Agent Trust Control Plane 收敛成：

```text
P1 Delegated Authority
P2 Continuous Binding
P3 Agent Identity
P4 Trust Source / Context
P5 Evidence / Replay
```

进一步核对外部项目后发现，这五块之间还需要一个共同中轴：

```text
Delegation
+ Binding
+ Identity
+ Context / Trust Source
+ Policy
        ↓
Runtime Authorization Gate
执行前授权闸门
        ↓
ALLOW / DENY / CONFIRM / WAIT
        ↓
产生真实副作用
        ↓
Receipt / Replay
```

这个 Gate 不是第七个领域对象，也不是新增一个 P 阶段，而是 P1—P5 最终汇合的执行前控制点。

## 2. 最值得持续跟踪的项目

| 项目 | 解决什么 | 对应本项目 | 当前吸收方式 |
|---|---|---|---|
| AARM | Agent 运行时安全的开放系统规范：执行前拦截、上下文累计、Policy + Intent、五类决策、Receipt、Identity Binding | P1—P5 横切 | **最高优先参考**。借 Gate、Gate 测试和 Receipt 要求，不宣称 Conformance |
| Microsoft Agent Governance Toolkit | 可运行的 Agent Governance 实现，包含 Policy Gate、Context、Identity、Audit、MCP 治理 | P1—P5 横切 | **最高优先代码参考**。重点看拦截接口、Policy/Context 输入、审计链；暂不整体引入 |
| SPIFFE / SPIRE | Workload Identity、运行实例 Attestation、短期可验证身份 | P3 Agent Identity | **P3 重点参考**。借 `Declared → Bound → Verified` 的实现方向，不现在部署 SPIRE |
| Cedar | 细粒度授权 Policy Language / Engine；`principal + action + resource + context` | Runtime Gate / P4 | **Policy Engine 候选参考**。先借授权请求模型和测试方法，不现在替换现有 Python 规则 |
| Open Policy Agent (OPA) | 通用 Policy-as-Code；业务代码把结构化输入交给独立 Policy Engine | Runtime Gate / P4 | **Cedar 的替代对照**。重点借“决策与执行解耦” |
| OpenFGA | Relationship-Based / Fine-Grained Authorization | P1 / P3 | **委托与关系模型参考**。适合表达 user → agent → resource 关系，不适合作为全部运行时安全逻辑 |

## 3. AARM：最重要的架构参照

官方入口：

- https://aarm.dev/
- https://aarm.dev/conformance
- https://github.com/aarm-dev/aarm

AARM Core 当前要求的关键能力：

```text
R1 Pre-execution interception
   所有 Agent 动作必须在执行前经过控制面

R2 Context accumulation
   决策不能只看当前一步，要看到当前任务和之前动作

R3 Policy evaluation with intent alignment
   Policy 判断当前动作，同时考虑是否仍符合原任务意图

R4 Authorization decisions
   ALLOW / DENY / MODIFY / STEP_UP / DEFER

R5 Tamper-evident receipts
   每次裁决都留下可验证 Receipt

R6 Identity binding
   Receipt 与执行身份绑定
```

### 对我们的直接吸收

我们的目标架构正式增加：

```text
Runtime Authorization Gate
```

它至少消费：

```text
subject / user
agent / executor
active authority + version
transaction object
current action
trusted context
session history / prior actions
policy version
```

输出先映射到当前项目已有决策语义：

```text
AARM ALLOW    -> ALLOW
AARM DENY     -> DENY
AARM STEP_UP  -> CONFIRMATION_REQUIRED
AARM DEFER    -> INDETERMINATE / WAIT
AARM MODIFY   -> 暂不自动映射
```

支付场景对 `MODIFY` 要特别保守：自动改写金额、payee、商品等关键字段本身可能破坏用户确认绑定，因此当前不把“修改后继续执行”作为默认能力。

## 4. Microsoft Agent Governance Toolkit：最值得读代码的样本

官方仓库：

- https://github.com/microsoft/agent-governance-toolkit

该项目当前公开实现覆盖：

```text
Agent / Tool Call
      ↓
Policy / Governance Gate
      ↓
Identity
      ↓
Allowed -> Tool executes
Denied  -> Side effect blocked
      ↓
Decision Record / Audit
```

公开仓库中可以重点研究：

```text
policy-engine/
agent-governance-python/
schemas/
benchmarks/prompt-injection/
tests/
```

### 对我们的直接借鉴

不复制整套框架，只看四件事：

1. Tool / Action 在执行前如何统一拦截。
2. Context、Intent、Agent Role、Action Parameter 如何组成 Policy Input。
3. Policy Decision 如何和真正副作用严格分开。
4. Audit / Receipt 如何保证事后能解释“为何放行”。

当前 P1 不需要引入该库；等 P2—P4 汇合成通用 Runtime Gate 时，再评估是否做最小 POC 对照。

## 5. SPIFFE / SPIRE：P3 Agent Identity 的现实参考

官方入口：

- https://spiffe.io/
- https://github.com/spiffe/spiffe
- https://github.com/spiffe/spire

SPIFFE 定义跨动态环境的 Workload Identity；SPIRE 是生产级实现，通过 Node / Workload Attestation 给运行中的 workload 发放短期 SVID。

### 它和我们 P3 的关系

我们当前只有：

```text
expected_agent_id == request.agent_id
```

未来可以逐级理解为：

```text
DECLARED
  Agent 声称自己是谁

BOUND
  当前执行实例和授权中的 agent_ref 对得上

VERIFIED
  有 workload identity / attestation / cryptographic credential 支持
```

SPIFFE / SPIRE 主要对应最后一层 `VERIFIED`。

### 当前决策

```text
P1 / P2 不引入 SPIRE
P3 先把 Identity Assurance 接口做出来
只有需要验证真实执行实例时，再做 SPIFFE/SPIRE POC
```

## 6. Cedar：最值得参考的 Policy Request 模型

官方入口：

- https://github.com/cedar-policy/cedar
- https://docs.cedarpolicy.com/

Cedar 的授权请求核心是：

```text
Principal
Action
Resource
Context
```

这个模型和我们的 Runtime Authorization Gate 很接近：

```text
Principal  -> subject + agent/executor
Action     -> pay / refund / retry / confirm / tool_call
Resource   -> order / payment / merchant / tool
Context    -> authority version + trusted facts + prior actions
```

### 当前吸收

先借它的请求模型和“Policy 与业务代码分离”的思想。

当前不马上把 Python 规则改写成 Cedar，因为：

1. P1 还在冻结业务语义；
2. 现在换 Policy DSL 会增加迁移成本；
3. 我们需要先证明哪些规则确实应该成为独立 Policy。

等 P4 后可以设计一个小型对照实验：同一组 Runtime Authorization Inputs，由现有 Python evaluator 和 Cedar evaluator 分别判断，再做差异测试。

## 7. OPA：Policy-as-Code 的另一条成熟路线

官方入口：

- https://www.openpolicyagent.org/
- https://github.com/open-policy-agent/opa

OPA 最值得借的不是 Rego 语法，而是：

```text
业务代码
  -> 结构化 Input
  -> 独立 Policy Engine
  -> Decision
  -> Enforcement Point 决定是否真正执行
```

这与我们的工程边界完全一致：

```text
Trusted Facts / Context
    ↓
Policy Decision
    ↓
Payment Domain / Action Layer
    ↓
真实副作用
```

### Cedar vs OPA 当前决策

现在不选型。

```text
Cedar：更贴近 authorization request / fine-grained policy
OPA：更通用、适合各种结构化策略
```

等 Runtime Gate 真正进入实现阶段，再用同一组支付策略做最小对照，不提前引入两套 Policy Engine。

## 8. OpenFGA：委托和关系图参考

官方入口：

- https://openfga.dev/
- https://github.com/openfga/openfga

OpenFGA 更擅长表达：

```text
user A
  -> can_delegate_to
agent B
  -> can_act_on
resource C
```

因此它最适合帮助我们想清：

```text
User
 -> Delegated Authority
 -> Agent
 -> Resource / Transaction Object
```

而不是替代 P4 的上下文累计、Prompt Injection 防护或支付状态机。

当前不接入服务，只借关系模型设计。

## 9. 开放标准：RFC 8693 / AAuth

### RFC 8693 OAuth 2.0 Token Exchange

官方标准：

- https://www.rfc-editor.org/rfc/rfc8693.html

它支持 Token Exchange 中的 impersonation / delegation，并允许把用户主体和 actor 关系传到下游，同时可签发面向特定 resource 的更窄 token。

对我们的未来价值：

```text
用户身份 / Subject
+ Agent / Actor
+ Target Resource
+ Narrow Scope
        ↓
短期执行凭证
```

它适合未来把 Runtime Authorization Gate 的“允许”结果转化成最小权限凭证，但 P1—P4 都不需要真正建设 STS。

### AAuth

IETF Datatracker 当前可查到 `draft-rosenberg-oauth-aauth-01`，但该 Internet-Draft 已于 2026-04-22 过期。

因此当前只把它当“Agent-native OAuth 授权正在探索什么”的研究材料，不作为实现标准，更不能写成已经成熟的行业规范。

## 10. 对本项目 P1—P6 的吸收映射

```text
P1 Delegated Authority
  <- OpenFGA 的关系表达
  <- RFC8693 的 subject / actor / delegation 思想

P2 Continuous Binding
  <- AARM 的 action-before-execution control
  <- AGT 的统一拦截点

P3 Agent Identity
  <- SPIFFE / SPIRE workload identity / attestation
  <- AARM Identity Binding

P4 Trust Source / Context
  <- AARM Context Accumulation
  <- Cedar / OPA Policy Input

          P1 + P2 + P3 + P4
                  ↓
        Runtime Authorization Gate
                  ↓
          ALLOW / DENY / CONFIRM / WAIT
                  ↓
             Payment Action

P5 Evidence / Replay
  <- AARM Receipt
  <- AGT tamper-evident audit chain

P6 Mature Payment Foundation
  <- 继续使用成熟支付规范
  <- 不由上述 Agent Identity 项目重新发明
```

## 11. 当前真正要吸收，而不是照搬的内容

### 现在就吸收

```text
1. 所有产生副作用的 Agent Action 都应经过执行前 Gate
2. Gate 输入不能只有当前 action，要带 task / intent / prior context
3. 用户身份和 Agent 身份必须分开记录
4. CONFIRM / WAIT 是正常授权结果，不是异常补丁
5. Gate 决策必须产生 Evidence / Receipt
6. Policy Decision 和 Action Execution 必须解耦
```

### 暂时不吸收

```text
完整 OAuth / STS
完整 SPIRE 部署
完整 Cedar / OPA 引擎替换
Agent PKI / DID Mesh
MCP Gateway 平台化
AARM Conformance 声明
企业级 Agent Inventory / IAM 产品
```

## 12. 后续研究 Gate

任何外部项目要真正进入代码前，必须回答：

```text
Q1. 它解决 P1—P6 的哪一个明确能力？
Q2. 我们是借模型、接口、测试方法，还是确实需要依赖？
Q3. 不引入它，现有最小实现是否已经足够验证问题？
Q4. 引入后能增加什么可证伪结果？
Q5. 是否会把 Agentic Payment Trust Lab 带偏成通用 IAM / Agent Security 平台？
```

当前默认策略仍是：**参考优先，依赖后置。**
