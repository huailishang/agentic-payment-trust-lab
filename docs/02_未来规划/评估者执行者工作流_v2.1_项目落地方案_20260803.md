> 日期：2026-08-03  
> 适用仓库：`agentic-payment-trust-lab`  
> 角色：项目级治理规则  
> 依据：`evaluator-executor-workflow/v2.1`

## 1. 一句话结论

现有评估者—执行者机制不推翻，增加两层：

```text
开发前：项目瓶颈裁决
开发后：项目影响裁决
```

完整闭环变为：

```text
项目目标
→ 项目瓶颈地图
→ 选择当前第一瓶颈
→ 冻结可证伪假设
→ 任务契约
→ 执行者单变量修改和原始证据
→ 评估者独立复核
→ 任务裁决
→ 项目影响裁决
→ 保留、回滚、换假设或重新排序瓶颈
```

## 4. task_kind 使用规则

每个新任务必须使用一个且只有一个 `task_kind`。

| 类型 | 本项目使用场景 | 是否必须绑定瓶颈地图和假设 | 项目影响裁决 |
|---|---|---:|---|
| `capability_experiment` | 要证明某项能力减少当前第一瓶颈 | 是 | 不得为 NOT_APPLICABLE |
| `repair` | 修复失败 AC、独立反例或实现缺陷 | 可继承父任务，但不强制声明能力增益 | 通常 NOT_APPLICABLE |
| `maintenance` | 文档、结构、依赖或常规维护 | 否 | NOT_APPLICABLE |
| `one_off` | 独立、一次性、完整交付 | 否 | NOT_APPLICABLE |
| `evidence_fix` | 只修报告、证据元数据、哈希或路由格式 | 否，且不得改实现与观察事实 | NOT_APPLICABLE |
| `evaluator_design` | 建瓶颈地图、评测集、指标或合同设计 | 可以引用地图，但不是能力实验 | NOT_APPLICABLE |

禁止：

- 为了满足模板把普通开发都写成 `capability_experiment`；
- 用“测试增加了”声称项目改善；
- repair 完成后自动宣称 active bottleneck 缩小；
- evidence_fix 创建新产品修复轮次。

新 v2.1 `CONTRACT.md` 在原有单一目标、AC、范围、排除项和验证命令外，必须增加：

```text

Strategic basis
Measurement status
```

### capability_experiment 必须回答


### AC 写法

每个强制 AC 应尽量包含：

```text

```

不能只写：

```text

测试通过
```

## 7. 执行报告新增要求

执行者仍然只记录事实，不发项目影响裁决。

`REPORT.md` 必须保留：

- 初始与最终 git status；
- 保存的 diff 与 SHA-256；
- 改动文件和 SHA-256；
- 每个 AC 对应的 EV triplet；
- 偏差、未运行检查和环境限制。

能力实验额外增加：

```text
Impact comparison
- Measurement evidence
- Before
- After
- Delta
- Guardrail result
- Scope caveat
```

禁止：

- 执行者写“项目明显改善”；
- 用完成代码数量替代 delta；
- before / after 使用不同任务集；
- 修改基线期望以适应本轮实现。

## 8. 交接责任变化

v2.1 的交接边界更严格。

### 执行者

```text
CONTRACT_FROZEN / Executor
→ EXECUTING / Executor
→ 完成 REPORT 和 EV
→ validator
```

如果 validator 返回：

- `FIX_IN_PLACE`：执行者在原报告和元数据内修正，仍保持 `EXECUTING / Executor`；
- `BLOCKING`：不得交接；
- `OK`：材料具备被评估者接收的结构条件。

执行者不能自行把任务改为最终 PASS。

### 评估者

评估者确认报告、证据和路由完整后，才接受为：

```text
READY_FOR_REVIEW / Evaluator
```

接受后：

- REPORT 与 Executor EV 不再修改；
- 评估者只写 REVIEW、RV-EV 和项目地图；
- 产品修复必须新建 bounded repair task。

## 9. 双重裁决

每个 REVIEW 必须有两个独立结论。

### 9.1 任务裁决

```text
PASS
REJECTED
HUMAN_REQUIRED
```

回答：

> 是否按冻结合同完成，证据是否真实，独立复核是否通过？

### 9.2 项目影响裁决

```text
IMPROVED
NO_MEASURABLE_GAIN
REGRESSED
INCONCLUSIVE
NOT_APPLICABLE
```

回答：

> 当前第一瓶颈是否真的变小？

可能出现：

```text
Task verdict = PASS
Impact verdict = NO_MEASURABLE_GAIN
```

含义：实现符合合同，但同基线比较没有达到改善阈值。

这种情况下不得因为代码已经开发，就继续沿同一假设追加更多功能。

## 10. 地图更新规则

不在每轮任务后机械修改地图。

只有出现以下证据才更新：

- 第一瓶颈实测缩小；
- 新证据改变瓶颈排序；
- 两到三轮同类实验无收益；
- 失败转移到另一阶段；
- 项目目标、外部约束或评测环境变化。

地图更新顺序：

```text
先完成当前 REVIEW 和 impact verdict
→ 再修改地图 revision
→ 下一任务引用新 revision
```

禁止让当前任务引用执行过程中被重写的地图版本。
