## 2. 筛选标准与证据分层

合格环境至少要具备：实际外部 API、由服务方维护的可回查对象、稳定操作标识及防重机制、能在我方受控位置制造响应丢失、明确测试凭证和隔离边界。第一轮不要求独立商户，但必须标明商户服务是否由本项目控制。

- 本地离线样本：输入和结果由本地构造，继续用于快速回归。
- 外部支付服务方沙箱：请求进入外部系统，测试交易状态由服务方维护；不经过真实卡网络、不移动真实资金。
- 公共测试网：增加可由其他节点查询的测试资产转移；不自动证明资源交付、真实主体或商户身份。
- 生产支付、第三方独立采用和商业价值：均未验证，不由上述层级替代。

因此外部沙箱仍然模拟资金，但与本仓自己返回成功具有不同的证据来源。这正是本轮要补的接口与恢复适用性。

## 4. Stripe：出现了较低门槛的具体接入路径

[官方沙箱文档](https://docs.stripe.com/sandboxes)明确列出无需预先注册账户的匿名沙箱。官方同时说明沙箱付款不经过卡网络或支付提供商，不能称为真实资金结算。[CLI（命令行工具）文档](https://docs.stripe.com/cli#sandbox)说明临时凭证会保存到本地配置，文档有效期为七天，创建要求邮箱或从 Git 配置推断邮箱/姓名。

本轮从官方 GitHub 核对了已发布 [v1.55.10](https://github.com/stripe/stripe-cli/releases/tag/v1.55.10)（发布时间 2026-11-10T18:18:01Z）的 [sandbox.go](https://github.com/stripe/stripe-cli/blob/v1.55.10/pkg/cmd/sandbox.go)，确认匿名创建和邮箱参数处理在发布标签内。另固定主分支 `f3ea38a25b2836cd127125331b6569e94833928f`，查看 [创建流程](https://github.com/stripe/stripe-cli/blob/f3ea38a25b2836cd127125331b6569e94833928f/pkg/cmd/sandbox.go)和[沙箱客户端](https://github.com/stripe/stripe-cli/blob/f3ea38a25b2836cd127125331b6569e94833928f/pkg/sandbox/sandbox.go)：有官方 challenge/provision 接线，返回测试密钥、环境标识及过期信息；这不是根据宣传页猜测接口存在。

发布元数据显示 Windows x86_64 压缩包为 11,929,882 字节，SHA-256 `ea273eaabe6641fc960c7b7fcdb1a7e6cb45ca47fe8202c91b2ef89458ccd937`；本轮未下载、核验二进制或执行命令。官方 CLI 根许可证为 Apache-2.0；服务条款、实际地区可用性、配额及返回凭证权限仍须在受限运行前确认。

关键取舍：无需预先注册正式账户，不等于无需个人数据或本地配置。不得自动用 `--from-git` 外传仓库邮箱/姓名；必须明确使用哪个邮箱。创建流程会输出或保存密钥，不能让完整输出进入工具日志、仓库或公开报告；已有正式配置不能复用。匿名失败还有浏览器登录回退，未来运行须明确停止，不自动认领正式账户或转正式登录。

[付款查询接口](https://docs.stripe.com/api/payment_intents/retrieve)可以按付款对象 ID 独立请求其状态；[幂等文档](https://docs.stripe.com/api/idempotent_requests)说明 v1 会保存首次已执行结果，包含错误，且键可能在至少24小时后清理。因此不能把重复请求仍返回错误直接当作未付款，也不能把这个保存期限视为永久业务防重。

[官方测试文档](https://docs.stripe.com/testing)提供合成 PaymentMethod（支付方式）及失败/认证场景。本轮不新增这些案例。实际商户前台优先考虑官方建议的 [Checkout（托管结账）](https://docs.stripe.com/api/checkout/sessions/create)；若仅测服务端付款状态恢复，可在合同中解释为何采用较窄的付款对象接口。不得仅根据成功页、模拟事件或本地改写的返回值判付款成功。

尚未知：本机是否能创建匿名环境、返回密钥能否执行本项目所需操作、具体权限/配额、外部对象与现有内部执行记录如何最小接线。结论是 `QUALIFIED_BY_DOCUMENT_AND_RELEASE_SOURCE`（文档及发布源码满足候选资格），不是运行就绪或产品通过。

## 5. PayPal 与 x402 的比较依据

[PayPal 官方沙箱](https://developer.paypal.com/sandbox-testing/overview/)是服务方托管的虚拟测试环境。[账户说明](https://developer.paypal.com/sandbox-testing/accounts)规定典型测试用一个个人买家账户和一个商户账户；本轮未登录、查找凭证或创建账户。

其 [Orders API（订单接口）](https://developer.paypal.com/api/orders/v2)有创建、批准、收款及[按 ID 查询](https://developer.paypal.com/api/orders/v2/orders-get)，[幂等说明](https://developer.paypal.com/api/rest/reference/idempotency/)明确要求逐接口核对 `PayPal-Request-Id` 支持及保存时间；不能把通用资料中的“最多45天”套到所有订单操作。

[Webhook（事件回调）模拟器](https://developer.paypal.com/api/rest/webhooks/simulator/)产生的事件并不关联真实应用交易，不能作为订单已付款证据；若后续做回调，应来自实际沙箱业务操作并能与查询结果对应。首轮可先查询恢复，避免先部署公网回调接收器。PayPal 更适合验证买家批准到商户收款的流程，但若没有现成开发者资格，新增账户与交互成本预计高于 Stripe 匿名方案。

x402 官方[网络文档](https://docs.x402.org/core-concepts/network-and-token-support)列出公共测试结算服务支持 Base Sepolia；[恢复文档](https://docs.x402.org/core-concepts/facilitator)区分等待确认与失败，以及默认内存恢复存储的限制。它适合需要外部结算事实的付费资源试验，但会增加钱包、签名、测试资产和最终性边界。已有 P8 测试网延期不因本次搜索自动解除。此轮未查询 supported、verify、settle 或 RPC。

支付宝继续保留而不重跑。已有 H38/H41 研究表明未闭合点不只是有没有沙箱账号，还包括有效 Payment-Proof（支付凭证）、传输边界及订单/金额/资源绑定；本轮没有新证据消除这些已知断点，不重复查资料或放宽旧验收。

## 6. 推荐的第一轮实际验证形态

首选一个隔离 Stripe 沙箱、一个本地受控数字资源、一个固定测试商户上下文：

```text
固定任务与金额批准
→ 本仓执行前裁决
→ 外部沙箱创建/确认测试付款
→ 服务方按 ID 查询付款与收款对象
→ 本地资源交付及客户端内容检查
→ 原操作恢复与审计
```

第一轮只保留两个功能情形：正常流程；服务方处理后我方丢失付款响应，再查原对象恢复。恢复时复用原业务操作和幂等键，不新建付款。暂不展开六类攻击、更多支付方式、强认证、跨商户及退款体系。

同时需要官方组件原有保护的对照，保留其幂等机制。若原组件与接入本仓都正确，只记录接入证据；本仓安全增量未测出就不扩能力。来源与结算真实性、控制效果、交付结果、独立采用分别记账。

候选执行预算估计：一次环境创建；一个指定发布版本；60分钟墙钟；至多两个不同业务操作、两笔成功的测试付款；每笔合成 USD 1.00、累计 USD 2.00，仅作沙箱账面值；创建/确认/查询总计不超过20次 API 请求，失败也计数。明确操作恢复与环境创建的停止条件，创建失败不自动重试或换平台。实际金额、方法、预算及同基线对照须在授权后冻结，当前不是执行合同。

没有第二笔的判定须包括隔离环境内对象清点、业务操作到付款对象/收款对象的对应、限定时间和查询范围，不能只看“相同对象查询成功”或余额。履约证据来自自有服务及客户端，不能计为第三方商户独立交付。
