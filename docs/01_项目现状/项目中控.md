# 智能体支付实验项目中控

> 更新时间：2026-09-08

## 1. 一句话定位

本仓库不是生产支付系统，而是 **Enterprise Agent Control Plane（企业智能体控制平面）的高风险交易 / 智能体支付信任验证场，也是当前最严格的 Security（安全）压力测试场**。公开展示名统一为 **Agentic Payment Trust Lab / 智能体支付可信实验室**：用协议中立模型、固定风险场景和外部挑战，验证智能体（Agent）代表用户下单、付款、履约、退款和恢复时，Identity Binding / Identity Assurance（身份绑定 / 身份保证）、Authorization / Delegation（授权 / 委托）、Binding（绑定）、Context / Tool Integrity（上下文 / 工具完整性）、Transaction Integrity（交易完整性）、幂等、Trace（轨迹）与 Audit / Recovery（审计 / 恢复）是否可靠。当前不把本地标识绑定表述为真实 Authentication（认证）；强认证、凭据 / 密钥治理和密码学签名验证仍需后续真实证据。支付领域规则留在本仓；只有跨领域稳定重复的安全 / 控制机制才进入 Control Plane 公共层。

项目能力不局限于信用卡，公开仓库名统一为 `agentic-payment-trust-lab`。项目不接真实卡、真实资金、生产商户、生产私钥、联机放行或清算网络。

## 2. 当前结构：一仓两域

唯一主仓库就是当前仓库根目录，仓库名为：

```text
agentic-payment-trust-lab
├── 支付域
│   ├── 委托 / 智能体意图
│   ├── 订单 / 支付请求
│   ├── AP2 / ACP 等适配器
│   ├── 允许（ALLOW） / 拒绝（DENY） / 需要确认（CONFIRMATION_REQUIRED） / 无法判定（INDETERMINATE）
│   ├── 支付执行 / 状态恢复
│   ├── 履约 / 退款 / 争议
│   └── 生命周期教学界面（UI）
│
└── 可信执行域
    ├── 规范化
    ├── 哈希 / 绑定
    ├── 后续签名 / 身份
    ├── 后续幂等 / 状态验证
    └── 后续审计 / 不变量
```

依赖方向只有：

```text
支付域
    -> 调用可信执行域
    -> 获得“对象是否一致、证据是否可信、是否存在重复或冲突”等确定性事实
    -> 支付域自己决定业务动作
```

可信执行域不得直接返回支付业务的 `ALLOW`、`DENY`、`CONFIRMATION_REQUIRED`、退款、争议或重试政策。

### 4.3 协议竞争与 x402 按量计费：新增两个验收维度

2026-09-02 补充两组外部材料：

1. 人民银行副行长陆磊在第十五届中国支付清算论坛的公开讲话及权威媒体报道：过去一年智能体支付协议密集出现，竞争将延伸到协议 / 技术标准；长期兼容不足可能形成新壁垒。
2. Apify 的 x402 实际接入说明与 x402 v2 官方规范：机器资源支付已经出现 `exact / upto / batch-settlement` 等不同收费与结算语义，协议本身不自动解决 Agent 的任务级总预算、实际用量、服务交付和失败补救。

对项目的吸收结论：

```text

→ 后续增加 Metering → Settlement → Fulfillment 商业闭环验收
→ 不新增第 7 个领域对象
```

两个方向都**不改变当前 B-04 / H-11 的冻结 Contract 和第一瓶颈顺序**。当前仍先证明真实 Autonomous Agent 行为；之后再把机器资源商业闭环和跨协议不变量作为后续独立实验。

H-15 在 Executor 开始前被主线替代。它的 `2/5` probe、Systematic `19/24`、failure ledger 全部保留，以后只有在 Agent policy / model 发生重大升级，或 intent/option 问题真实阻塞信任链时才重新激活。

Fresh Unseen Transfer Measurement（新鲜未见迁移测量）也从“进入 H-13 的强制 Gate”降级为 B-04 的后续评测工具。

失败归因已经高度集中：`REQUIRED_OPTION_MISMATCH（必要规格不匹配）=4`，`TARGET_PRODUCT_MISMATCH（目标商品不匹配）=1`。因此当前不再笼统说“unseen transfer 未测量”，而是把 B-04 的第一重复失败位置收敛到 option grounding（规格依据用户要求进行匹配）：已选规格可能被后续误覆盖，尺寸 / 数量 / 包装表达与页面标签不能稳定归一，多规格组不能连续完成。

这里增加一条长期主线原则：**不要把“当前已经发现的细节”当成“能力空间已经测全”**。项目不追求靠人工不断补更多 Case 来穷举细节，而采用四段式收敛：先修重复已知失败族，再用 capability invariants（能力不变量）做系统性变形测试主动找反例，再用 fresh unseen evidence（新鲜未见证据）测迁移，最后按 failure family（失败族）决定是否值得继续修。同一新问题只出现 1 个孤立 Case 时默认进入 failure ledger（失败台账）观察；只有在多个独立 Case 重复，或触碰零容忍安全守护线时，才升级为新的 hypothesis（假设）和执行包。若连续新增细节持续分裂成多个互不相关规则，应考虑 SWITCH（换方向），而不是无限增加确定性补丁。

另一个长期证据边界仍保留：H-11 是 accepted-but-uncommitted（已验收但未提交）快照，只留下 policy SHA-256 `af2a8530c661709c35a806f4074c38691ba9718f63d2f4d3aa8a2f5d2aa61189`，没有 exact source snapshot（精确源码快照）。因此仍不得伪造 H-11 vs H-12 的同集 before / after。

### 4.5 当前 Evaluator 路由规则

H-17 已正式复核通过：Task=`PASS`、Project impact=`NOT_APPLICABLE`、Evaluator L3=`8/8 PASS`，same-journey `C01..C08=8/8`，五类 Action Origin 均可投影，Trace=`VALID`，full unittest=`657/657`，真实 Buy Now / payment / fulfillment / network side effect 均为 0。

这说明 H-16 的失败主要是 measurement baseline lifecycle（测量基线生命周期）错误，而不是现有 Adapter / Runtime Gate / Sidecar / Trace 产品链失败。B-11 因此阶段性关闭，不继续扩 `action_origin` 字段。

当前路由为：

```text
task_id: P9-AUTONOMOUS-WEBSHOP-SAME-JOURNEY-PAYMENT-LIFECYCLE-BRANCH-MEASUREMENT-V1
task_kind: one_off
state: CONTRACT_FROZEN
current_role: Executor
active_bottleneck_id: B-12

project_map_revision: 2026-09-06-r28
```

H-18 是 measurement-only（只测量）任务。它复用 H-17 已验收的同一 pre-payment journey，对四个互斥离线反事实分支做 `repeat=2`：

```text
J01 payment SUCCEEDED + fulfillment SUCCEEDED
J02 initial UNKNOWN → trusted query SUCCEEDED
J03 payment SUCCEEDED + fulfillment FAILED
J04 query SUCCEEDED / async FAILED terminal conflict
```

评估重点不是要求四分支都“跑绿”，而是如实测量：

```text
observed semantics
semantic_match
same Order / Request / Payment refs
Trace availability / validity
Action Origin projectability
8 continuity checks
first_breakpoint
```

Task PASS 只要求 4/4 Case 完整、重复可复现、证据真实、Evaluator audit 可机械复核、真实副作用为 0。若出现 `semantic_match=false` 或 `continuity_pass=false`，属于项目 finding，不允许 Executor 在 H-18 里修改 Sidecar / Recovery / Finality / Conflict / Lifecycle / Trace 等产品逻辑。

四个分支共享同一 parent journey，但它们是互斥 counterfactual branch（反事实分支），不得声称同一真实交易同时经历四种结果。

H-15 / Fresh Unseen 继续保持 B-04 WATCH，不重新打断支付生命周期主线。

## 5. 当前最重要的判断

截至 2026-09-06，项目当前最重要的判断已经从“Agent 能不能选得足够准”切换为：

> **Agent 已经会行动，也会犯错；现在要把“谁做了什么决定、依据是什么、Runtime 有没有另行裁决、最后执行结果是什么”纳入可信支付责任链。**

大白话就是：

```text
以前重点：
Agent 会不会买、会不会选对

现在重点：
用户说了什么
→ Agent 自己决定了什么
→ 网页/商户给了什么事实
→ Runtime 又决定了什么
→ 最后支付/履约发生了什么
→ 每一步证据能不能回指
```

这是支付信任项目比“做一个更聪明的购物 Agent”更核心的价值。

当前正确顺序：

```text
B-04 Autonomous Behavior
阶段性验证完成，长尾 WATCH
        ↓
B-11 Action Origin / Same-Journey Responsibility
STAGE CLOSED：5/5 origin + 8/8 same-journey
        ↓
B-12 / H-18 Same-Journey Payment Lifecycle Branch Measurement
当前执行：把同一 Agent journey 放进支付状态 / 恢复 / 履约 / 冲突分支
        ↓
根据 semantic X/4 + continuity Y/4 决定是否需要最小产品修复
        ↓
Payment / Finality / Fulfillment / Recovery / Closure
        ↓
Accountability View / Replay
```

以下内容不再抢占当前主线：

- H-15 intent / option uncertainty：保留回归资产，不主动逐题修；
- Fresh unseen transfer：Agent policy 大改或 B-04 再次成为真实瓶颈时再做；
- x402 测试网、Metering→Settlement→Fulfillment、Cross-Rail、Cross-Protocol Invariance：继续作为后续分支；
- 法律责任 / 赔偿责任 / 监管责任：不由本项目的 technical responsibility trace 自动推导。
