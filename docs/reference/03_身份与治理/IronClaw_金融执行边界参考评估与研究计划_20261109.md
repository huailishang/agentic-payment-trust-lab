## 1. 全局位置与本轮目的

- 最终目标：证明智能体交易的用户授权、对象绑定、执行前治理、恢复与审计能够独立复核。
- 最新地图r106：A–D本地阶段关闭，E受控本地代表性闭合，F外部验证当前。第一瓶颈B-18仍是外部轨迹的独立可判定性；真实身份、凭据治理、清算和客户价值尚未证明。
- H64R已独立签收；本次写文档时H65为EXECUTING/Executor、已提交L2、尚待独立复核。这个事实不由外部资料或本笔记代替验收。
- 本轮只建立外部机制与现有代码的对照，并准备11月10日的研究问题；不调整瓶颈排序，不修改CURRENT、H65合同或其预算。
- 继续条件：找到现有代表覆盖之外、能从具体执行入口复现的新断点，才考虑另冻一个最小测量任务；若只是已有能力换名、只有旧设计或缺执行证据，停留在参考资料。

H65解决“外部材料能否形成交易证据”，IronClaw研究解决“运行环境怎样限制模型、工具和签名/付款执行器的权力”。二者相关，但后者不能补造前者缺失的事实。与重新扩本地测试或恢复受授权限制的真实支付相比，本次短时只读研究成本更低；它也不自动升为新的第一瓶颈。

## 2. 大白话结论

IronClaw最值得研究的是：**模型可以提方案，但真正执行资金动作的服务，要独立知道谁批准了什么、从哪里取最终参数，以及这次执行权是否已经用过。**

这与本项目的目标重叠。我们应核查它如何把安全规则接到真实工具入口，而不是据此宣布本仓缺五个新模块。它也不是已经获证的客户需求、独立评测集或支付服务方付款凭证。

NEAR AI在2026-02-23的官方发布中将IronClaw定位为Rust智能体运行环境，并介绍其云端TEE部署；这是厂商产品说明，不能推导为本仓已获得硬件证明或金融授权正确性。[官方发布](https://near.ai/blog/near-ai-launches-ironclaw-confidential-gpu-marketplace-and-multimodal-confidential-inference)

## 4. 三层执行设计的参考价值与限制

Read / Prepare / Spend（读取 / 准备 / 资金执行）设计的关键，是把可修改的模型建议变为服务端保存、带版本和有效期的执行对象，后续只按引用读取；展示、批准和执行都应由同一对象导出。不能在执行时重新信任模型转述的金额、收款方或签名数据。[#1712正文](https://github.com/nearai/ironclaw/issues/1712)

这主要约束**准备后**的替换。若准备前的网页污染已影响候选交易，冻结错误对象并不能让它变成用户授权。因此准备输入仍须与独立可信的用户约束比较；修改对象后也必须重新核验是否仍在有效授权内，必要时重新确认。[项目成员评审](https://github.com/nearai/ironclaw/issues/1712#issuecomment-4149600391)

另一个限制是：本项目的“准备订单”有时会创建持久checkout或占用库存，未必是无副作用操作。不能把上述三层名词机械映射为“所有prepare工具都可自动放行”；应按实际状态变化和可恢复性分类。

### 4.1 可信签名计划还能提供什么线索

#6532提出把展示内容、规范签名字节、签名账户、精确链标识、交易类型和展示版本纳入同一绑定，并由一次授权领取独立的执行权；批准摘要本身不是授权。对本仓最有价值的通用问题是：**用户看见A、批准A，执行器会不会因为另一适配层重新编码或重建对象而实际提交B？** 链标识只适用于相应链交易，不应强塞进普通支付合同。[可信签名设计](https://github.com/nearai/ironclaw/issues/6532)

同一计划把广播幂等状态与普通任务状态分开，要求未知结果进入查询/人工核查路径，不能悄悄换新nonce重新广播。可以借它检查“批准消费、执行占用和外部结果恢复”是不是同一条可靠链；当前仍只是设计参考，不说明本仓已拥有硬件签名或链上终局性。

## 5. 当前代码里值得继续追踪的两个具体线索

### 5.1 密钥服务不等于执行入口已经隔离

固定提交的`crates/substrates/ironclaw_secrets/src/lib.rs`开头明确区分：该模块负责带租户范围的秘密保存和不透明句柄/租约，不自行作授权判断、运行时注入或审计；还需要上层组合消费这些原语。

这支持我们研究**句柄 → 授权 → 宿主注入 → 限制目标地址 → 工具调用 → 回执**是否完整接线，而不是仅看到密钥模块就认定所有工具通道都安全。本轮只读了模块入口，未追完网络、WASM、MCP和浏览器的全部路径。[固定源文件](https://github.com/nearai/ironclaw/blob/b0b999d96781516ee05e6ba961d6f3ead900da96/crates/substrates/ironclaw_secrets/src/lib.rs)

### 5.2 审批成功与一次执行权不是同一件事

固定提交的`crates/kernel/ironclaw_approvals/src/lib.rs`说明审批服务发放受限能力租约，不直接执行工具。其租约发行重试注释还提示：底层每次可产生新grant id；若重复租约不可接受，调用者须核对已有租约。

这是一个**待核实的消费端约束**，不是已确认漏洞。本次研究应检查具体资金能力如何领取和消费权限，是否存在原子去重、过期/撤销检查和失败恢复；不能把“审批记录重试安全”直接当作“不会重复执行资金动作”。[固定源文件](https://github.com/nearai/ironclaw/blob/b0b999d96781516ee05e6ba961d6f3ead900da96/crates/kernel/ironclaw_approvals/src/lib.rs)

## 7. 对用户材料的保留意见

合理部分：模型与执行权分开；最终参数不经模型回传重新采信；财务批准不能被通用自动批准替代；未知结果先查询原交易；确认摘要要绑定实际执行内容。

需要降格或补证据的部分：

1. 五项P0/P1建议不是本仓差距排序。授权、绑定、确认、幂等、恢复已有代表性实现，不能直接新建五个模块或重开已关闭阶段。
2. Issue完成、PR存在、README特性声明与主分支已接线、运行验证、外部消费者有效性是不同证据等级；尤其不能将7月旧计划当作11月完整产品交付清单。
3. 不透明spec id不是授权凭证；仍要防跨用户/租户引用、过期、撤销、重复领取及存储记录被修改。一次批准也不自动授权任意次重试。
4. 标准交易摘要、不可变对象、签名合法，都不能证明准备输入最初符合用户意图；哈希一致也不能替代授权来源。
5. 同协议或跨协议的六类攻击建议多数已有代表性覆盖。未来只有出现新的运行通道/消费者接缝，才测相同风险是否跨边界失守，不以测试数量证明增量。
6. Rust、WASM或TEE本身不证明交易语义正确；不因NEAR生态而引入链、代币、DeFi或硬件钱包。整套运行时替换与真实资金接入为REJECT（本轮不采用）；其安全机制仍可参考。

首选候选问题：**在一个明确运行入口中，通用自动批准或重试是否仍然不能替代“某用户对某交易的一次有效执行授权”？** 只有当前代码和可独立判定的测试输入支持时，才考虑后续冻结；本笔记没有授权该实验。

## 10. 11月10日评估更新：先纠正判定，再决定接入研究

H65独立复核没有支持“这六例缺确认桥，所以停止”的执行建议。原turns中四条用户消息的arguments.consent直接包含checkout_id、amount、currency和given=true；第4例工具定义还明确标注allowance.max_amount的单位。原分析漏读这些字段，虽L3结构四项通过，仍因AC-02/03/04语义失败而拒收。直接位置与限制见H65 REVIEW；下一H65R只修已知漏读，不扩样、不联网、不回放。

这改变眼前优先级：B-18首先是恢复源事实判断的可靠性。不能拿失真的“证据不足”结论支撑切换到IronClaw，也不能由发现确认字段就宣布真实身份、签名、付款或完整单位链已证明。修复签收后才能按完整链决定是否另冻回放测量；确实仍缺环则停止当前源视图。

本日补读固定提交的宿主入口与WASM凭据接线：HostRuntime（宿主执行接口）包装CapabilityHost（能力调用协调器）；HostWasmRuntimeCredentials（宿主WASM凭据提供器）的说明要求先有宿主批准的暂存注入计划，不把秘密交给WASM，也不自行授予新权限。这比单独看到秘密存储模块更具体，但本次未安装、执行或追完资金工具调用，不能升级为已验证金融执行闭环。[固定宿主入口](https://github.com/nearai/ironclaw/blob/b0b999d96781516ee05e6ba961d6f3ead900da96/crates/kernel/ironclaw_host_runtime/src/lib.rs)、[固定凭据接线](https://github.com/nearai/ironclaw/blob/b0b999d96781516ee05e6ba961d6f3ead900da96/crates/kernel/ironclaw_host_runtime/src/wasm_credentials.rs)。
