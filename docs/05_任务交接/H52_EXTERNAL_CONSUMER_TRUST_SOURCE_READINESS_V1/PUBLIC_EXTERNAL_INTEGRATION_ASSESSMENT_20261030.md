## 全局判断

最终目标是授权、绑定、受控执行、恢复、审计可独立复核。A–D阶段关闭、E仅本地代表性闭环、F当前。B-17仍第一瓶颈：H51证明人工接线下固定本地入口可测，尚未把外部标准授权与项目执行/恢复/证据串成同一条可消费链。继续同类锁或路由样本边际价值低；支付宝与比赛保持延期，真实客户不应成为公开受控研究的机械前置条件。

## 必须纠正的安全推论

1. **AP2签名不自动等于用户同意。** 需要可信签发主体、密钥信任根、用户确定性确认或既有委托链。模型所在进程自己生成一把key并签名，只能证明它有这把key，不能升级为真实用户授权。受控测试可以采用独立角色/合成用户，但必须明示边界。
2. **HTTP签名不等于交易授权签名。** 现有花店RFC 9421请求验签不替代merchant_authorization/CheckoutMandate/PaymentMandate。
3. **验签和执行之间仍需绑定。** 即使授权签名全部有效，也要在实际执行位置约束当前checkout、数量/金额/币种/收款方与已确认内容。保留H50R2的持久执行占用、稳定引用和查询恢复，防止检查后变更、换键重放或直接调用旁路。
4. **完整签名对象不能先丢字段再验。** UCP扩展要求对除ap2外的完整checkout做JCS（规范化序列化），并绑定商家签名。现有业务投影适合中立模型，不能替代原始签名对象。教程排序JSON示例不能直接当通用JCS实现。
5. **Stripe不能被默认为AP2授权验证方。** 必须选清楚谁验证PaymentMandate、谁持有服务方密钥、哪个执行点调用服务方；metadata仅是关联线索，不是授权证明。用户委托授权与Stripe资金预授权也是不同对象。
6. **撤销的有效先后要定义。** 本地撤销/执行占用先后不能外推跨系统即时撤销，已经完成的付款不能靠撤销变回未发生。
7. **两协议复用只比较共同可表达语义。** ACP缺失AP2某类证明时应保留缺证据等级，不能为使结果一致而编造VERIFIED。
8. **“未经授权的钱永远付不出去”需限定声明。** 可验收的是固定授权主体、密钥、可控写入口、实现版本和攻击范围内的零错误放行证据；不外推生产资金、所有调用通道或监管合规。

## 三阶段建议

| 阶段 | 项目化目标 | 本轮优先度／成本估计 | 进入与停止条件 |
|---|---|---|---|
| 接入1 | 固定UCP checkout与AP2授权，经现有中立判断进入真正商家执行点，保留恢复和审计关联 | 优先；成本中等估计，版本/角色/签名载荷未固定前不称就绪 | 先只读核对版本和能力；已有功能不重做；不能映射或需重写商家则退回合同；仅模拟付款 |
| 接入2 | 保持商城/授权/测试不变，只换一种Stripe沙箱支付流程，取得服务方观察与异步状态证据 | 有条件候选；成本中等估计，环境/配额/密钥与权限未知 | 先离线合同/事件回放，再有界真实沙箱；无授权则不外连。不得全面替换Mock，保留确定性故障回归 |
| 接入3a | 换完整商城，保持已选协议、授权与付款合同，测同一核心能否复用 | 延期；成本高估计 | 只有第二商城带来未覆盖工作流或独立复用证据才做，不为“商城更完整”而接 |
| 接入3b | 固定同一商城与付款，增加第二协议并比较共同语义 | 延期；成本高估计 | 先单协议链验收，另一协议仅适配；官方已有保护作原生基线，不另写第二套核心 |

Stripe沙箱通过只升级“外部服务接口证据”，不是实网资金清算/生产身份/真实商户采用。Medusa官方支付组件应复用，不能再由Python核心和Medusa各自独立确认/扣款，必须定义唯一执行责任和事件回传。第二个支付商城仍属同一领域，不满足向Enterprise Agent Control Plane回抽的跨领域第二消费者条件。

## 更合适的结构

UCP/ACP协议对象与原始签名证据
→ 协议专属解析、验签、来源/缺失标注
→ 现有中立事实与支付业务规则
→ 不可绕过的商家执行控制（绑定快照、持久占用、稳定引用）
→ 该链唯一支付适配器（Mock或Stripe）
→ 结果查询/异步事件
→ 现有生命周期、Trace、Read Model与独立评测

AP2位于协议证据边界，不成为整个核心的必需协议。商城与支付适配器按实际责任固定，不先造双重抽象层或新增独立控制服务。智能体框架与模型可暂时保留固定脚本；第一阶段不同时迁移ADK/Gemini、前端、数据库或新身份系统。

## 下一最小任务建议（尚未派发）

先做H52的一个只读就绪单元：**固定UCP/AP2版本与可信签发/执行责任，查清标准授权能否复用现有执行闸门**。使用已有花店和H37接受结果，教程为机制对照；不重做H47/H49通用研究，不要求先有付费客户。主动时间上限建议2小时，不安装、不运行云/模型/商家/服务方，不新增产品实现。

应交付一张差距表：版本/schema；协商能力；完整签名载荷/JCS；用户/平台签发角色与可信根；商家强制入口；金额/币种/收款方与稳定执行引用；查询/审计回传。每项区分已有代码、已有运行证据和待补，不用规范存在填“已覆盖”。

完成后只有三种决策：
- 当前版本有可复用接缝 → 冻结一个最小“授权→执行”包；
- 必须升级/补商家扩展 → 单独列明确商家合同变化，再决定是否值得投入；
- 只会得到另一个自签模拟演示或必须重写商城 → STOP，比较第二消费者/Provider候选。

下一实现包的候选验收必须至少包含：合法授权完成一次；未获确认但签名有效仍拒绝；篡改/跨checkout/跨收款方或币种拒绝；过期/撤销按明确先后拒绝；同键重放不重复、换键不能复用同一一次性授权；检查后变更及直调旁路零付款；付款后异常用原引用查询、不盲重试；运行证据进入现有审计消费链。具体场景数量、代码范围、独立判定与预算在固定来源后冻结，不在本评估中伪造可执行计划。
