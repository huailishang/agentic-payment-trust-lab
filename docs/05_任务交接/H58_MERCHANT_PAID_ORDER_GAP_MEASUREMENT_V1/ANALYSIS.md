# H58：已付款无订单——能补什么、还缺什么

本轮**只有只读测量**。固定输入来自 H57R 已验收的评估者 `run_0002`，不是当前再开商城，也没有新付款或补单。读取 `transactions.db`、`psp.db` 使用 SQLite `mode=ro&immutable=1`，输入文件的 SHA-256 由冻结清单约束。两次测量输出一致，不能代替真实商家账务/生产验证。

## 业务结论

正常对照 M01：一次模拟付款、一个订单、库存从5变4；HTTP顺序201/200/200/200/200。故障 M06：一次模拟付款、**零订单**、库存仍为5；HTTP顺序201/500/200/409，重启后 `recover` 返回 `QUERY/SUCCEEDED`。这不是重复扣款：**钱的模拟状态已成功，但商城完成订单的第二事务在提交前被故障打断。** `GET 200` 只是结账对象可读，并非订单成功。M06 的 `h50_attempts.state=IN_FLIGHT` 是商家本地持久占用状态，不是支付失败；成功来源于模拟 PSP 的收据及只读对照，不能外推为实际 PSP 最终清算。

M06 固定事务库实际保留：checkout ID、确认快照与撤销位、授权**摘要**、支付引用与原请求哈希、商品rose数量1/金额1000 USD、合成商户和收款方、当前库存5。独立假 PSP 库保存1次charge、1条receipt及1条query。未找到对应订单行；`checkouts.data.order` 为null。只有“create”记录进入 `idempotency_records`，原complete在独立交易占用表中有key/hash，但没有可按原始字节重验的生产授权及原完成请求。真实来源校验必须同时追踪冻结 L3 HTTP 证据和代码，不把测试交接对象默认为可长期使用的商家凭证。

## 持久与实验边界：12个检查主题

| 主题 | 本地观测及可用性 | 对自动动作的限制 |
| --- | --- | --- |
| 结账身份 | 持久checkout ID及attempt主键一致 | 不是最终订单ID |
| 付款引用/状态 | 持久payment_ref及假PSP收据，商家仍IN_FLIGHT | 不代表生产结算，也不授权副作用 |
| 金额/币种/收款方 | USD、1000、合成payee/merchant及快照已留存 | 未验证真实渠道、清算、退款额 |
| 商品/履约 | rose数量1与配送快照已存 | 没有完成的订单及履约承诺 |
| 回滚库存 | 当前5；M01对照4 | 不能保证未来可补单时库存仍可用 |
| 确认/撤销 | revoked=0、expires_at及快照已存 | 新补救的授权、有效期与撤销语义不成立 |
| 授权证据 | 仅token/checkouts摘要、ALLOW | 原完整授权与可信发行根缺生产持久来源 |
| 原请求/幂等 | complete的request_key/hash已存，create的响应幂等已存 | 无完整独立重验的完成请求/恢复授权 |
| 订单ID/结束状态 | orders=0，checkout为ready_for_complete、order=null | 不能自由生成新ID说是原订单 |
| 重启可信配置 | 测试监督者传trusted_context和token给新worker | 生产系统不能依赖实验进程交接 |
| 补偿权限 | 假PSP只有charge/query，未测到refund | 缺PSP和商户的真实退款权限/政策 |
| 审计归属 | 有attempt、模拟PSP与冻结HTTP、GET日志 | 缺真实主体的状态迁移/处置审批/通知链 |

上表否定的是**在已检固定来源中足以自动补救的证据**，不宣称真实商家一定没有这些资料。每个主题的文件、数据库主键/列、源码位置、原始值详见 `ANALYSIS.json`。

## 三种机制的比较及停止代价

**1. KEEP_QUERY_ONLY（继续查询，ABSORB）：** 目前无需修改已有授权/付款逻辑，可以保持“不重复扣款”的约束。工程成本最低，但已经付款而没有订单的问题会遗留，客服与对账人员未来需处理滞留工单，存在长期营运成本。支付源不能核验、状态不明或职责不清时，必须继续等待/上报，禁止自动重试扣款。本轮未执行任何新查询。

**2. ORDER_COMPLETION_CANDIDATE（受限补单，REFERENCE_ONLY）：** 从快照可以看出补单的材料“有一部分”，但不能把“重建一个订单对象”误判为安全补单。必须先取得可独立重验的真实支付最终性、签名/授权/确认来源、唯一订单身份、库存再校验、履约承诺和并发幂等规则，并明确谁能批准这个补救动作。工程复杂度中高，需独立状态机、事务交接、可重放失败与负向回归；任何一项关键事实缺失则STOP。**本轮没有创建订单。**

**3. COMPENSATION_OR_MANUAL_CANDIDATE（补偿/人工，REFERENCE_ONLY）：** 对无法安全补单或商品缺货的场景，人工对账+补偿政策可能必要。但必须由商家与PSP明确真实资金归属、可退款金额、退款权限、审批和用户通知；不能在模拟付款接口上构造“假退款成功”。人工处理的工程成本可控，却有持续客服成本；自动退款将显著提高权限、对账及重复补偿风险。**本轮没有退款。**

**什么也不做的代价：** 不会自动多扣款，但客户可能已被扣款且收不到订单；商家的服务承诺、履约、账务和投诉处理不能闭环。只有query-only而没有责任人不是最终业务方案。

## 唯一下一决策：MISSING_DURABLE_INPUT

目前存在足以**只读对账**的支付引用和确认快照，但不存在经本次验证可作为**自动恢复授权**的完整持久可信输入：原授权与信任根只能由实验交接提供；原生商家订单最终身份缺失；补单/退款的真实责任与政策未知。因此不冻结实现包、不自作自动恢复。

后续评估者可以冻结一个更小的“持久输入/责任边界”验收合同：先明确商户与PSP可被独立重验的支付最终性、原始用户意愿及撤销、生效订单ID或确定性身份、库存履约再校验、一次性补救权限、最终审计/通知责任；即使不能取得，也保留 `MISSING_DURABLE_INPUT` 作为有效结果。以上是**可证伪的要求**：任一来源、身份绑定、确认、库存或授权的负向例失败就停止自动补救；只有证据稳定可独立复算，才讨论编码与新的评测预算。

## 为什么不先做H56

H56 是未执行的披露完整性安全支线，尚没有明确目标商家的真实消费场景证明它比已发现的付款/订单断链更优先。它不解决“已付款但无订单”的商家交易责任，不能因此被当作H58的自动修复手段；若后续有第二消费者和真实需求，再由评估者按全局瓶颈重新排序。

## 规模与成本口径

本任务只增加本地标准库提取器和证据分析，**不增加支付业务代码**。只读工具工程成本低；未来若构建端到端安全补单，开发/测试/维护成本中高，并可能涉及真实商户与PSP审批；只读查询方案工程成本低但运营人工成本持续，补偿方案另需政策/授权与对账。没有生产交易量、退款率、工单量、客户预算，不能报具体人天或货币收益。这是受限工程判断，不是商业投资回报结论。
