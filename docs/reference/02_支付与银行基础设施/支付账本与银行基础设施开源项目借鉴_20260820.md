# 支付、账本与银行基础设施开源项目借鉴（2026-08-20）

> 目的：把支付编排、账本、核心银行、支付网络工具和金融互联标准放到当前 `agentic-payment-trust-lab` 架构中判断，不因为项目成熟或 Star 多就直接接入。
>
> 当前原则：**先借对象、状态机、失败语义、适配边界和证据结构，不先搬完整基础设施。**

## 1. 先给结论

按当前项目价值排序：

```text
第一梯队：直接值得研究
Hyperswitch
→ 支付编排 / PSP Adapter / attempt / routing / retry / reconciliation

Blnk
→ 双分录账本 / balance / inflight / reconciliation / economic truth

Moov
→ ACH / ISO8583 / Wire 等单一责任支付网络组件

第二梯队：边界参考
Apache Fineract
→ 完整银行核心、账户/贷款/会计边界

FDC3
→ 金融应用 Intent + Context + App Directory 互操作模型

第三梯队：辅助数据参考
OpenFinTech
→ PSP / payment method / currency 等主数据和统一标识
```

当前不纳入 Payment 参考主线：

```text
yfinance / akshare / baostock
→ 市场数据，不解决支付可信执行问题

freqtrade
→ 加密交易机器人，属于交易策略与自动交易，不是本项目的支付授权 / 执行 / 状态 / 证据问题
```

## 2. 与本项目主链怎么对应

当前项目主线：

```text
L1 授权
→ L2 Agent 意图
→ L3 订单 / 报价
→ L4 付款前检查
→ L5 支付执行
→ L6 支付状态
→ L7 履约
→ L8 补救 / 退款 / 争议
→ L9 证据归档
```

外部项目不是来替换这条主线，而是补充不同位置的真实工程参考：

| 外部项目 | 最相关阶段 | 对当前项目最有价值的东西 | 不应该误吸收什么 |
|---|---|---|---|
| Hyperswitch | L4-L8 | PSP 适配、统一错误、Payment Attempt、Routing、Retry、Reconciliation | 不把“路由成功”当成“授权可信”；不直接接真实 PSP |
| Blnk | L5-L9 | 双分录、在途交易、余额、对账、原交易与后续经济动作关系 | 不把账本写入等同于 Agent 已获得合法授权 |
| Moov | L5-L8 | ACH / ISO8583 / Wire 等外部支付轨道的解析、校验和单一责任组件边界 | 不因支持某支付网络就扩成美国支付平台 |
| Fineract | L5-L9 | 银行账户、贷款、会计、产品、交易的系统边界 | 当前不建设 Core Banking（核心银行） |
| FDC3 | L1-L4 / 跨应用 | Intent（意图）+ Context（上下文）+ 应用发现 + 来源元数据 | 不把桌面互操作协议当支付协议 |
| OpenFinTech | L3-L5 | PSP / 支付方式 / 币种等统一标识和 Master Data（主数据）思路 | 不把社区主数据当支付权威事实源 |

## 3. Hyperswitch：当前最高价值的支付执行层参考

官方项目：<https://github.com/juspay/hyperswitch>

### 3.1 为什么和我们有关

Hyperswitch 的核心不是 Agent Trust（智能体可信），而是成熟的 Payment Orchestration（支付编排）：

```text
统一内部支付语义
        ↓
Connector Adapter（通道适配）
        ↓
多个 PSP / Acquirer
        ↓
执行结果 / Error
        ↓
Routing / Retry / Recovery / Reconciliation
```

这和我们当前的：

```text
AP2 / ACP / UCP / x402 / PSP
        ↓
Adapter
        ↓
内部协议中立语义
        ↓
Gate / Execution / State / Recovery / Trace
```

在“外部差异如何被 Adapter 收敛”这个问题上高度相似。

### 3.2 最值得吸收的四点

#### A. Connector（连接器）与内部模型分开

Hyperswitch 为不同 PSP 保留各自 request / response 转换层，再映射成内部统一的 Router Data / Error 语义。

对我们的启发：

```text
外部 AP2 / ACP / PSP 对象
≠
项目内部事实模型

Adapter 负责映射
Trust Gate 只消费稳定的内部事实
```

这强化了我们当前“不让可信执行域直接依赖 AP2 / ACP / PSP 私有对象”的边界。

#### B. Payment Attempt（支付尝试）必须是一级对象

成熟支付系统不会把：

```text
用户要付款
= 某一次 PSP 调用
```

混成一个对象。

一次 Payment（支付意图/交易）可能对应多次 Attempt（执行尝试），这与我们现在处理：

```text
UNKNOWN / PENDING
→ 查询原交易
→ 是否允许 retry
→ 新 attempt 是否仍引用原 payment
```

高度相关。

后续若项目继续深化 S12 / S20，优先研究 Hyperswitch 的 Payment / Attempt / Connector Transaction 分层，而不是自己继续扩零散字段。

#### C. Retry（重试）不是简单“失败再调一次”

Hyperswitch 把 retry 与错误类型、路由、预算、connector 选择等放在独立机制里。

对应我们应继续坚持：

```text
Trust Fact：
原交易是谁？状态可靠吗？是否重复？
        ↓
Payment Domain：
等待 / 查询 / 换通道 / 重试 / 人工介入
```

也就是可信执行域提供“能不能证明这是安全重试候选”，支付域才决定“是否实际重试”。

#### D. Reconciliation（对账）给 L9 新视角

我们当前 L9 更强调 Trace / Replay（轨迹 / 回放）。Hyperswitch 提醒我们：

```text
执行证据完整
≠
经济结果最终一致
```

未来真实 Payment 项目要证明的可能是：

```text
Agent / Merchant / PSP 的运行记录
        ↓
外部结算 / 对账文件
        ↓
最终是否一致
```

这与 Blnk 的 Ledger / Reconciliation 可以形成一条新的长期参考线。

### 当前决策

**高优先参考，不接入代码。**

优先研究：

1. Payment / Attempt / Connector Transaction 对象关系；
2. Connector Adapter 的统一错误模型；
3. UNKNOWN / retry / connector failover 的状态处理；
4. Reconciliation 如何证明执行记录和经济结果一致。

## 4. Blnk：对“权威经济事实”非常有价值

官方项目：<https://github.com/blnkfinance/blnk>

### 4.1 它补的是我们当前相对弱的一层

当前项目已经比较擅长：

```text
Mandate
Order
Payment Request
Payment Attempt
Binding
Execution Fact
Authoritative Trace
```

但是还没有真正的：

```text
Ledger Entry（账本分录）
Balance（余额）
Settlement / Reconciliation（结算 / 对账）
```

所以我们当前 Authoritative Trace（权威轨迹）更准确说是：

> “这次执行过程发生了什么”的权威证据链。

它还不是：

> “钱的最终经济归属是什么”的账本真相。

Blnk 对这个边界非常有借鉴意义。

### 4.2 最值得吸收的结构

```text
Payment / Business Event
        ↓
Transaction
        ↓
Debit / Credit
        ↓
Balance
        ↓
Reconciliation
```

这能帮助我们以后严格区分：

```text
Execution Truth（执行事实）
→ PSP 返回 success / pending / failed

Ledger Truth（账本事实）
→ 哪个账户增加 / 减少多少

Settlement Truth（结算事实）
→ 外部机构最终是否真的结算一致
```

### 4.3 对 S10-S12 / L8-L9 的帮助

例如“支付成功但履约失败 → 全额退款”：

现在项目主要验证：

```text
原 payment 是否绑定
refund 是否关联原交易
证据是否可回放
```

账本视角会再增加：

```text
原始扣款分录
        ↓
退款分录
        ↓
是否形成正确反向经济影响
        ↓
余额 / 对账是否一致
```

这比只看 API 返回 `REFUNDED` 更接近真实金融系统。

### 当前决策

**高优先架构参考，暂不引入 Blnk 服务。**

短期只借：

- Double-entry（双分录）不可变经济记录思想；
- inflight（在途）与最终余额分离；
- 原交易与退款 / 冲正关系；
- Reconciliation（对账）作为最终事实验证层。

只有后续项目要验证“经济结果是否正确”，而不仅是“执行过程是否可信”时，再考虑做最小 Ledger Slice（账本切片）。

## 5. Moov：最值得借的是“一个金融组件只干一件事”

组织：<https://github.com/moov-io>

代表项目：

- ACH：<https://github.com/moov-io/ach>
- ISO8583：<https://github.com/moov-io/iso8583>
- Watchman：<https://github.com/moov-io/watchman>

### 5.1 对我们最大的架构启发

Moov 没有把“支付基础设施”做成一个巨大包，而是拆成：

```text
ACH parser / validator
ISO8583 codec
Wire
Routing number
Watchlist screening
...
```

每个组件只解决一种稳定金融协议或基础能力。

这和我们目前：

```text
Adapter
Binding
Identity
Policy
Status Observation
Idempotency
Trace
```

继续保持小组件边界的思路一致。

### 5.2 ACH / ISO8583 的具体借鉴

未来如果我们从“Agent Commerce 协议”继续往真实支付网络靠近，不应该：

```text
Agent
→ 直接理解 ACH / ISO8583 字段
```

而应该：

```text
ACH / ISO8583 / PSP
        ↓
Rail Adapter（支付轨道适配器）
        ↓
内部 Payment Fact
        ↓
Trust / Policy / Lifecycle
```

这继续强化“外部协议只负责事实表达和执行，不重定义项目核心判断”的原则。

### 5.3 Watchman 的位置

Watchman 更像未来的 External Compliance Fact Provider（外部合规事实提供器）：

```text
Merchant / Payee / Entity
        ↓
Watchman
        ↓
screening fact（筛查事实）
        ↓
Policy Gate
```

它不应该直接返回我们项目里的 `ALLOW / DENY`；应由支付域 Policy（策略）消费其事实。这与我们现在 P4 的 Trust Source（可信来源）边界一致。

### 当前决策

**高优先参考，按项目拆分吸收，不整体接 Moov 平台。**

## 6. Apache Fineract：用来校准“我们不是 Core Banking”

官方项目：<https://github.com/apache/fineract>

官网：<https://fineract.apache.org/>

Fineract 是完整的 Core Banking（核心银行）平台方向，覆盖客户、账户、储蓄、贷款、产品、会计等。

它对当前项目最主要的价值不是抄代码，而是校准边界：

```text
Agentic Payment Trust Lab
→ 授权 / 执行 / 状态 / 恢复 / 证据

Core Banking
→ 客户 / 账户 / 产品 / 利息 / 贷款 / 会计 / 总账
```

如果未来进入银行/信用卡真实场景，Fineract 可以帮助我们理解：

- Payment Action 最终落到什么账户/产品对象；
- 交易事件如何进入会计/账务体系；
- 业务生命周期与账务生命周期不是一回事。

### 当前决策

**中长期参考，不进入现阶段实现。**

## 7. FDC3：不是支付协议，但对 Agent 金融互操作有借鉴

官方项目：<https://github.com/finos/FDC3>

官网：<https://fdc3.finos.org/>

FDC3 解决的是金融桌面应用之间互操作，核心模型可以简化为：

```text
Intent（想做什么）
+
Context（围绕哪个对象做）
+
App Directory（谁能做）
+
Desktop Agent（负责发现 / 路由）
```

### 对 Payment 项目的可借鉴点

它进一步证明：

```text
Action / Intent
≠
Context / Facts
```

例如：

```text
Intent = ViewOrder / ExecutePayment（假设的支付动作）
Context = order / merchant / payment identity
```

两者需要明确绑定，且消息来源要可追踪。

这与当前项目一直强调的：

```text
Agent Action
+ 当前 Trust Context
+ Source Identity
+ Binding
```

有概念上的交叉。

### 但不要放大

FDC3 是金融桌面互操作标准，不是支付授权协议，也不提供支付最终状态、账本或结算真相。

### 当前决策

**中优先参考。** Payment 只吸收 Intent / Context 分离、应用能力发现、来源元数据等思想；更完整的 FDC3 研究更适合未来 Enterprise Agent / 金融工作台方向。

## 8. OpenFinTech：只适合做统一标识与主数据参考

官方组织：<https://github.com/openfintechio>

对当前项目可能有用的不是支付执行，而是：

```text
PSP
Payment Method
Currency
Organization
Location
```

等对象如何有统一 ID / Schema。

这与当前 S14 “商户别名 / 聚合商 / 实际收款主体不一致”存在潜在联系：

```text
外部显示名称
→ canonical provider / merchant / payment-method id
→ Binding / Policy
```

但社区 Master Data（主数据）不能自动成为本项目的 Authoritative Source（权威来源），仍然必须记录来源和可信等级。

### 当前决策

**低优先辅助参考。** 只有 Merchant / PSP Identity Normalization（商户 / 支付服务商身份归一化）成为真实瓶颈时再深入。

## 9. 综合吸收后的长期四层事实模型

这批项目真正给当前 Payment 项目的最大启发，不是“再增加 6 个依赖”，而是把支付事实分层看得更清楚：

```text
第一层：Intent / Authorization Truth
用户到底授权 Agent 做什么
AP2 / Policy / Binding

第二层：Execution Truth
实际向谁发起了哪次支付尝试，结果是什么
Hyperswitch / Moov 类参考

第三层：Ledger Truth
钱在账本上到底怎么变
Blnk 类参考

第四层：Settlement / Reconciliation Truth
内部记录和外部 PSP / 银行最终是否一致
Hyperswitch Reconciliation / Blnk Reconciliation
```

再叠加当前已有的：

```text
Fact Lineage（事实血缘）
+ Authoritative Trace（权威轨迹）
```

以后可以回答的不只是：

> “Agent 当时为什么允许付款？”

而是完整回答：

> “谁授权 → Agent 做了什么 → 发起了哪次 attempt → PSP 状态是什么 → 账本如何记 → 最终是否对账一致 → 出问题如何退款/恢复 → 全链路证据在哪。”

这条线值得保留为中长期 Payment 架构参考，但当前不因为概念完整就立即扩实现。
