# Agentic Payment Trust Lab 整体修正执行计划

> 日期：2026-07-29
> 状态：执行中
> 角色：后续项目修正的唯一主执行计划（SSOT）
> 原则：先能力、后案例；先验证、后重构；先 Agent 新增问题、后成熟支付补齐。

## 1. 为什么需要这份计划

项目此前已经完成 S01—S13、M1—M5、PayBench、AP2、Attack Overlay 等大量工作，但一度出现了研发主线漂移：

```text
发现异常
  ↓
增加 S / M / Case
  ↓
增加字段和规则
  ↓
增加 UI 入口
  ↓
继续解释这些案例
```

这种方式能让测试数量增长，却容易把项目变成“异常案例集合 + if/else 实验台”。

2026-07-28 至 2026-07-29 已完成第一轮架构重新定标。新的主线是：

```text
成熟支付交易底座
        +
Agent Trust Control Plane
        ↓
稳定领域能力
        ↓
S / PayBench / AP2 / Attack 只负责验证和攻击
        ↓
M5 / 回归体系负责裁判
```

因此，从本文件开始，后续研发不再以“下一个 S 编号是什么”为主线，而以“下一个真正缺失的能力是什么”为主线。

## 2. 项目第一性原理

本项目不是重新造支付系统，也不是堆协议 Demo。

核心问题只有一个：

> **当 Agent 代替人进入交易链路后，怎么证明它仍然在用户授权范围内，以正确身份、针对正确交易对象执行，并且交易过程中没有被不可信上下文静默改写，最终还能安全恢复和审计回放。**

对应两层：

```text
A. Mature Payment Foundation
   成熟支付交易底座

B. Agent Trust Control Plane
   Agent 新增可信控制面
```

测试和协议都在两层之外：

```text
S01—S13 / PayBench / AP2 / ACP / Attack
                ↓
          只是测试输入
                ↓
       M5 / Regression
                ↓
              裁判
```

## 3. 后续统一目标架构

```text
用户原始意图 User Intent
          ↓
委托授权 Delegated Authority
          ↓
Agent Identity / Executor
          ↓
交易对象 Transaction Object
Offer → Order → Payment Request
          ↓
┌────────────────────────────┐
│ Runtime Authorization Gate │
│       执行前授权闸门        │
└────────────────────────────┘
          ↓
ALLOW / DENY / CONFIRM / WAIT
          ↓
支付执行 Payment Execution
          ↓
支付状态 / 恢复 / 售后
          ↓
Evidence / Replay
```

`Runtime Authorization Gate` 不是新增第七个领域对象，也不是新增一个 P 阶段。它是 P1—P4 逐步提供输入、P5 记录结果的共同执行前控制点：

```text
Delegation / Authority
+ Continuous Binding
+ Agent Identity
+ Trust Source / Context
+ Policy
        ↓
Runtime Authorization Gate
        ↓
是否允许产生真实副作用
```

横向贯穿三条控制能力：

```text
Binding
授权、Agent、订单、支付对象持续绑定

Trust Source / Context
高可信事实不能被低可信来源静默覆盖，并保留任务上下文与前序动作

Runtime Authorization
每个真正产生副作用的 Agent Action 在执行前统一裁决
```

外部参考与开源实现见 [Agent 身份与运行时授权开源项目参考](../reference/Agent身份与运行时授权开源项目参考_20260729.md)。当前主要借鉴 AARM / Microsoft Agent Governance Toolkit 的执行前拦截与 Receipt 思路，SPIFFE/SPIRE 的 Workload Identity，Cedar/OPA 的 Policy Engine，以及 OpenFGA 的关系授权模型；暂不直接引入这些依赖。

成熟支付底座继续负责：

```text
Request / Transaction Identity
Idempotency
SUCCESS / FAILED / PENDING / UNKNOWN
Original Transaction Binding
Query / Retry / Refund / Dispute
Async / Reconciliation / Finality
```

## 4. 总体执行阶段

后续严格按照以下阶段推进。

```text
P0 架构重新定标                【完成】
        ↓
P1 Delegated Authority v1      【完成】
        ↓
P2 连续 Binding 到 Payment     【完成】
        ↓
P3 Agent Identity              【完成】
        ↓
P4 Trust Source / Untrusted Context【完成】
        ↓
P5 Evidence / Replay           【完成】
        ↓
P6 成熟支付底座补齐            【完成】
        ↓
P7 UI / 文档重新组织           【完成】
        ↓
P8-A x402 离线外部验证         【完成】
        ├── P8-B x402 测试网   【可选授权分支】
        ↓
P9 WebShop 外部商城接入       【当前：P9-A1】
```

主线阶段必须通过自己的 Gate，才能进入下一阶段。P8-B 是独立外部验证分支，不阻塞 P9；P9 的外部网络权限按任务细分，P9-A1 只允许获取官方 WebShop Git 仓库。

其中 `Runtime Authorization Gate` 是横切主线，不单独编号：

```text
P1 提供 Delegated Authority / Confirmation Policy
P2 提供 Transaction / Payment Continuous Binding
P3 提供 Agent / Executor Identity
P4 提供 Context / Trust Source / Policy Input
        ↓
Runtime Authorization Gate 具备完整输入
        ↓
P5 把每次裁决固化成 Receipt / Replay
```

P1—P8-A 已按 Gate 依次完成；当前推荐进入 P9，本地环境仍必须继续消费既有 Runtime Authorization Gate，而不是另建一套商城专用规则。

# P2 连续 Binding 到 Payment

## 9. P2 要解决什么

P1 只做到 Authority → Order。

P2 要把链补到真正的支付执行：

```text
Delegated Authority
        ↓
Order
        ↓
Payment Request
        ↓
Payment Execution
```

目标不是证明两个 Hash 相同，而是证明：

> 最终执行的 Payment，确实来自用户授权允许、且用户确认过的交易对象。

## 10. P2 最小能力

预计补充：

```text
PaymentExecutionRecord
  + authority_ref
  + agent_ref
  + transaction_object_ref
```

并明确：

```text
request_id != payment_id
order_id != payment_id
```

Binding 应能回答：

```text
这笔 Payment 对应哪个 Order？
这个 Order 对应哪个 Authority？
执行金额 / currency / payee 是否仍一致？
```

## 11. P2 Gate

```text
[x] Order → Payment Request 绑定明确
[x] Payment Request → Payment Execution 绑定明确
[x] 错绑 payment / order 会被识别
[x] 关键字段变化不会静默执行
[x] 原有 UNKNOWN / Idempotency 恢复逻辑不被破坏
[x] 专项 + 全量回归通过
```

# P3 Agent Identity

## 12. P3 要解决什么

当前能力基本是：

```text
expected_agent_id == request.agent_id
```

这只说明两个字符串一致。

P3 目标不是立即建设生产 PKI，而是先形成明确的身份可信等级：

```text
DECLARED
  只声明自己是谁

BOUND
  当前执行身份与授权引用可绑定

VERIFIED
  有额外 credential / attestation 等证据
```

项目当前预计只真正实现到 `DECLARED / BOUND`，`VERIFIED` 先保留接口。

## 13. P3 Gate

```text
[ ] 声明身份与验证身份语义分开
[ ] Agent 被替换时不能继续复用原授权
[ ] 不把字符串相等描述成真实身份认证
[ ] 至少一个现有场景真实消费身份事实
[ ] 负向测试 + 全量回归通过
```

# P4 Trust Source / Untrusted Context

## 14. P4 要解决什么

当前 Attack Overlay 已证明固定测试字段不能直接改写可信输入，但还没有形成稳定的“事实来源等级”。

P4 要建立：

```text
USER_CONFIRMED
SYSTEM_POLICY
AGENT_DECLARED
AGENT_INFERRED
MERCHANT_PROVIDED
PROTOCOL_VERIFIED
PAYMENT_PROVIDER_OBSERVED
EXTERNAL_TOOL_UNTRUSTED
WEB_UNTRUSTED
LLM_GENERATED
```

核心不变量：

> **低可信来源不能直接覆盖高可信事实。**

例如：

```text
网页文字
  X 不能修改用户授权金额

LLM 推断
  X 不能修改已验证 payee

支付机构状态观察
  可以更新 Payment Status
  X 不能修改 Delegated Authority
```

## 15. P4 Gate

```text
[ ] 核心事实具有 source_type
[ ] 定义最小覆盖规则
[ ] Attack Overlay 从“攻击案例集合”升级为 Trust Source 规则压力测试
[ ] 至少包含允许覆盖 + 禁止覆盖两类测试
[ ] M5 能识别 forbidden side effect
```

# P6 成熟支付底座补齐

## 18. 为什么放到 P6

这些能力非常重要，但大多不是 Agent 新问题。

因此前面先把 Agent Control Plane 主线立住，再补成熟支付底座的薄弱环节。

重点三项：

### 18.1 Original Transaction Binding

统一：

```text
Query
Refund
Reversal
Dispute
```

与原交易的绑定语义。

### 18.2 最终性分层

从现在的：

```text
SUCCESS / FAILED / PENDING / UNKNOWN
```

逐步增加对：

```text
请求受理
业务成功
异步通知
查询确认
对账 / 清算确认
```

的区别。

### 18.3 Async / Query / Reconciliation

建立最小实验，不直接建设真实支付网络。

## 19. P6 Gate

```text
[ ] UNKNOWN 仍优先查询原交易
[ ] 后续动作统一绑定 Original Transaction
[ ] 不把 HTTP / API 成功等同业务成功
[ ] 同步 / 异步 / 查询状态冲突有明确处理
[ ] 继续保持成熟支付能力与 Agent 新增能力的叙事分离
```

# P9 WebShop 外部商城接入

## 22A. 为什么复用外部商城而不是自建 MiniShop

P8-A 已证明 x402 合成对象能够安全映射到协议中立事实，但当前项目仍缺少一个让 Agent 真正执行多步骤购物任务的环境。Princeton WebShop 已经提供商品、搜索、页面、商品属性选择、购买动作和任务奖励，因此不再优先重建商城主体。

```text
WebShop
= 商品 / 搜索 / 页面 / 选择 / Buy Now / reward

本项目
= Commerce Adapter
+ Runtime Authorization Gate
+ Payment / Fulfillment Sidecar
+ M5 状态差异评测
```

集成原则：不把 P1—P6 写进第三方源码；优先使用 wrapper 在 `click[buy now]` 前拦截购买意图。WebShop 上游代码和数据放入 Git 忽略目录，主仓只保留版本清单、检查脚本、适配器和评测结果。

推荐顺序：

```text
P9-A1 上游固定与接入缝隙预检【当前】
  官方仓库 / 固定提交 / 许可证 / 文本环境 / Buy Now接点
        ↓
P9-A2 独立环境 + small数据 smoke test
  Python 3.8.13 / 1000商品 / reset-search-click
        ↓
P9-B Commerce Adapter + 购买动作拦截
  instruction / 商品 / 选项 / 价格 → 内部中立对象
        ↓
P9-C Payment / Fulfillment Sidecar
  SUCCESS / FAILED / PENDING / UNKNOWN / 履约
        ↓
P9-D 外部任务对比评测
        ↓
P10 UCP或ACP最小对象适配
        ↓
P11 数据最小化与隐私披露
        ↓
P12 银行业务沙箱最小切片
```
