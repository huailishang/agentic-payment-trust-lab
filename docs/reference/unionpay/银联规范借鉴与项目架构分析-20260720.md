# 银联规范借鉴与项目架构分析（2026-07-20）

## 1. 文档目的

本文记录两份中国银联规范对主仓库“一仓两域”架构的学习价值，并明确支付域与 `agentic_payment_experiment.trusted_execution` 的职责边界。

参考资料：

1. 《中国银联平台标准通用技术规范（Q/CUP 083-2024）》
2. 《中国银联全渠道支付平台指引（JSON版）产品卷·签约支付 H5 模式（Q/CUP-SC 071.4.4-2024.08）》

这些资料仅作为现实金融基础设施的设计参考，不声称实现银联生产接口，也不将实验模型描述为银联官方实现。公开仓库不再分发两份 PDF 原文件，只在 `docs/reference/unionpay/source/` 保留文档名称、SHA-256 和来源说明；本地原件统一保存在 Git 忽略目录 `local_sources/third_party/unionpay/`。项目文档仍以自己的提炼、模型和实验结论为主，不复制规范正文、接口表格或大段原文。

## 2. 核心结论

两份规范最值得借鉴的不是具体接口字段，而是以下可信执行思想：

```text
用户意图
  -> 形成结构化意图 / 授权对象
  -> 绑定商户、商品、金额、次数、有效期等约束
  -> 对确定对象签名并形成唯一标识
  -> 后续交易显式引用原对象
  -> 区分请求标识与交易标识
  -> 支付结果允许 SUCCESS / PROCESSING / 未知（UNKNOWN） / FAILURE 等状态
  -> 未知（UNKNOWN）优先查询原交易，而不是直接重新支付
  -> 撤销、退款、冲正等动作显式绑定原交易
  -> 同步应答、异步通知、查询、对账共同形成结果确认和证据链
```

这与本项目原有方向一致，但需要把原来较分散的哈希（Hash）、签名（Signature）、幂等（Idempotency）、StateMachine、审计（Audit）教学点，重新串成一条完整的可信执行主线。

## 3. 对意图 / Mandate 的修正

原项目使用 `Mandate -> Order -> PaymentRequest` 表达用户授权、订单和支付请求。

参考真实智能体（Agent）支付意图设计后，Mandate 应进一步明确为一个“可验证授权对象”，而不是一句自然语言：

```text
Raw User 意图
  -> 智能体 Interpretation
  -> Structured Constraints
  -> User / Trusted Confirmation
  -> Canonical 授权 Object
  -> 哈希 / 签名
  -> 授权 / 意图 ID
```

候选中立字段包括：

```text
authorization_id / intent_id
agent_id
subject_id
merchant_scope
category_scope
item_scope
amount_limit
currency
max_count
valid_from
valid_until
autonomy_level
confirmation_policy
version
```

这些是本项目的协议中立实验语义，不复制任何单一协议字段定义。

## 4. 请求标识与交易标识必须分开

现实接口中，请求流水用于识别一次接口（API）请求，但不必然等于业务交易主键。

本项目后续明确区分：

```text
request_id
  一次调用或投递尝试

transaction_id / payment_id
  一笔业务金融动作

idempotency_key
  判断多个请求是否属于“同一个业务意图”的唯一执行边界

original_transaction_ref
  撤销、退款、冲正、查询等后续动作绑定的原交易
```

因此 TE-06 不能简化为“见过 request_id 就拒绝”，而要验证业务动作身份、请求尝试和幂等边界之间的关系。

## 5. 未知（UNKNOWN）必须成为一等状态

支付执行可能出现：

```text
SUCCESS
PROCESSING
未知（UNKNOWN）
FAILURE
```

未知（UNKNOWN）的含义是“当前无法确认结果”，不等于失败（FAILED）。

安全恢复链应为：

```text
支付请求 Sent
  -> Response Lost / Timeout
  -> 未知（UNKNOWN）
  -> Query Original Transaction
  -> SUCCESS / PROCESSING / 未知（UNKNOWN） / FAILURE
  -> 再决定继续、等待、人工处理或进入安全重试候选
```

禁止：

```text
未知（UNKNOWN）
  -> 直接创建第二笔支付
```

这将成为 TE-08 和界面（UI）教学的重要现实参考。

## 6. 同步应答、异步通知与最终性分层

项目后续需要明确区分：

```text
HTTP Success
  通讯成功

Request Accepted
  请求已被接收

Processing
  正在处理

Business Success
  业务交易完成

Settlement / Reconciliation
  清算或对账确认

Legal Finality
  法律和责任意义上的最终状态
```

因此 UI-07 不再只解释“链上确认与数据库提交不同”，还应加入接口（API）同步应答、异步结果和状态查询的差异。

## 7. 签名实验的现实参考

真实金融接口（API）的签名对象通常不是只对业务 body 做摘要，而是把协议版本、调用方、接口类型、请求标识和业务体共同纳入确定性签名输入。

本项目近期仍使用测试密钥和本地实验，但 TE-02 / TE-03 应学习以下结构：

```text
Canonical Request Metadata
+ Canonical Body
  -> Deterministic Signing Payload
  -> Digest
  -> 签名
  -> Key / Certificate Reference
  -> Verify Before Trusted Processing
```

边界保持：

```text
签名 Valid
!= User 意图 Correct
!= 授权 Scope Correct
!= Business Legal
```

证书生命周期、CA、硬件密码设备和生产密钥管理属于后期学习，不在当前阶段建设。

## 8. 支付域与可信执行域的功能边界

两个域会看到相似对象，但职责不同。

| 能力 | 支付域 | 可信执行域 |
|---|---|---|
| 用户意图 / Mandate | 定义业务语义、确认策略、自主度和场景 | 验证对象完整性、版本、签署和绑定关系 |
| 订单 | 定义商品、价格、商户、履约和变化后的业务处理 | 提供规范化摘要、哈希、版本绑定验证 |
| 付款前检查 | 决定允许（ALLOW） / 拒绝（DENY） / 需要确认（CONFIRMATION_REQUIRED） / 无法判定（INDETERMINATE） | 返回约束是否满足、证据是否完整等验证事实 |
| 幂等 | 决定支付业务何时允许继续或查询 | 提供请求、交易、幂等边界和唯一执行机制 |
| 未知（UNKNOWN）恢复 | 定义支付业务的查询、等待、重试候选和用户体验 | 提供通用状态验证、观察绑定和重复执行防护 |
| 退款 / 撤销 / 冲正 | 定义支付生命周期和售后业务规则 | 验证后续动作是否正确绑定原交易、是否重复 |
| 状态机 | 定义支付业务状态及业务允许路径 | 提供通用确定性迁移验证器，不定义支付业务状态含义 |
| 审计证据 | 定义需要记录哪些支付业务事实 | 提供事件摘要、签名、哈希 Chain、回放完整性能力 |
| 协议适配器（Adapter） | AP2 / ACP / UCP / x402 / 支付接口（API）映射 | 原则上不做业务协议适配器（Adapter），只消费协议中立对象 |
| 界面（UI） | 展示支付生命周期、异常位置和业务恢复 | 解释为什么需要某种可信机制、机制能证明什么 |

## 9. 允许的复用方向

唯一推荐的依赖方向：

```text
支付域
  -> 调用 agentic_payment_experiment.trusted_execution 的稳定组件
  -> 获得验证事实
  -> 自己决定业务动作
```

例如：

```text
支付项目：
订单变化后是否必须重新确认？

可信项目：
只返回：authorized_order_hash 与 final_order 是否一致，
哪些绑定字段发生变化，证据是否足够。

支付项目：
根据自身业务规则决定需要确认（CONFIRMATION_REQUIRED）或拒绝（DENY）。
```

禁止反向依赖：

```text
可信执行域
  X 导入 AP2 / ACP / UCP 业务模型
  X 定义支付生命周期 L1-L9 的业务裁决
  X 决定退款、争议、确认等业务动作
```

## 10. 后续项目主线

本项目教学与实验主线调整为：

```text
用户表达意图
  -> 形成结构化授权对象
  -> 验证对象 / 身份 / 授权关系
  -> 绑定具体订单和支付请求
  -> 区分 Request 身份 / Transaction 身份
  -> 幂等执行
  -> 状态确认
  -> 未知（UNKNOWN）查询与恢复
  -> 后续动作绑定 Original Transaction
  -> 审计证据
  -> Replay / 争议
```

底层实验仍按最小组件逐步实现，不因参考真实规范而提前建设完整支付安全平台。
