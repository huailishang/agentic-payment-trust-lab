## 1. 可确认的外部事实

Apify 的实际接入说明表明，机器资源支付与固定价商品支付不同：Actor 运行时间、抓取量、计算量等会让最终成本在执行前不可完全确定。

Apify 当前同时支持两类 x402 计费语义：

```text
exact
→ 预先确定固定金额
→ 对未知最终成本的任务并不自然
→ Apify 通过预付额度 + 实际消耗 + 退回未使用余额补足商业流程

upto
→ Client 只授权“本次最多可收多少”
→ Resource 执行后按实际使用量确定最终金额
→ actual charge 必须不超过 authorized cap
```

x402 v2 官方规范进一步确认：

- 协议包含 `exact`、`upto`、`batch-settlement` 等 scheme；
- `upto` 面向最终成本执行后才确定的 usage-based pricing（按量计费）；
- `authorization / upfront / escrow` 表达不同的执行与结算先后关系；
- `settlement_pending` 是非终态，交易可能已经广播但尚未确认，调用方应先 reconciliation（对账 / 查询）再决定是否重试；
- client-side budget management（客户端预算管理）明确不属于 x402 核心协议负责的范围。

因此，x402 能表达“怎么请求付款、怎么验证/结算”，但不会自动完成 Agent 任务级总预算、服务质量、退款责任、跨调用累计消费等完整商业治理。

## 2. 对当前项目的影响

### 2.1 已经覆盖的部分

当前项目已有能力已经覆盖其中相当一部分失败模式：

```text
UNKNOWN / PENDING
→ Payment Finality / Payment Recovery
→ 先查询原支付，再决定重试

重复调用 / 重复扣款
→ Idempotency / Original Transaction / Replay

支付成功但资源未交付
→ Payment State 与 Fulfillment 分离

后续退款 / 争议 / 恢复
→ Remediation + Original Transaction Binding

状态冲突
→ Payment Status Conflict + Evidence / Replay
```

因此不需要新增“x402 状态管理器”或第二套支付恢复体系。

### 2.2 当前真正缺少的部分

项目对机器资源支付目前仍主要停留在字段和路线设计，缺少一个被真实外部实践证明有必要的可执行 Contract：

> **Metering → Settlement → Fulfillment（计量 → 结算 → 履约）能否形成一条可验证经济闭环。**

最小需要回答：

```text
Agent 被授权最多花多少？
        ↓
资源实际使用了多少？
        ↓
计费规则是什么？
        ↓
应该扣多少？
        ↓
实际结算多少？
        ↓
API / 数据 / 算力是否真实交付？
        ↓
失败、少交付或状态未知时如何退款 / 恢复？
        ↓
全过程能否从 Evidence 复核？
```

## 3. 架构吸收：不新增第 7 个领域对象

继续保持现有 6 个核心对象，不新增独立 Metering Domain。

机器资源支付只在已有对象上补充被验证需要的经济事实：

```text
Transaction Object
├─ pricing_unit
├─ authorized_cap
├─ quote / pricing_rule_ref
├─ quote_expiry
└─ service_scope

Payment Execution
├─ actual_charge
├─ settlement_status
├─ payment_ref
└─ retry / idempotency identity

Fulfillment / External Fact
├─ usage_quantity
├─ usage_evidence_ref
├─ service_result
└─ service_receipt_ref

Evidence / Fact Lineage
└─ Authorization → Usage → Charge → Settlement → Delivery → Recovery
```

字段只有在后续真实 Contract、Checker 和 Evidence 消费时才进入代码；当前不因参考材料预先扩充模型。

## 4. 新增验收维度：Commercial Closure

后续机器资源支付实验统一增加纵向验收维度：

### Commercial Closure（商业闭环）

至少验证以下不变量：

| 不变量 | 机械判定 |
|---|---|
| 授权上限 | `actual_charge <= authorized_cap` |
| 计量可证 | 实际扣费必须存在可引用的 usage / pricing evidence |
| 金额一致 | usage × pricing rule 与 expected charge / settlement 可解释一致 |
| 状态最终性 | `settlement_pending / UNKNOWN` 不得被当作 terminal failure 后盲目重付 |
| 单次消费边界 | 同一 authorization / request 不得被重复结算产生双扣 |
| 服务交付 | Payment Success 不得自动等于 Service Success |
| 经济补救 | 未交付、少交付或失败时必须能进入 refund / dispute / recovery |
| 可回放 | 授权、用量、扣款、结算、交付、补救之间必须有稳定引用和来源 |

第一轮优先用离线 / 模拟 fixture，不接真实资金、钱包、主网或生产凭据。

## 5. 对开发顺序的影响

本资料**不改变当前 B-04 / H-11**。

建议顺序：

```text
当前 H-11
→ 先得到真实 Autonomous pre-Buy-Now Trace
→ 再扩多任务验证 Agent 行为不是单 Case 硬编码
→ 再把机器资源支付作为独立纵向实验
→ Metering → Settlement → Fulfillment
→ 之后才评估是否需要 x402 testnet / wallet / real facilitator
```

单纯“把一笔测试币转出去”对当前项目的信息增益，低于验证按量计费商业闭环。

## 6. 一句话吸收结论

> Apify 的 x402 实践没有要求项目改用某个协议，而是把机器资源支付的真实缺口从“付款是否成功”推进到了“授权额度、实际用量、实际扣款、服务交付和失败补救是否能共同闭环”；该问题应作为现有 Trust Control + Payment Lifecycle 的一个新增纵向验收维度，而不是新增顶层架构。
