# 协议与网络能力映射

## 1. 先分层，再比较

| 对象 | 主要层级 | 当前状态 | 第一轮验证重点 | 不能由此推出 |
|---|---|---|---|---|
| AP2 | 用户委托、支付意图、支付授权 | 开源规范和样例 | 委托（Mandate）、金额/商户绑定、人是否在环、签名与重放 | 不负责完整商品和履约生命周期 |
| UCP | 商品发现、结账、订单、履约、售后 | 开源规范 | 商务对象如何引用支付能力；订单变化如何回传 | 不等同支付网络或结算资产 |
| ACP | 买方智能体（Buyer Agent）—商户结账—支付提供方 | 测试阶段（Beta）的开放标准 | 结账会话、支付处理器、订单与认证 | Beta状态不代表生产稳定性或全球适用性 |
| x402 | HTTP/接口（API）资源付费与结算 | 开源标准；链上实现较成熟 | 402挑战、支付要求、验证、幂等、按次/批量结算 | 不代表消费者信用卡交易或监管认可路线 |
| MPP | 机器支付请求、凭证与多轨结算 | 2026-03上线，仍处早期 | 双方支付、共享支付凭证、链上与法币结算边界、重试和收据 | 交易笔数不证明持续采用，也不能替代任务级委托和消费者保护 |
| 维萨智能商务（Visa Intelligent Commerce） | 卡网络身份、令牌（Token）、指令、授权控制和信号 | 产品部署中、提供沙箱/示例 | 智能体专属令牌（Token）、用户指令与VisaNet授权匹配、争议信号 | 公开能力说明不是完整生产规则 |
| 万事达卡智能体支付（Mastercard Agent Pay） | 卡网络智能体识别、智能体令牌（Agentic Token）与交易可见性 | 项目与受控试点 | 注册智能体、意图、权限、令牌（Token）和责任追踪 | 不能据新闻稿推断所有接口和责任规则 |

## 2. “协议”、支付工具和结算轨道不是同一层

| 对象类别 | 作用 | 示例 | 与其他层的关系 |
|---|---|---|---|
| 智能体与商务协议 | 表达用户委托、智能体身份、商品、订单、确认和支付请求 | AP2、ACP、UCP | 说明“应不应该发起、发起什么”，通常不直接完成资金结算 |
| HTTP/API付费协议 | 在资源请求中表达价格、付款要求、验证和结算交互 | x402 | 同时连接应用协议与特定支付轨道，当前实现多与链上稳定币结合，但两者不是同义词 |
| 支付工具与资金来源 | 指定用户使用什么账户、信用或余额付款 | 信用卡、银行账户、钱包余额、数字人民币钱包、稳定币钱包 | 可能通过不同网络执行；信用卡本身不是结算资产 |
| 支付轨道或网络 | 传输、授权、清算或确认支付指令 | 卡组织网络、银行账户转账系统、数字人民币系统、公链或联盟链 | 决定参与机构、状态确认和异常处置方式 |
| 结算资产 | 最终用什么货币性资产清偿义务 | 商业银行货币、央行货币、数字人民币、稳定币、代币化存款 | 决定信用来源、赎回基础、法律终局性和流动性风险 |
| 治理与责任机制 | 决定谁能冻结、撤销、升级、恢复和处理争议 | 央行、银行、卡组织、稳定币发行方、链上治理与适用法律 | 不能仅从技术架构推断法律责任和消费者保护 |

因此，“AP2还是数字人民币”“AP2还是稳定币”不是同一层的二选一。更准确的组合方式是：智能体依据 AP2 等委托 / 商务协议形成支付请求，再选择信用卡、数字人民币钱包、稳定币钱包或银行账户等支付工具，经相应网络执行，最后落到具体 Settlement Asset（结算资产）及其 Finality（最终性）机制。

长期统一原则：**Agent 支付控制解决“这笔钱该不该花”；支付轨道解决“钱怎么走”；结算资产解决“最终收到的到底是什么钱、由谁保证、什么时候真正结束”。三者不得混为一层。** 同理，x402 是机器资源支付交互协议，不等于稳定币、USDC 或区块链本身。

## 3. 协议中立对象

| 中立对象 | 最小字段 | 主要验证问题 |
|---|---|---|
| 智能体身份 | agent_id、provider、credential_ref、status | 谁代表用户行动，是否可撤销和追踪 |
| 用户委托 | mandate_id、scope、budget、merchant/category、expiry、count | 用户究竟授权了什么 |
| 商务订单 | cart/order_id、items、price、merchant、fulfilment_terms | 最终购买是否仍符合原意 |
| 支付意图 | payment_id、amount、currency、payee、mandate_ref | 支付是否与委托和订单绑定 |
| 执行结果 | request_id、decision、reason、rule_version、timestamp | 为什么执行、拒绝或要求确认 |
| 结算与争议 | rail、finality、refund/dispute_ref、evidence_refs | 钱是否最终转移，失败后如何恢复和分责 |

## 4. 两类交易任务不是两套互斥支付系统

| 任务形态 | 判断依据 | 协议中立补充字段 | 主要风险 |
|---|---|---|---|
| 人类代理型交易 | 智能体代表人完成商品购买、预订或订阅管理 | order_version、fulfilment_terms、confirmation_policy、consumer_dispute_ref | 订单变化、诱导购买、越权订阅、退款和责任不清 |
| 机器资源型交易 | 软件为完成任务购买接口（API）、数据或算力 | pricing_unit、quantity、quote_expiry、spent/pending_amount、window_count、service_receipt_ref | 高频累计超支、报价漂移、重试扣款、付费未交付和质量争议 |

分类依据是委托关系与交易经济性，不只是金额大小。同一用户任务可能先发生多笔机器资源支付，再完成一笔面向商户的人类代理型交易；两类交易必须共享任务、委托、预算和证据引用，但可以使用不同支付轨道。

### 4.1 后续：跨支付轨道（Cross-Rail Payment）验证

当前不把稳定币、银行卡、账户体系或代币化存款设为项目唯一技术路线。后续 Cross-Rail 不能只理解成替换一个 `rail` 字段，而要拆成两层：**Shared Trust Invariants（共享信任不变量）**与 **Rail / Asset-specific Finality（轨道 / 结算资产特定最终性）**。

第一层保持统一：同一个 Task / Mandate（任务 / 委托）无论经机器资源支付还是商户支付，都必须共享身份、授权、总预算、订单 / 支付绑定、人工确认、幂等和证据规则。

```text
Task / Mandate
    ↓
统一预算与授权边界
    ├─ Machine Resource Payment -> x402 -> 某支付轨道 / 结算资产
    └─ Merchant Payment         -> card / account -> 某支付轨道 / 结算资产
    ↓
Shared Trust Control
Identity -> Authority -> Binding -> Runtime Gate
-> Idempotency -> Evidence / Replay
```

第二层不强求完全一致：不同支付轨道和结算资产的 `Finality / Query / Redemption / Recovery` 可能具有不同语义。`amount=100`、`currency=USD` 只表达记账金额和单位，不能自动推出 100 美元银行存款、100 USDC、100 USDT、不同链上的同名稳定币或代币化存款具有相同的兑付主体、平价保障、最终结算锚和恢复机制。

```text
Shared Trust Control
        ↓
Rail Adapter
        ↓
Payment Rail / Network
        ↓
Settlement Asset
        ↓
Rail / Asset-specific Finality
        ↓
Query / Redemption / Recovery / Evidence
```

因此 Cross-Rail 首要验证仍是：**Agent 切换支付方式、轨道或结算资产后，是否仍然无法绕过用户委托和可信执行控制。** 当该方向未来升为真实瓶颈时，再冻结最小结算语义 Contract；当前不因外部研究立即给 Payment 对象增加大量字段，也不接真实主网、真实资金或生产凭证。

机器资源支付还需额外关注传统单笔支付不突出的累计风险：`pricing_unit`、`quantity`、`quote_expiry`、`spent_amount`、`pending_amount`、`window_count`、`retry_count`、`service_receipt_ref`。重点验证“小额 × 高频 × 自动重试”是否造成累计超支、重复扣款或付费未交付。

BIS 2026 对稳定币、代币化存款与央行结算锚的比较用于校准这一未来边界，不改变当前 B-12 / H-18 主线。详见 [德科斯“稳定币与代币化存款”对项目的影响分析](../reference/05_产业与机构资料/bis/德科斯_稳定币与代币化存款_项目影响分析_20260908.md)。

### 4.1.1 三种现实路线只校准“下面半截”

2026-09 补充三个正式 / 官方样本：CBMT、韩国 Project Hangang、俄罗斯数字卢布。它们分别对应“多银行存款代币 + Bridge”“批发 CBDC + 商业银行存款代币”“零售 CBDC 平台”三种不同结构，但对本项目形成同一组约束：

| 样本 | 对项目真正有用的事实 | 映射结论 |
|---|---|---|
| CBMT | 各银行分别发行本行存款代币，通过 Bridge 做跨银行 / 跨网络互操作；官方沙盒还测试带 Agent 身份与人工确认的跨境 Agentic B2B Payment | `currency` 相同不等于发行主体 / 恢复语义相同；Bridge 不替代 Authority / Binding |
| Project Hangang | 客户侧使用商业银行存款代币，底层以央行数字货币支撑机构间结算 | Payment Instrument 与 Final Settlement Anchor 可以不是同一层 |
| 数字卢布 | 支付平台自身存在额度、准入和交易规则 | `Trust Decision=ALLOW` 不等于 Rail 一定接受，更不等于 Settlement Final |

因此未来 Cross-Rail 还要保持两条职责分离：

```text
Agent Trust Policy
负责：用户是否授权、是否越界、是否需要确认

Rail / Wallet / Settlement Policy
负责：具体支付工具和网络是否允许执行、何时最终完成、异常如何恢复
```

不把 Rail 规则塞进 Agent Validator，也不让 Rail“能支付”反向证明 Agent“有权支付”。完整分析见 [数字货币三路线与可信基础设施：项目影响分析](../reference/02_支付与银行基础设施/数字货币三路线与可信基础设施_项目影响分析_20260908.md)。

### 4.2 Machine Resource Commercial Closure（机器资源支付商业闭环）

Apify 的 x402 实践与 x402 v2 的 `upto` / `batch-settlement` 等 scheme 说明，机器资源支付需要把“支付成功”继续向下拆解为：

```text
authorized_cap
    ↓
usage_quantity + pricing rule
    ↓
expected_charge
    ↓
actual_charge
    ↓
settlement status
    ↓
service result
    ↓
refund / recovery
```

首轮验收至少要求：

1. `actual_charge <= authorized_cap`；
2. 实际扣费存在可引用的 usage / pricing evidence；
3. `settlement_pending / UNKNOWN` 不得直接触发第二次扣款；
4. 同一 authorization / request 不能产生重复成功结算；
5. Payment Success 与 Service Success 分离；
6. 未交付、少交付或失败可以进入退款 / 恢复；
7. Authorization → Usage → Charge → Settlement → Delivery 必须可回放。

这些是现有 Payment Lifecycle + Trust Control 的纵向验收条件，不新增独立 Metering Domain。详细参考见 [Apify x402 按量计费与商业闭环：项目影响分析](../reference/01_支付协议/x402_Apify按量计费与商业闭环_项目影响分析_20260902.md)。

### 4.3 Cross-Protocol Invariance（跨协议判断不变量）

协议兼容在本项目中先收敛成 **Semantic Interoperability（语义互操作）**，而不是直接实现网络级互联互通：

```text
冻结同一业务 Case
    ↓
不同协议表达
    ↓
Adapter
    ↓
Canonical Facts diff
    ↓
Trust Decision diff
```

等价事实应保持 Authority / Identity / Transaction / Decision 的核心语义不变；无法等价表达时必须显式暴露 capability gap（能力缺口），不得由 Adapter 自行补猜。该测试用于发现“协议差异是否污染核心业务规则”，而不是比较哪一个协议更先进。

详细参考见 [陆磊“协议与技术标准竞争 / 兼容”观点：项目影响分析](../reference/05_产业与机构资料/pboc/陆磊_协议标准竞争与兼容_项目影响分析_20260902.md)。

## 5. 第一轮适配顺序

1. AP2 → 中立委托与支付意图：验证现有模型是否缺身份、签名、确认状态和订单绑定。
2. ACP或UCP → 中立订单：验证价格、库存、履约变化是否会使原委托失效。
3. 同一场景跨协议回放：只比较对象和风险语义，不比较营销宣传。
4. x402 单独作为机器/接口（API）付费对照，不与卡支付强行统一。
5. MPP只做对象与状态机对照；没有新的可证伪问题时不增加适配器（Adapter）。
6. 维萨（Visa）/万事达卡（Mastercard）暂以官方能力矩阵做差距分析；具备明确沙箱目标后再接入。

## 6. AP2 v0.2.0 最小对象映射

M4 固定 AP2 `v0.2.0 / b4587ac`，只验证人在场（HP）和人不在场（HNP）两个最小流程。

```text
AP2 IntentMandate
    -> 用户授权范围 / 是否要求实时确认

AP2 CartMandate
    -> 最终商户 / PaymentRequest / 总金额

AP2 PaymentMandate
    -> PaymentRequest 绑定 / 支付金额 / 用户授权证据

        ↓ Adapter

IntentMandate + TransactionRequest
        ↓
现有 Validator
```

关键绑定：

```text
CartMandate.payment_request.details.id
    = PaymentMandate.payment_details_id
    = PaymentResponse.request_id

Cart total = PaymentMandate total
Cart merchant = PaymentMandate merchant_agent
```

HP 与 HNP 的区别只在授权事实：

```text
HP  -> 最终交易时必须有用户确认事实
HNP -> 必须已有用户预授权事实，且触发条件已满足
```

这些协议事实先由 Adapter 检查；通过后仍然交给相同的协议中立 Validator 判断金额、商户、类别、时效等业务约束。Adapter 不替代 Payment Domain，也不修改四态决策规则。

当前只做离线字段和绑定验证，不验证 AP2 加密签名、自然语言 Intent 真值或真实支付执行，因此不是 AP2 一致性认证（Conformance Test）。

## 7. 执行层适配器边界

MoltsPay等实现可以把x402、链上、支付宝、微信或余额账户包装成统一执行体验，但它们不负责证明交易仍在用户委托范围内。未来执行接口保持：

```text
PaymentInstruction -> PaymentChallenge -> PaymentProof -> PaymentReceipt
```

授权与订单判断发生在`PaymentInstruction`之前；执行适配器不得修改委托（Mandate）、订单（Order）或四态决策。返回后还要独立记录支付、履约、任务结果和退款状态，不能把HTTP成功或链上确认等同于用户任务完成。具体实现样本见 [MoltsPay项目借鉴分析](../research/MoltsPay项目借鉴分析.md)。
