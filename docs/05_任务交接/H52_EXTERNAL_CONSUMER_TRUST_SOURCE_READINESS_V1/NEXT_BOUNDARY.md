# H52 单一下一边界：商家 AP2 授权到执行前可信入口

**唯一建议：MERCHANT_CONTRACT_CHANGE_REQUIRED，先冻结一个 UCP 2026-08-25/AP2 授权消费方合同及其最小商家执行点。** 当前固定 H51 花店 profile 只有 2026-04-08 的 shopping 能力、未广告 AP2 Mandates。H51 的本地 HTTP 写入/幂等/执行占用已经验收，不能靠在客户端提前验签就关闭直连商家、确认与执行之间的旁路。

## 实施边界（仅供未来评估者冻结，不在 H52 实现）
候选仅在**商家侧 checkout 完成入口、现有 execution_control.claim 之前**增加一个“不可绕过的可信授权读取/验证/投影绑定”接缝：
1. 固定清楚支持的 UCP/AP2 规范版本、完整 schema、能力协商规则；商家 profile 按实际实现宣告，而不是声称兼容；扩展激活后不准 fallback 到无授权 complete。
2. 商家原始 checkout 的每一项价格/数量/币种/收款方等参与完整 JCS/RFC8785 和 detached JWS 签名验证；原文及 sig 不能先投影丢失未知字段；用户/平台授权凭据由可信外部公钥注册机制验证并绑定到同一个 checkout 状态。区分可信签发人和 AI 自签者。
3. 独立确定性确认事件由合规的授权/确认责任方提供且与 checkout 绑定；不采信请求中自带的 `consent_present`、签发者 ID 或公钥作为独立证据。
4. 现有中立业务策略消费**已验签且与原文一致**的金额、币种、收款方及一次性执行引用，后接 H51 的持久占用、付款/订单状态与错误恢复；按顺序定义撤销、占用、实际扣款和结果查询边界，禁止重放、检查后修改及另一个直接完成入口旁路。
5. 记录可追溯的授权哈希/版本/信任根/审核判定、claim ID、Provider 引用与查询状态，向现有 Trace/Read Model 输出可验证证据。不新增独立核心、第二套支付确认或新 Agent Runtime。

## 未来必须独立验证（均未在 H52 执行）
正例：受信根+真实独立确认+相同签署 checkout+合适范围，固定商家支付模拟恰好一次；重启和查询保持同一付款引用。负例：不同 checkout/hash、签过的 checkout 再更新、金额/币种/收款方修改、过期、信任根替换、没有确认、未协商扩展却强用 AP2、已协商却无 mandate、重复同键及换键重放、同订单并发/在途撤销、绕过客户端直连原生 complete 均零错误付款。付款成功后订单写失败只能查询恢复，不重复扣款；各种结论有稳定 Trace 与原始证据核对。

## 责任、止损与非目标
必须先由商家端责任方确认 checkout schema/版本升级、来源密钥/用户同意归属、写入口控制和后续 Provider 稳定引用；无法提供信任根或完整商家合同则转 STOP/回评估者，不凭空构造演示证明。若方案需要修改 H51 冻结保护文件、产品核心、API 权限或安装依赖，必须另冻结新的任务；本任务不实现 Stripe/Medusa、不启用生产、不联系团队、不支付、不运行 ASGI/网络、不声称真实用户认可或监管符合。未来是否启动仅取决于 H52 独立复核通过和下一合同的新授权。
