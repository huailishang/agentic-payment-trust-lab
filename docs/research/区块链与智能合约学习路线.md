# 区块链与智能合约按需学习路线

> 2026-07-20 调整：系统性的区块链、密码学与可信执行学习已经回收到主仓库的 `agentic_payment_experiment.trusted_execution` 模块，采用“一仓两域”。本文件继续作为支付场景触发映射和技术来源索引，不再指向独立可信执行仓库。

## 1. 当前决策：一仓两域，业务问题按需调用可信能力

区块链、智能合约、稳定币和代币化存款与智能体支付联系紧密。为了避免把支付协议、结算轨道、密码学和区块链概念混成一层，主仓库内部保持支付域与可信执行域两个职责域：支付域负责业务生命周期和业务裁决，可信执行域负责哈希（Hash）、签名、对象绑定、幂等、状态验证和审计等确定性验证能力。

后续原则是：支付场景提出明确可信问题时，由支付域单向调用 `agentic_payment_experiment.trusted_execution` 的稳定组件，把验证事实转换为本项目自己的业务裁决。可信执行组件不得反向修改 Mandate、Order、支付生命周期或四态决策语义。

## 2. 学习原则

- 从支付问题出发，不按公链生态或热门项目罗列课程。
- 先理解交易状态、签名、幂等和终局性，再写智能合约。
- 先使用本地模拟和固定数据，不使用真实资金、主网资产或生产密钥。
- 智能合约只执行确定条件；语言模型不得决定不可逆资金转移。
- 学习产出必须说明适用范围和不能推出的生产结论。

## 3. 模块与触发条件

| 学习包 | 触发场景 | 核心问题 | 最小产出 |
|---|---|---|---|
| BC-01 账本与交易生命周期 | S05、S12 | nonce、确认、终局性、重组、费用和状态未知有什么区别 | 状态图、术语映射和一个本地重试样品 |
| BC-02 签名与对象绑定 | S09、S13、S18 | 如何证明委托、订单、收款方和请求未被替换 | 哈希/签名边界说明和固定签名测试；不接真实凭证 |
| BC-03 智能合约状态机 | S10—S12 | 托管、条件释放、退款、事件日志和失败恢复如何表达 | 本地最小状态机或伪合约及确定性测试 |
| BC-04 Token与可编程钱包 | x402/MPP进入后 | Token授权、permit、账户抽象、消费限额和会话权限如何工作 | 与中立委托模型的字段映射和风险清单 |
| BC-05 结算资产与治理 | 路线比较 | CBDC、代币化存款和稳定币由谁负债、谁治理、如何赎回 | “负债主体×账本治理”比较表 |
| BC-06 Oracle、桥和跨链 | 只有明确跨链场景时 | 外部事实和跨链消息为何引入新信任与恢复风险 | 威胁模型；当前不实现桥或Oracle |

学习顺序由场景触发，不要求从BC-01连续学到BC-06。当前I2最多按需使用BC-02中的对象摘要和绑定概念，不因此启动链上开发。

## 4. 允许与禁止的实验

允许：

- 纯本地、可删除、无真实价值的交易状态模拟。
- 固定私钥或测试向量的签名验证，但不得与个人或生产身份关联。
- 用最小合约理解状态机、事件、回退和幂等。
- 比较EVM、联盟链或中心化账本如何表达同一支付问题。

禁止：

- 主网或测试网上持有、转移真实价值。
- 保存助记词、生产密钥、卡凭证或客户身份。
- 创建代币、钱包产品、跨链桥或投资策略作为项目目标。
- 因学习了某条链就将其中立字段或治理假设写入核心模型。

## 5. 何时重新评估公共平台化

可信执行已经作为主仓库内的独立职责域存在，但仍不等于要建设公共平台。只有同时满足以下条件，才向总控评估公共开发工具包（SDK）、服务化或更强治理：

1. 至少两个独立金融智能体（Agent）项目持续复用同一组哈希、签名、幂等、状态机或审计组件。
2. 已形成不依赖智能体支付场景的可运行资产，而不是资料汇编。
3. 有明确使用者、问题、验收方式、维护责任和停止条件。
4. 独立安全、依赖或发布治理已超出单一学习实验仓库的合理边界。
5. 平台化不会挤占信用卡经营主线和当前支付实验任务。

在此之前，可信执行项目首先是学习与实验仓库；区块链仍是一组可被金融智能体问题调用的技术思想和组件，不是新的创业方向。
