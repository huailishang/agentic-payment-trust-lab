# 能力归位与缺口分析 v1

> 日期：2026-07-29
> 目的：落实《智能体支付架构基线 v1》的 Architecture Rebaseline。先重新判断现有代码到底属于成熟支付底座、Agent Trust Control Plane、测试基础设施还是测试案例，再决定是否重构代码、重做 UI 或继续新增能力。

## 1. 先给结论

当前项目不需要推倒重来。

真正需要纠偏的是研发组织方式：

```text
过去：案例 -> 规则 -> 字段 -> UI -> 更多案例

以后：稳定能力 -> 明确边界 -> 可重复验证 -> 案例只负责攻击和验证
```

现有能力大体可分成四类：

```text
A. 成熟支付交易底座
B. Agent Trust Control Plane
C. 测试 / 评测基础设施
D. 测试案例 / 外部输入
```

当前最明显的问题不是“没有能力”，而是 A、B、C、D 混在同一套代码叙事和 UI 导航里，导致 S/M/PayBench/AP2 等研发标签看起来像产品架构。

## 2. 四类能力的定义

### A. 成熟支付交易底座

传统支付系统已经长期面对的问题，例如：

- 请求身份与交易身份分离；
- 幂等与重复执行防护；
- SUCCESS / FAILED / PENDING / UNKNOWN 状态；
- UNKNOWN 后查询原交易；
- 退款 / 争议 / 后续动作绑定原交易；
- 同步应答、异步通知、查询、对账与最终性；
- 支付、履约、补救结果分离。

项目对这类能力的原则是：**学习、复用、对齐，不包装成 Agent 独有创新。**

### B. Agent Trust Control Plane

Agent 进入交易链路以后新增或显著强化的问题，例如：

- 用户到底委托 Agent 做什么；
- 谁是被授权执行的 Agent；
- Agent 当前动作是否仍忠实于原用户意图；
- Intent / Order / Payment 是否持续绑定；
- 哪些变化 Agent 可以自主处理；
- 哪些变化必须重新找用户确认；
- 网页、工具、LLM 输出等不可信内容能否改写可信支付事实；
- 最后能否回放 Agent 为什么执行了该动作。

这是本项目最应该形成研究差异化的部分。

### C. 测试 / 评测基础设施

负责证明能力是否可靠，而不是业务能力本身：

- M1 交互式实验台；
- M2 内部回归；
- M3 PayBench 接入；
- M4 AP2 协议样品验证；
- M5 统一评测；
- Attack Overlay Harness；
- 回归基线、结果卡、HTML 报告。

### D. 测试案例 / 外部输入

用于触发能力，不直接决定架构：

- S01—S13；
- PayBench A1—E1；
- AP2 HP/HNP 样品；
- ACP 固定样品；
- Attack Overlay A00—A04。

只有案例暴露出现有能力模型确实无法表达的新问题时，才允许推动新增基础能力。

## 4. 目前真正已经形成的能力

### 4.1 成熟支付底座：已有“最小骨架”

当前已经不是只有简单付款前 if/else，至少有以下可运行主线：

```text
Request
  -> Order
  -> Payment Execution
  -> Payment Status
  -> UNKNOWN / PENDING 查询恢复
  -> Fulfillment
  -> Refund / Dispute
  -> Evidence
```

并且已经开始区分：

```text
request_id
payment_id
provider_ref
idempotency_key
order_id
```

这部分价值是让 Agent 控制面可以建立在一个相对合理的支付生命周期上，而不是自己发明支付状态机。

### 4.2 Agent Control Plane：目前只有三个真正成形的雏形

#### ① Delegated Authority 雏形

当前 `IntentMandate` 已表达：

- 用户；
- 金额范围；
- 商户范围；
- 品类范围；
- 次数；
- 有效期；
- 确认阈值；
- 预期 Agent。

但它目前仍然是“规则集合”，还缺少授权版本、授权形成过程、用户确认事实、自主度等更完整语义。

#### ② Object Binding 雏形

当前已经有：

```text
authorized_order
  -> canonicalize / hash
  -> final_order
  -> verify_binding
```

这是 Agent 支付非常关键的一条主线，但目前主要验证订单摘要一致性，还没有形成：

```text
User Intent
  -> Delegated Authority
  -> Selected Offer / Order
  -> Payment Request
  -> Payment Execution
```

整条链的持续绑定。

#### ③ Untrusted Context Boundary 雏形

Attack Overlay 已证明：

```text
可信支付输入
+
不可信网页 / 工具提示
  -> 不允许直接改写可信状态
```

这是 Agent 场景真正有差异化的方向。

但当前仍是固定字段和确定性攻击样品，不能宣称已经解决真实 LLM Prompt Injection、工具调用污染或跨 Agent 数据污染。

## 5. 当前最重要的 Agent 能力缺口

按优先级排序：

### P0：Delegated Authority 还不够完整

现在有 `IntentMandate`，但没有完整回答：

```text
用户原始意图是什么？
Agent 如何解释？
哪些约束是用户明确确认的？
授权对象是否有版本？
授权是一次性、持续性还是分级自主？
发生哪些变化必须重新确认？
```

这是整个 Agent Control Plane 的根。

### P0：Intent -> Order -> Payment 的连续绑定还没有形成

当前 Binding 主要集中在 S09 的授权订单与最终订单。

真正应该逐步形成：

```text
Delegated Authority
      ↓ binding
Agent Intent / Selection
      ↓ binding
Order
      ↓ binding
Payment Request
      ↓ binding
Payment Execution
```

否则系统只能证明“某两个对象相同”，不能证明整条 Agent 执行链忠实于用户授权。

### P0：Agent Identity 只有字符串引用比较

当前明确只有：

```text
expected_agent_id == request.agent_id
```

它不能证明：

- 谁控制这个 Agent；
- credential 是否有效；
- 当前调用者是否持有对应凭证；
- provider / runtime / delegated identity 是否可信；
- Agent 身份是否在执行过程中被替换。

因此这是明确能力缺口，但暂时不等于必须马上建设完整 PKI / 密钥系统。

### P1：Autonomy Level / Human-in-the-loop 还没有形成统一模型

当前只有 `confirmation_above` 等零散规则。

后续应该统一回答：

```text
Agent 可自主做什么？
哪些动作必须确认？
确认针对哪个对象版本？
确认后对象变化是否使旧确认失效？
```

### P1：Agent Audit / Replay 仍以 EvidenceRef 为主

当前已经记录很多 `EvidenceRef`，但还没有形成真正的：

```text
谁
在什么时间
基于哪个授权版本
看到了哪些可信事实
做了什么判断
触发了什么动作
最终结果是什么
```

也没有完整的事件序列 / 防篡改 / Replay 契约。

### P1：Trust Boundary 需要从“固定 Overlay”升级为“来源分级”

当前可以阻止测试 Overlay 直接改写可信字段，但还缺少统一事实来源模型，例如：

```text
user_confirmed
merchant_signed / protocol_verified
payment_provider_observed
agent_inferred
web_untrusted
llm_generated
external_tool_untrusted
```

没有来源分级，就很难系统性回答“哪个事实能覆盖哪个事实”。

## 6. 成熟支付底座仍存在的缺口

这些缺口重要，但不应该抢走 Agent Control Plane 主线：

### P1：支付最终性模型仍较简化

当前有 SUCCESS / FAILED / PENDING / UNKNOWN，但还没有完整区分：

```text
HTTP 成功
请求受理
处理中
业务成功
异步通知确认
对账 / 清算确认
```

### P1：Original Transaction Binding 还没有抽成统一能力

退款 / 争议已有引用检查，但查询、退款、争议、撤销、冲正等后续动作还没有统一成一套 `original_transaction_ref` 契约。

### P2：异步通知 / 对账仍未形成实验链

当前状态观察来自固定离线 fixture，尚未形成“同步结果 + 异步结果 + 查询 + 对账”的组合确认实验。

这些未来应该优先参考成熟支付行业，不自己发明新机制。

## 7. 对现有 UI 的直接影响

当前 UI 代码不立即重写，但信息架构已经明确需要调整。

### 现在的第一层

```text
M2 内部回归
M3 PayBench
M4 AP2
M5 统一评测
Attack Overlay
S01—S13
```

这些都是研发 / 测试语言。

### 未来应该变成

```text
用户授权
  ↓
Agent 身份与权限
  ↓
意图 / 订单 / 支付绑定
  ↓
支付执行
  ↓
状态确认与安全恢复
  ↓
人工确认边界
  ↓
审计与回放
```

然后把 S、PayBench、AP2、Attack 作为每个能力下面的“验证样品”。

因此当前结论是：

> **暂停 UI 返工是正确的。先冻结能力地图，再重做 UI 信息架构。**

## 8. 对代码架构的直接影响

当前暂时不搬目录。

原因是现有 `trusted_execution/` 同时放了：

- Canonicalization / Hash / Binding；
- Agent 声明身份引用；
- 支付状态观察；
- 幂等事实。

从新架构看，这些并不全属于 Agent 新增能力，但现在直接拆目录只会先制造一次机械重构。

正确顺序：

```text
能力归位【本文件】
  ↓
冻结内部领域模型
  ↓
确定 Agent Control Plane 的最小接口
  ↓
再决定代码目录是否需要拆分
```

## 9. 下一阶段建议

### 第一优先：不要继续 D1 / S14

D1 数据最小化、S14 商户别名等继续保留为候选案例，但都不能直接成为下一开发任务。

### 第二优先：先补一份“Agent Control Plane 最小领域模型”

下一份设计只回答 6 个对象：

```text
1. User Intent
2. Delegated Authority
3. Agent Identity / Executor
4. Order / Transaction Object
5. Payment Execution
6. Evidence / Replay Event
```

并明确它们之间的 binding / version / confirmation / trust-source 关系。

这份模型出来后再决定：

- `IntentMandate` 是否需要升级；
- `TransactionRequest` 是否需要拆出 Agent Action / Payment Request；
- Binding 是否需要从“对象摘要验证”升级为“链式绑定”；
- Agent Identity 下一步做到什么程度；
- UI 第一层如何重新组织。

### 第三优先：继续让现有测试体系当裁判

任何新模型不能只靠文档证明，应继续使用：

```text
S01—S13 回归
+ PayBench
+ AP2
+ Attack Overlay
+ M5
```

来证明新模型没有破坏已有行为，并确实解决新的能力缺口。

## 10. 当前正式决策

```text
Architecture Rebaseline v1
        ↓
能力归位完成
        ↓
不立即重构代码
不立即重做 UI
不继续堆 S 编号
不默认继续 D1
        ↓
下一设计任务：Agent Trust Control Plane 最小领域模型
        ↓
模型冻结后
再决定代码重构 + UI 重构 + 下一能力开发
```

## 11. 一句话结论

> **当前项目已经有一套可运行的支付生命周期骨架和验证基础设施；下一阶段真正要补的不是更多异常案例，而是把“用户授权—Agent 身份—对象持续绑定—人工确认边界—可信事实来源—审计回放”形成清晰的 Agent Trust Control Plane。**
