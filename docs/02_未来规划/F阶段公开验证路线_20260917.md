# F 阶段公开验证路线

> 日期：2026-09-17  
> 定位：A—E 本地代表性能力闭环后的外部真实协议 / SDK / Sandbox / Testnet / Production-like 验证路线。  
> 原则：先公开可复现，再官方 Sandbox，再极小额 Production；每一步都复用现有 Canonical Facts + Trust Core，不为协议重写业务规则。

## 1. 一句话目标

F 阶段不是继续给 A—E 加本地 Case，而是把已经完成的授权、绑定、身份、生命周期、恢复、审计与真实性验证放到真实外部实现中，回答：

> 同一套 Trust Core 在官方协议、官方 SDK、真实 Provider、真实网络和最终小额真实交易下，是否仍然成立？

## 2. 为什么第一步先 AP2

AP2（Agent Payments Protocol）适合作为 F 的第一个外部协议验证场，而不是项目核心模型。

原因：

1. AP2 v0.2.0 的核心正是 Agent 代表用户支付时的 Mandate、Checkout/Payment Binding、Receipt 与 Human Not Present 自主交易；
2. 官方仓库公开 SDK、JSON Schema、Reference Samples，能够做可复现的外部对照；
3. AP2 与本项目现有 `IntentMandate → Order → TransactionRequest → Runtime Gate → Payment → Trace` 高度对应；
4. 它能先验证“协议对象是否能无语义漂移进入现有 A—E”，无需第一步就接真钱；
5. 之后支付宝 Agent Pay、x402、ACP/UCP 都应通过 Adapter 进入同一个 Canonical Core，可继续验证 Cross-Protocol Invariance。

当前冻结官方稳定基线：

```text
Repository: https://github.com/google-agentic-commerce/AP2
Release: v0.2.0
Release commit prefix: b4587ac
License: Apache-2.0
Primary focus: Human Not Present flows
```

不使用 rolling `main` 作为第一轮基线，避免协议漂移影响测量。

## 3. F 阶段证据阶梯

```text
F0  AP2 v0.2.0 官方合同兼容测量
    官方 release / SDK source / schemas / HNP samples
    → 与当前 Adapter / Canonical Facts 对照
    → 不改产品

F1  AP2 官方 SDK 本地可执行集成
    真实 AP2 Python types / Mandates / Receipts
    → Adapter
    → A-E Core
    → 不接真钱、不跑外部 LLM 必需链路

F2  支付宝 Agent Pay Sandbox
    官方 Sandbox / test buyer / test merchant
    → 第一个真实 Payment Provider
    → 验证支付回调、状态、Receipt/Proof、幂等和恢复

F3  真实 Identity / Wallet Provider
    支付宝 Wallet/APASS 或 SPIFFE/SPIRE 等
    → 外部 Credential
    → 现有 E：Identity / Credential / Possession / Replay

F4  极小额线上 Production Evidence
    在人工明确授权下使用最小金额（如平台允许的极小额）
    → 真正资金动作
    → 异步通知 / 查询 / 退款
    → 全程保留 A-D Evidence

F5  真实 Commerce Environment
    京东或其他公开/合作商城
    → 商品 / SKU / Order / Checkout
    → Trust Core
    → Payment Provider
    → Fulfillment / Refund / Dispute
```

F0—F3 的通过不等于生产合规；F4 也只证明“受控真实链路可工作”，不能外推为生产大规模可用。

## 4. F0：为什么先 measurement-first

第一包不允许一上来改 `src/`。

先固定 AP2 v0.2.0 官方来源，然后对照当前实现，回答以下问题：

```text
官方 AP2 对象 / 约束
        ↓
当前 AP2 Adapter
        ↓
Canonical Facts
        ↓
现有 Trust Core
```

每个关键维度标记：

- `SUPPORTED`：当前实现可忠实表达；
- `PARTIAL`：可表达部分语义，但存在证据/绑定缺口；
- `UNSUPPORTED`：当前实现无法忠实表达；
- `NOT_APPLICABLE`：该维度不属于当前 Trust Core。

F0 至少测量：

1. Mandate `vct` / schema version；
2. Human Not Present open→closed Mandate 约束；
3. Checkout hash binding；
4. Payment Mandate ↔ Checkout binding；
5. amount / currency；
6. payee / merchant；
7. Agent key / `cnf` 与身份/持有证明的边界；
8. Checkout Receipt / Payment Receipt；
9. rejection receipt / reuse prevention；
10. selective disclosure / data minimization；
11. signature verification responsibility；
12. 现有 Canonical Core 是否因协议差异被迫改业务规则。

F0 Task PASS 不要求 12 项全部 `SUPPORTED`。PASS 的含义是“官方来源被固定、12 个维度被真实测量、差距可机械复核、没有把未知写成已支持”。

## 5. F0 的停止条件

以下任一出现，Executor 停止，不自行修产品：

- 需要修改核心授权/支付业务规则才能“适配” AP2；
- 需要用 task/scenario 特判才能通过；
- 官方 v0.2.0 source 无法固定或 release 身份不一致；
- 需要 Google API Key / Vertex / Gemini 才能完成合同兼容测量；
- 需要真实支付、钱包、生产凭证；
- 需要安装新的依赖才能完成第一轮 source/schema measurement；
- 发现 AP2 v0.2.0 与当前文档假设存在重大版本不一致。

出现差距时，下一包只针对重复共同断点，不得把 F0 直接扩成“完整 AP2 实现”。

## 6. F1—F5 的推进门

### F0 → F1

只有 F0 给出明确 compatibility matrix 和首个共同断点，才允许：

- 新增最小 official SDK bridge；
- 引入必要依赖；
- 跑 AP2 官方 types / local sample objects；
- 对比 Adapter 前后 Canonical Facts。

### F1 → F2

只有官方 SDK 对象能稳定进入 A—E，才进入支付宝 Sandbox。Sandbox 首先验证：

```text
Mandate / Authorization
→ Runtime Gate
→ Payment request
→ Provider callback/query
→ Payment Finality / Recovery
→ Receipt / Trace
```

### F2 → F4

必须先满足：

- Sandbox 全链稳定；
- 重复付款保护有效；
- 异步通知与查询结果可重放；
- 失败不会自动二次付款；
- 测试凭证与生产凭证完全隔离；
- 人工明确授权真实资金范围。

## 7. Cross-Protocol Invariance

F 阶段不能变成“接一个协议写一套规则”。

正确架构：

```text
AP2 ─┐
ACP ─┤
UCP ─┤→ Adapter → Canonical Facts → Trust Core → Decision / Lifecycle / Trace
x402 ─┘
Alipay ─┘
```

核心验收原则：

> 同一个业务事实，在不同协议可等价表达的范围内，Adapter 后应形成语义等价的 Canonical Facts，并得到一致的 Trust Decision；协议能力确实不同的差异必须显式归因。

## 8. 第一执行包

当前第一包：

`F0_AP2_V020_OFFICIAL_CONTRACT_COMPATIBILITY_MEASUREMENT_V1`

性质：`measurement-only / one_off`。

目标：

> 用官方 AP2 v0.2.0 release 的真实 source/schema/HNP samples，独立测量当前 AP2 Adapter 与 Canonical Core 的兼容程度，冻结首个 F 阶段真实外部差距；不修改产品代码。

完成后由 Evaluator 决定：

- `NO_PRODUCT_GAP` → 直接设计 F1 official SDK executable slice；
- `BOUNDED_ADAPTER_GAP` → 只开一个最小 Adapter capability package；
- `CORE_SEMANTIC_GAP` → 暂停 F1，先判断是不是现有 Core 真缺能力；
- `SOURCE/ENV_BLOCKED` → 不猜，转 Human / 环境准备。
