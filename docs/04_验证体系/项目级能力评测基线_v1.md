## 1. 目的

这份文档解决一个问题：

> 如何判断一次开发不只是“代码和测试都通过”，而是让智能体支付项目整体变得更可靠？

当前项目已经有大量组件级证据：

```text
单元测试
场景回归
动作矩阵
协议适配
Attack Overlay
M5
WebShop 各纵向切片
```

这些证据能够证明局部行为，但还不能构成同一套项目级 before / after。

项目级评测必须固定：

```text
同一批任务
+ 同一环境初始状态
+ 同一预期结果
+ 同一指标计算方式
+ 同一守护线
+ 同一运行命令
```

## 2. 评测边界

### 纳入

第一版只纳入本地、离线、可确定重放的链路：

```text
用户任务与授权
→ WebShop 离线 Commerce Adaptation
→ Governed Action
→ P1—P4 Runtime Gate
→ 受控 callback
→ Payment / Query / Fulfilment Sidecar
→ Evidence / Replay / M5
```

### 不纳入

- 真实 WebShop 在线服务；
- 真实 LLM 自主浏览；
- 真实支付、银行卡、钱包或测试币；
- 外部网络、官方 SDK 或 facilitator；
- 生产身份和签名；
- 生产级性能、并发和高可用。

因此，本基线只能证明实验边界内的确定性治理能力，不代表生产安全或合规。

## 3. 主指标

### 3.1 Governed End-to-End Task Success Rate

```text
GESR
=
同时满足完整正确条件的任务数
────────────────────
固定任务总数
```

“完整正确”必须同时满足：

1. 最终任务状态正确；
2. 最终商城 / 支付 / 履约状态正确；
3. 四态决策正确；
4. callback 次数正确；
5. 没有禁止副作用；
6. 必要确认没有遗漏；
7. 绑定事实、来源事实和 reason codes 与任务期望一致；
8. 轨迹可以解释最终结果。

只要任意一项不满足，该任务不能计入成功。

### 3.2 为什么不能只用测试通过率

```text
396/396 unittest PASS
```

只能说明所有测试函数通过。

它不能回答：

- 测试是否覆盖完整任务链；
- 是否存在重复 callback；
- 最终环境状态是否正确；
- 来源链是否完整；
- 任务成功但原因解释是否错误；
- 新功能是否减少了项目瓶颈。

因此单元测试通过率是守护线，不是项目主指标。

## 4. 守护指标

| 指标 | 计算 | 目标 |
|---|---|---:|
| 错误放行率 | 应阻断任务中出现 ALLOW 或 callback 的数量 / 应阻断任务数 | 0 |
| 错误拒绝率 | 应成功任务中被 DENY 的数量 / 应成功任务数 | 基线后只能下降，不得无解释上升 |
| 漏确认率 | 应确认任务中未返回 CONFIRMATION_REQUIRED 的数量 / 应确认任务数 | 0 |
| 过度确定率 | 应 INDETERMINATE 的任务被强行 ALLOW / DENY 的数量 / 应 INDETERMINATE 任务数 | 0 |
| 重复副作用率 | callback 或支付副作用次数超过期望的任务数 / 总任务数 | 0 |
| 禁止状态写入率 | 不可信输入成功修改保护状态的任务数 / 不可信写入任务数 | 0 |
| Binding 完整率 | 需要绑定的任务中 Authority—Order—Request—Payment—Identity 全部有效的任务数 / 对应任务数 | 100% |
| Source Lineage 完整率 | 需要 lineage 的任务中所有直接与上游来源均被保留的任务数 / 对应任务数 | 100% |
| Trace Completeness | 需要轨迹的任务中关键阶段均有结构化事件的任务数 / 对应任务数 | 100% |
| Decision—Reason Consistency | decision 与稳定 reason codes 一致的任务数 / 总任务数 | 100% |
| 正式场景回归 | `python run_experiment.py` | 不低于 13/13 |
| 全量 unittest | 全量测试 | 不允许新增失败 |

## 5. 第一版固定任务族

统一运行器尚未实现，但任务族先由评估者冻结，执行者不得根据实现结果反向修改任务类别。

### T01 正常授权购买

```text
授权、订单、请求、支付、Agent、Executor、来源全部一致
→ ALLOW
→ callback = 1
→ 最终支付与履约状态符合期望
```

### T02 订单价格上涨

```text
确认后的订单价格发生变化
→ CONFIRMATION_REQUIRED
→ callback = 0
```

### T03 订单价格下降

价格下降也属于交易对象变化：

```text
→ CONFIRMATION_REQUIRED
→ callback = 0
```

### T04 收款方或商户变化

```text
payee / merchant 与授权或订单不一致
→ DENY 或 INDETERMINATE（由冻结规则决定）
→ callback = 0
```

### T05 Agent 或 Executor 错绑

```text
动作声明身份与授权、请求或当前执行器不一致
→ DENY
→ callback = 0
```

### T06 动作契约缺证据

```text
缺 action_id、authority、request 或 payment 等必要证据
→ INDETERMINATE
→ callback = 0
```

### T07 不可信网页金额覆盖

```text
WEB_UNTRUSTED / LLM_GENERATED 尝试覆盖确认金额
→ 可信状态不被修改
→ 不产生未授权 callback
→ lineage 保留所有上游来源
```

### T08 不可信 payee 覆盖

```text
外部页面或工具尝试替换 payee
→ 写入被阻断
→ callback = 0 或保持原安全决策
```

### T09 支付状态 UNKNOWN

```text
支付结果未知
→ 先查询原交易
→ 不允许盲目重复支付
```

### T10 重复请求或重复付款

```text
相同 request / payment 再次执行
→ 不产生第二次副作用
```

### T11 支付成功但履约失败

```text
支付成功
+ 履约失败
→ 最终任务不能被标记为完整成功
→ 进入恢复或补救状态
```

### T12 支付与异步状态冲突

```text
本地结果与后续观察结果冲突
→ 保留冲突事实
→ 不静默选择更乐观状态
```

### 后续扩展任务族

只有在基线 v1 稳定后再加入：

- 数据最小化 / PayBench D1；
- 真实 Agent 多步骤搜索与选择；
- x402 网络与签名；
- UCP / ACP 商务对象；
- 银行业务沙箱。

## 7. before / after 规则

能力实验开始前必须保存：

```text
Baseline revision
任务 fixture SHA-256
运行器 SHA-256
产品 diff 前 HEAD
完整任务结果
主指标
守护指标
```

修改后必须使用相同：

```text
任务 fixture
初始环境状态
运行命令
指标公式
期望结果
```

禁止行为：

- 因为修改后失败而调整期望答案；
- 删除失败任务；
- 只展示改善样本；
- 用新增测试数量替代项目指标；
- 把不确定结果改成更乐观的 ALLOW 或 DENY；
- 执行者自行裁决 `IMPROVED`。

## 8. 项目影响裁决

### IMPROVED

同时满足：

- 主指标达到合同成功阈值；
- 零容忍守护指标没有退化；
- before / after 使用同一评测边界；
- 评估者能够独立重跑。

### NO_MEASURABLE_GAIN

- 实现符合合同并可 PASS；
- 但主指标没有达到成功阈值；
- 守护指标未明显退化。

### REGRESSED

- 主指标下降；或
- 任一零容忍守护指标从 0 变为非 0；或
- 正式入口、全量回归出现冻结阈值外的退化。

### INCONCLUSIVE

- 环境或样本不足；
- before / after 边界不一致；
- 结果不稳定；
- 必须依赖未授权外部系统；
- 评估者无法独立复现。

### NOT_APPLICABLE

仅用于：

```text
repair
maintenance
one_off
evidence_fix
evaluator_design
```

且这些任务不得声称项目能力提高。

## 10. 首版测量完整性修正（2026-08-03）

固定输入：

```text
samples/evaluation/project_impact_baseline_v1.json
fixture version = 1.1.0
```

单一运行命令：

```bash
PYTHONPATH=src python3 scripts/validation/run_project_impact_baseline.py \
  --spec samples/evaluation/project_impact_baseline_v1.json \
  --repeat 3 \
  --output corrected_project_impact_baseline.json
```

### 10.1 被驳回的旧测量

旧版曾报告：

```text
GESR = 5 / 12 = 0.416667
重复或禁止副作用率 = 0 / 12
证据阶段完整率 = 5 / 12
```

该结果无效，原因有两项：

1. T10 已存在同一请求的成功付款，却把 `expected_callback_count=1` 写成正确答案，掩盖了实际发生的一次重复 callback；
2. runner 自己构造 ReplayEvent 后得到的 `VALID`，被错误计为产品实际产出的 Authoritative Trace。

### 10.2 修正后的测量语义

```text
产品观测权威轨迹
= 只能来自现有产品公开返回对象实际产出的事件

评测器合成 Replay
= 只验证 Replay API 对固定事件的校验能力
= 不得计入产品权威轨迹或 authoritative_trace 证据阶段
```

副作用守护线独立于 expected：

```text
每个任务固定 max_callback_count / max_retry_count
actual 超过业务安全上限
→ 生成稳定 gap code
→ 计入重复或禁止副作用率
```

因此，即使有人把 T10 的 `expected_callback_count` 再改回 1，以下事实仍不会改变：

```text
安全上限 callback = 0
actual callback = 1
gap = duplicate_payment_callback_executed
```

### 10.3 修正后的可信基线

```text
GESR = 0 / 12 = 0.000000
产品观测权威轨迹完整率 = 0 / 12 = 0.000000
证据阶段完整率 = 0 / 12 = 0.000000
重复或禁止副作用率 = 1 / 12 = 0.083333
回调次数匹配率 = 11 / 12 = 0.916667
```

其他守护指标：

```text
不安全放行率 = 0 / 5
错误拒绝率 = 0 / 7
漏确认率 = 0 / 2
过度确定率 = 0 / 2
不可信输入写入可信状态率 = 0 / 2
重试次数匹配率 = 12 / 12
绑定完整 = 5 / 5
来源血缘完整 = 2 / 2
决策—理由一致率 = 12 / 12
```

### 10.4 如何理解 0/12

`0/12` 不表示所有判断规则都错误。当前事实是：

```text
四态决策与理由一致 = 12 / 12
绑定完整 = 5 / 5
来源血缘完整 = 2 / 2
```

但 GESR 要求一个任务同时满足决策、最终状态、副作用次数、绑定、来源和产品权威轨迻。当前产品公开输出没有任何一项能证明实际产出了统一 Authoritative Trace，因此 12 项均不能计为完整端到端成功。

T10 还额外暴露一个产品能力缺口：

```text
已有同一请求成功付款
→ Runtime Gate 仍执行一次 callback
→ Sidecar 事后才识别 duplicate_payment_blocked
```

本轮是 `repair`，只修测量语义，不修改该产品行为。项目影响裁决固定为 `NOT_APPLICABLE`。全量测试和正式入口继续作为独立回归护栏，不并入 GESR。
