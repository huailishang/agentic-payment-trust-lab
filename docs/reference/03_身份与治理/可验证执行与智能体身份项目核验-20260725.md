# 可验证执行与智能体身份项目核验

核验日期：2026-07-25

适用范围：本地离线的智能体支付可信执行实验，不构成产品选型、生产安全评估、法律意见或监管合规结论。

## 1. 结论摘要

“2026 年中可验证执行与智能体（Agent）身份受到集中关注”可以作为趋势判断，但公开材料不足以证明已经形成统一、成熟、广泛采用的行业基础设施。

现有项目需要分层看待：

- Dapr 1.18 是有官方文档、开源实现和社区治理背景的工作流历史完整性方案，工程参考价值最高。
- NexArt 已公开 CER 数据结构、规范化与本地验证方法，但成熟度、采用范围和第三方安全验证仍主要依赖项目方材料。
- OpenMatter 已发布商业平台，公开信息以公司网站和新闻稿为主，不能据此确认实现完整度、客户采用或密码学方案经过独立审计。
- DNSid 提出了持久、可解析的智能体归属锚点，但截至核验日仍是 IETF individual Internet-Draft，不是已批准标准，也不负责运行时认证、授权或策略执行。
- KPMG 与 Microsoft 的部署说明企业治理、可见性和问责需求真实存在，但不能单独证明“密码学可验证执行已经成为市场准入前置条件”。

对本项目的直接借鉴价值较大，但应吸收证据模型和失败语义，不应现在接入外部平台或提前建设通用可信基础设施。

## 3. 需要修正的表述

### 3.1 Dapr 不是“把每步输出哈希嵌入下一步输入”的简单实现

Dapr 工作流历史签名（Workflow History Signing）的公开机制是：

1. 对新增 `HistoryEvent` 做确定性 protobuf 编码。
2. 对带长度前缀的事件批次计算 SHA-256。
3. 计算前一个 `HistorySignature` 消息的摘要。
4. 对 `SHA-256(previousSignatureDigest || eventsDigest)` 签名。

因此更准确的说法是“事件批次与前序签名形成签名链”。工作流之间的谱系传播属于相邻但不同的机制。

### 3.2 “日志可改，所以必须用密码学证明”过于绝对

普通应用日志可能被修改、遗漏或脱离上下文，但受控审计日志、WORM 存储、透明日志和外部时间戳也能提供不同等级的防篡改与追溯能力。是否需要签名链，应由威胁模型、证据保留期、跨组织验证需求和运维成本决定。

### 3.3 “外部审计只需验证数学完整性”不完整

密码学验证仍依赖：

- 规范化与签名覆盖字段是否完整；
- 签名密钥与真实执行主体的绑定；
- 信任根、密钥轮换、撤销和历史验证策略；
- 证据是否在执行时生成，而非事后由同一受控系统补造；
- 外部工具响应、支付服务商回执和时间来源是否可信。

数学完整性只能证明“给定证据之间一致且未被检测到篡改”，不能证明证据完整记录了现实，也不能证明业务决策正确。

### 3.4 “可验证执行 + 数字身份 = 完整问责闭环”仍缺少两层

执行证据回答“记录显示做了什么”，持久身份回答“哪个标识或密钥参与”。完整问责还需要：

- 授权与委托：该主体在当时是否有权执行这项动作；
- 业务与法律归责：组织、操作人、平台和服务商分别承担什么责任。

因此身份、认证、授权、执行证据和业务归责应保持分层。

### 3.5 “集中爆发”是趋势信号，不是成熟度证明

多个项目在相近时间发布可以说明市场关注度提升，但样本中包含成熟开源项目的新功能、早期商业平台、厂商证据格式和标准草案。它们不能仅因发布时间接近就被视为同等成熟，也不能推出行业已经收敛到统一架构。

## 4. 对本项目的可吸收部分

| 外部机制 | 本项目可吸收内容 | 对应阶段 | 明确不吸收的结论 |
|---|---|---|---|
| Dapr 确定性事件编码 | 明确定义跨运行时稳定表示、版本字段和被签名字节 | TE02 规范化（Canonicalization） | 不直接引入 Dapr 运行时 |
| Dapr 前序签名链接 | 在确有多步证据需求时，为事件记录加入 `previous_digest` 和覆盖范围 | TE06 审计（Audit） | 链验证通过不等于支付应继续 |
| Dapr 失败保全 | 验证失败后保留原始不可信证据，返回稳定错误类型，停止可信模块继续派生事实 | TE03—TE06 | 可信执行域不直接退款、拒绝、重试或开争议 |
| NexArt CER | 参考最小、可移植、带 `schema_version` 的执行证据包，以及本地独立验证方式 | TE03/TE04 | 不使用“认证”措辞暗示合规或第三方背书 |
| SPIFFE/DNSid 分层身份 | 区分短期运行时身份、持久智能体标识、组织归属和支付授权 | TE05 身份 | 身份可解析不等于有支付权限或法律责任已确定 |
| 企业智能体治理 | 记录智能体所有者、版本、能力、使用工具和生命周期状态 | 后续真实需求触发 | 不为假设中的企业控制面提前建设平台 |

当前最稳妥的吸收顺序保持不变：

```text
TE02 规范化契约
  -> TE03 授权对象与执行对象绑定
  -> TE04 执行身份 / 状态观察 / 幂等事实
  -> TE05 测试密钥下的签名与身份实验
  -> TE06 由真实场景触发的链式审计
```

首批消费者仍应是：

- S09：验证授权订单与最终订单是否为同一绑定对象；
- S12：验证 request、payment、provider reference、order 和 idempotency 之间的关系。

可信执行域只返回确定性事实，支付域继续决定是否继续、重新确认、查询、等待或人工介入。

## 5. “每次实验先搜索最新项目/协议”规则的批判性分析

### 合理之处

- 能及时发现正式协议的新版本、破坏性变更和更成熟的实现，减少重复实现已有机制。
- 能为数据结构、失败语义、负向测试和密钥生命周期提供现实样本。
- 能避免项目长期封闭在旧假设中。

### 主要风险

- 每次执行都搜索会让固定场景回放依赖当日互联网结果，破坏可复现性。
- 新闻稿、SEO 内容和厂商命名容易制造“已经成熟”的错觉，反而扩大范围。
- 搜索成本可能高于一个小实验本身，诱导频繁换方向和无止境调研。
- 新协议不一定解决本项目的问题；为了复用而引入框架可能比本地最小实现更复杂。
- GitHub 热度、Stars 和近期提交不等于安全、正确或适合信用卡支付。
- 让独立智能体自动检索并给出结论，仍需要主任务按来源等级复核，不能把研究判断外包给搜索结果。

### 推荐的仓库规则

不采用“每次执行前强制全网搜索”，改为“阶段门触发的外部扫描”：

> 当任务将新增外部协议适配、密码学原语、身份/签名/幂等/审计能力，或改变长期架构边界时，先进行一次有范围的外部扫描；纯回归、缺陷修复、固定样品回放、文案或无架构影响的小改动不强制搜索。

扫描结果必须：

1. 先查正式标准、官方规范、官方仓库和版本化 Release，再看研究、试点、厂商材料和媒体。
2. 记录访问日期、版本或提交、适用范围、许可证、运行/凭证要求和不确定性。
3. 明确它解决的本项目问题；没有具体消费者，不克隆、不安装、不接入。
4. 将外部实现作为设计样本，核心语义仍由本项目的支付场景和边界决定。
5. 固定进入实验的协议快照；后续网络新信息通过显式升级任务吸收，不在普通回放时漂移。
6. 搜索没有发现合适实现时，才记录“为何需要最小自研”，而不是笼统声称行业没有方案。

建议的触发节奏：

- 任务级：只有命中上述阶段门时扫描；
- 月度或里程碑级：集中复查协议 Release、正式标准状态和关键项目变化；
- 紧急级：出现安全公告、协议废弃、许可证变化或上游破坏性升级时专项复查。

这条规则已于 2026-07-25 写入仓库根目录 `AGENTS.md`。后续可通过一至两个命中阶段门的任务检验执行成本，再决定是否需要增加统一扫描输出模板；在此之前不扩大触发范围。
