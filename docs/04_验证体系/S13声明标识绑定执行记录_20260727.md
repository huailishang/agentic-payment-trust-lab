# S13 声明标识绑定执行记录

> 执行日期：2026-07-27

## 1. 结论

```text
S13 声明的智能体标识与委托指定标识不一致：PASS

用户委托 expected_agent_id
        +
付款请求 agent_id
        ↓
可信执行域：声明标识引用绑定事实
VALID / INVALID / MISSING_EVIDENCE
        ↓
支付域：委托验证器
继续决定 ALLOW / DENY / CONFIRMATION_REQUIRED / INDETERMINATE
```

本轮没有新增第二套 `DENY` 规则。原支付域已经存在 `expected_agent_id` 与 `request.agent_id` 不一致时阻止请求的业务规则；本轮新增的是一个独立、可审计的可信执行事实层，并新增 S13 固定样品作为真实消费者。

## 2. 为什么 S13 仍然值得做

已有能力：

```text
expected_agent_id != request.agent_id
-> agent_identity_mismatch
-> Payment Domain = DENY
```

缺失能力：

```text
谁负责只回答“两个声明的标识引用是否一致”？
这个事实是否可以独立测试、独立审计？
界面是否明确区分“标识引用一致”和“真实身份认证”？
```

因此 S13 的增量不是重复业务规则，而是把“声明标识绑定事实”和“支付业务裁决”分层。

## 3. 新增可信执行事实

新增：

```python
verify_declared_identity_binding(
    expected_identity_id,
    actual_identity_id,
) -> VerificationResult
```

返回：

```text
VALID
    declared_identity_reference_match

INVALID
    declared_identity_reference_mismatch

MISSING_EVIDENCE
    declared_identity_reference_missing
```

最重要边界：

> `VALID` 只表示两个给定的标识引用字符串一致，不表示完成了身份核验（identity proofing）、认证（authentication）、认证器验证、凭证验证、联邦身份保证或密钥控制证明。

因此接口没有 `authenticated=true` 一类字段。

## 4. 支付域如何消费

`validator.py` 当前流程：

```text
mandate.expected_agent_id 存在
        ↓
verify_declared_identity_binding()
        ↓
记录：
agent_claim_binding_status
agent_claim_binding_reason
        ↓
若事实不是 VALID
        ↓
Payment Domain 保留原规则：
agent_identity_mismatch
        ↓
DENY
```

也就是说：

```text
Trusted Execution = INVALID
≠ Trusted Execution 决定 DENY

Trusted Execution = INVALID
+ Payment Domain 委托规则
= DENY
```

## 5. S13 固定样品

新增：

```text
samples/scenarios/S13_agent_identity_mismatch.json
```

样品：

```text
委托指定：agent-shop-001
请求声明：agent-shop-other
        ↓
声明标识绑定事实 = INVALID
        ↓
Payment Domain = DENY
reason = agent_identity_mismatch
```

样品同时明确限制：

- 不执行真实身份核验。
- 不验证认证器、证书、签名或密钥。
- 不因为字符串标识一致就声称身份已认证。
- 不执行真实支付。

## 6. 外部规范核对

本轮只参考 NIST 官方数字身份指南，不引入外部代码或 SDK。

NIST SP 800-63-4 将数字身份保证拆分为身份核验、认证与联邦等不同问题，并把认证建立在认证过程与认证器之上。因此本项目把当前能力严格命名为“声明标识引用绑定”，不称为真正的身份认证。
