# 数字货币三路线与可信基础设施：对智能体支付项目的影响分析

> 日期：2026-09-08  
> 材料范围：CBMT、俄罗斯数字卢布、韩国 Project Hangang、UNDP × DFINITY 主权云、知识产权可信数据空间。  
> 项目结论：**前三项用于校准未来 Cross-Rail Payment（跨支付轨道）与 Settlement（结算）边界；后两项只吸收 Trust / Provenance（信任 / 来源）原则。全部材料均不改变当前 B-12 / H-18 主线。**

## 1. 先给吸收结论

| 材料 | 项目判断 | 真正吸收 | 不吸收 |
|---|---|---|---|
| CBMT | `ABSORB（吸收）` | 多银行各自发行存款代币、Bridge 互操作、跨行 / 跨链结算、Agentic B2B 场景中的身份与人工确认 | 不把区块链、发币、智能合约设为项目主线；不把沙盒写成生产网络 |
| Project Hangang | `ABSORB（吸收）` | 客户侧商业银行存款代币与底层央行结算资产分层；统一账本上的可编程支付；Payment Instrument 与 Final Settlement Anchor 分离 | 不把韩国试点直接推导为其他国家制度路线；不因试点扩容立即接 CBDC |
| 数字卢布 | `ABSORB / REFERENCE（部分吸收）` | Agent Authority（智能体授权）与 Rail / Wallet Policy（轨道 / 钱包规则）分层；支付工具自身可以有额度、准入和用途约束 | 不把零售 CBDC 当成智能体支付的必然资金形态 |
| UNDP × DFINITY 主权云 | `REFERENCE_ONLY（只参考）` | Runtime Provenance、Credential / Key Governance、数据与执行环境控制权 | 不在支付仓建设主权云、去中心化 AI 或通用 Runtime |
| 知识产权可信数据空间 | `REFERENCE_ONLY（只参考）` | 一数一源、分类分级、使用边界、Fact Lineage、数据安全与来源追踪 | 不新增“可信数据空间”模块；现有 Fact Lineage 已承接主要思想 |

## 2. 三条数字货币路线带来的共同校准

三份支付材料表面上分别讨论代币化存款、零售 CBDC 和“批发 CBDC + 存款代币”，但对本项目共同说明了一件事：

```text
Agent Trust Control
        ↓
Payment Instrument / Funding Source
        ↓
Payment Rail / Network
        ↓
Settlement Asset
        ↓
Final Settlement Anchor
        ↓
Finality / Query / Redemption / Recovery
```

上层可以保持统一：Identity、Authority、Budget、Order / Payment Binding、Human Confirmation、Idempotency、Evidence / Replay。

下层不能强行统一：谁承担负债、是否平价兑付、跨机构怎样结算、什么时候真正结束、异常后找谁查询 / 退款 / 恢复，要服从具体 Rail 与 Settlement Asset 的真实制度和技术语义。

因此继续坚持：

> **Agent 支付控制解决“这笔钱该不该花”；支付轨道解决“钱怎么走”；结算资产解决“最终收到的是什么钱、由谁保证、什么时候真正结束”。**

## 3. CBMT：最值得吸收的是“多发行主体 + Bridge + Agentic B2B”

CBMT 官方将自身定义为 GBIC 发起的 Commercial Bank Money Token 研究沙盒。每家银行发行的仍是对本行的商业银行存款债权，不是一个全网统一稳定币；官方明确标注沙盒只使用测试资金，不是生产金融服务。

当前官方沙盒还直接列出了 `Cross-border Agentic B2B Payments` 场景：AI Agent 发起跨银行、跨区块链企业支付，同时结合 certified agent identity（认证智能体身份）和 human-in-the-loop authorization（人工在环授权）。

对本项目的价值不是“证明应该上链”，而是提供了一个未来 Cross-Rail / Cross-Institution 验证样本：

```text
同一 User / Enterprise Mandate
        ↓
Agent Identity + Authority
        ↓
Order / Payment Binding
        ↓
Runtime Gate
        ↓
CBMT / 其他 Rail Adapter
        ↓
具体银行发行的 Deposit Token
        ↓
Bridge / Interbank Settlement
```

需要保留两个边界：

1. `currency=EUR` 相同，不代表不同银行发行的存款代币在负债主体、银行信用暴露和恢复机制上完全相同；
2. Bridge 负责网络 / 结算互操作，不负责替代 Agent Authority / Transaction Binding。

### 对后续实验的具体启发

未来 Cross-Rail 真正升为第一瓶颈后，可以把“同一授权跨不同发行银行 / Rail 后，Trust Decision 是否不变”作为测试，而不是现在增加大量 token / chain 字段。

## 4. Project Hangang：客户支付资产与最终结算锚可以分层

韩国银行 Project Hangang 二阶段继续推进“机构型央行数字货币 + 商业银行存款代币”的真实交易试验。韩国银行公开材料显示，二阶段参与银行扩大，并加入生物识别、存款与存款代币自动转换、可编程国库资金等能力。

它对本项目最重要的启发是：**用户看到 / 持有的支付工具，不一定等于金融机构之间最终用于清偿的结算资产。**

```text
用户 / 企业
    ↓
商业银行 Deposit Token
    ↓
统一账本
    ↓
批发 CBDC / 央行结算资产
    ↓
最终机构间结算
```

因此未来不要把 `rail` 做成一个过度扁平的万能字段。真实建模至少要能区分：

```text
Payment Instrument
Payment Rail / Network
Settlement Asset
Issuer / Obligor
Final Settlement Anchor
Finality / Recovery Source
```

但这些当前都只是**未来最小 Contract 的候选维度**，不是现在立即加入领域对象的字段清单。

## 5. 数字卢布：Trust ALLOW 不等于 Rail 一定允许支付

俄罗斯央行已从 2026-09-01 起按正式决定扩大数字卢布业务可用范围，并明确个人从银行账户等增加数字卢布余额的月度上限等平台规则。

这说明未来 Agent 支付至少存在两层独立判断：

```text
第一层：Agent Trust Control
用户是否授权？金额 / 商户 / 商品 / 次数是否符合 Mandate？

第二层：Rail / Wallet / Regulatory Policy
该钱包能否执行？是否超过额度？该类交易是否被平台 / 监管规则允许？
```

所以项目后续应保持：

```text
Trust Decision = ALLOW
≠ Payment Accepted
≠ Settlement Final
≠ User Task Success
```

同理，Rail 技术上允许执行，也不能反向证明 Agent 获得了用户授权。

这一点应继续由 Payment Lifecycle / Finality / Recovery 与上层 Trust Control 分层承担，而不是把钱包规则塞进 Agent Validator。

## 6. UNDP 主权云：只吸收 Runtime Trust，不扩支付项目边界

UNDP 与 DFINITY 的正式合作重点是探索 sovereign cloud（主权云）与 decentralized AI（去中心化 AI）在政府、公民社会和 UNDP 项目中的试点使用。它不是支付标准，也不是金融监管要求。

对本项目仅保留以下问题：

```text
Agent 在哪里运行？
谁控制 Runtime？
谁能修改工具 / 模型 / 配置？
凭据和密钥由谁托管？
日志和证据保存在哪里？
执行环境是否能被单一外部主体静默改写？
```

这些问题映射到现有：

- Executor Identity / Identity Assurance；
- Context / Tool Integrity；
- Credential / Key Governance（当前仍是待真实证据验证能力）；
- Evidence Provenance / Replay。

如果未来证明这些能力在支付以外也被第二个领域真实消费，再考虑回抽 Enterprise Agent Control Plane；**当前不在支付仓建设主权云或去中心化 AI 基础设施。**

## 7. 可信数据空间：用来校准 Fact Lineage，不新增新模块

国家知识产权局、国家数据局 2026-08-24 印发的意见强调公共数据“一本账”、分类分级、使用边界、安全风险评估、“一数一源”、可信数据空间和人工智能应用安全。

对支付项目最有价值的是来源治理思想：一个事实不仅要有值，还要知道来源、版本、使用边界和被谁消费。

映射到当前项目：

```text
WebShop / Merchant 原始事实
        ↓
Commerce Adapter 派生事实
        ↓
Authoritative Payment Fact
        ↓
Trust / Runtime Gate
        ↓
Payment / Fulfillment / Recovery
        ↓
Evidence / Replay
```

例如 `price=100` 不能只保留数值，还需要能够回答：来自哪个权威源、哪个订单版本、何时观察、是否派生、最终绑定到哪个 Payment Request。

这正是现有 Fact Lineage / Authoritative Trace 主线，不需要新增 `Trusted Data Space` 领域对象。

## 8. 对当前 B-12 / H-18 的裁决

**不改变当前任务，不冻结新执行包。**

当前仍然先测：

```text
Same-Journey Payment Lifecycle
    ├─ Success / Fulfillment
    ├─ UNKNOWN -> Query Recovery
    ├─ Fulfillment Failure
    └─ Status Conflict
        ↓
semantic match
+ continuity
+ first breakpoint
```

原因是这批材料反而强化了 B-12 的价值：未来无论接卡、账户、CBDC、代币化存款还是链上结算，Payment Finality / Query / Recovery 都会存在，只是具体语义不同。

所以正确顺序是：

```text
当前 B-12 / H-18
→ 先把支付生命周期与恢复连续性测扎实
→ 形成稳定 Shared Trust / Lifecycle 边界
→ Cross-Rail 未来升为真实瓶颈
→ 再引入不同 Rail / Settlement Asset 做对照实验
```

## 9. 未来真正值得新增的两个验收问题

当 Cross-Rail 以后被激活时，只新增两个高层验收问题，不按每种数字货币新增一套业务逻辑。

### A. Shared Trust Invariance（共享信任不变量）

同一个 Task / Mandate 切换卡、账户、CBDC、稳定币或代币化存款后：

- 身份不能重置；
- 授权范围不能扩大；
- 总预算不能重新计算；
- 原订单 / 支付绑定不能丢；
- 人工确认要求不能被 Rail 切换绕过；
- Idempotency / Replay 规则继续有效。

### B. Settlement Semantics Explicitness（结算语义显式化）

每个 Rail / Settlement Asset 必须明确告诉上层：

- 谁是负债 / 兑付主体；
- 最终结算锚是什么；
- 当前状态是不是 Final；
- UNKNOWN 时去哪里 Query；
- 是否支持 Redemption / Refund / Reversal；
- Recovery 证据来自哪里。

如果外部 Rail 无法给出这些事实，项目应返回 capability gap（能力缺口），而不是由 Adapter 自行猜测。

## 11. 最终边界

这批材料用于补全项目的“下面半截”，不是重写项目主线：

```text
User Intent / Mandate
→ Agent Identity / Action Origin
→ Order / Payment Binding
→ Agent Trust Control
────────────────────────
→ Payment Instrument
→ Payment Rail / Network
→ Settlement Asset
→ Final Settlement Anchor
→ Finality / Query / Recovery
────────────────────────
→ Fulfillment / Refund / Dispute
→ Evidence / Replay / Accountability
```

**项目继续做“智能体是否被可信地允许执行高风险交易”的验证场，而不是数字货币、区块链或支付清算基础设施实现项目。**
