# 智能体支付产业动态核验与外部测试路线

> 核验日期：2026-08-01  
> 用途：记录近期公开进展的可信边界，并把外部生产、沙盒、协议和调查材料转化为本项目可执行的验证路线。  
> 结论边界：本文件不把企业公告、单笔交易、链上笔数或沙盒参与等同于规模化采用、监管批准或生产安全。

## 1. 总结

近期公开进展说明，智能体支付已经从概念演示进入以下并行阶段：

```text
公开协议与开发环境
  + 商业产品有限开放
  + 单笔或少量真实交易
  + 企业/监管受控沙盒
  + 身份、授权、责任标准研究
```

但目前还不能得出“已经形成统一技术路线”或“已经规模化采用”的结论。银行卡网络、稳定币、开放协议、企业钱包和商户编排仍在并行发展；多数公告没有披露客户覆盖、独立用户、交易金额、失败率、争议率、清结算通道或长期留存。

对本项目最重要的启示不是继续收集案例，而是把外部协议和项目作为同一组稳定能力的验证输入：

```text
外部协议 / Agent / 商户 / PSP
              ↓
            Adapter
              ↓
成熟支付底座 + Agent Trust Control Plane
              ↓
统一评测、攻击测试、回放证据
```

## 3. 信源与口径注意事项

### 3.1 链上交易笔数不能直接等于商业采用

x402scan展示的是链上或索引层观察数据。解读时必须至少区分：

```text
请求数
付款证明验证数
链上结算数
独立付款方
独立收款方
独立资源交付数
成功履约数
```

因此：

```text
交易笔数 ≠ 独立用户数
链上结算 ≠ 资源正确交付
高频小额交易 ≠ 已形成可持续商业模式
```

FluxA“200万笔”应作为本项目的数据口径测试题：保存来源、观察时间、统计窗口、指标定义和不可确认项，不直接复制宣传数字。

### 3.2 “生产”需要分级

| 层级 | 典型案例 | 能证明什么 |
|---|---|---|
| 公开协议与测试环境 | Coinbase/x402 SDK、x402.org testnet facilitator | 开发者可以真实调用协议并完成测试网闭环 |
| 商业产品有限开放 | Coinbase Business、Adyen Agentic、Natural | 产品已经供部分客户或合作方使用，但覆盖和效果可能不公开 |
| 单笔或少量真实交易 | Visa + 连连LoopXPay | 真实业务链路至少成功运行过一次 |
| 企业/监管沙盒 | Mastercard Proto、FCA Sandbox | 可在受控边界内验证流程、安全和责任 |
| 标准工作组 | EPAA + HSBC | 行业正在形成身份、授权和责任共识 |

## 4. 与项目六项能力的对应关系

| 外部进展 | 对应项目能力 | 可形成的验证问题 |
|---|---|---|
| Visa Agentic Directory | Agent与执行者身份 | 当前Agent是否可识别、是否与被授权执行者一致、身份变化是否阻断 |
| LoopXPay金额和审批参数 | 用户授权与确认 | 金额、商户、品类、次数、期限和人工审批边界是否被持续执行 |
| x402付款要求与付款证明 | 交易对象与支付绑定 | 付款证明是否绑定具体资源、金额、收款方、网络和请求，能否跨资源替换或重放 |
| 网页、工具、MCP返回内容 | 可信上下文与执行前拦截 | 不可信内容能否改写收款方、金额、授权或支付状态 |
| facilitator验证、链上结算、HTTP资源交付 | 支付状态恢复与最终性 | HTTP、验证、结算、交付、查询和异步观察不一致时是否安全停机 |
| Mastercard争议、FCA责任、Natural可观测性 | 证据与回放 | 能否回放谁基于什么授权、事实和规则执行了什么动作 |
| Adyen消费者信任边界 | 人工确认横切能力 | 哪些变化必须重新确认，安全检查是否被当作必要信任机制而非多余摩擦 |

这进一步支持项目当前架构：成熟支付能力负责交易状态、幂等、查询、争议和最终性；Agent Trust Control Plane负责委托、身份、对象持续绑定、不可信上下文隔离和行为回放。

## 5. 外部互动与测试路线

### 阶段A：Coinbase官方x402测试网闭环

优先选择公开、可复现、无真实资金的x402测试环境。Coinbase官方文档提供买方和卖方SDK；`x402.org/facilitator`支持Base Sepolia和Solana Devnet，测试网无需API密钥。

最小拓扑：

```text
本地模拟付费API（卖方）
        ↓ 返回HTTP 402付款要求
测试Agent（买方）
        ↓ 生成测试网付款证明
官方x402 facilitator
        ↓ 验证/结算
本地API返回资源
        ↓
本项目Evidence + M5统一评测
```

第一版不追求“能付款”的演示效果，而要验证P4—P6是否能在真实协议对象上发现问题。

### 阶段B：协议一致性与故障注入

建议固定第一批十个测试：

1. 修改收款地址后，原付款证明必须失效；
2. 修改金额、网络或资产后，原授权不得继续使用；
3. 同一付款证明不得换到另一资源或API路径；
4. 同一付款证明并发提交不得导致重复交付；
5. 报价后价格变化必须重新判断授权或确认；
6. facilitator验证成功但结算状态未知时不得盲目重复付款；
7. 链上结算成功但HTTP资源交付失败时，支付成功与履约失败必须分离；
8. HTTP成功、异步通知和主动查询结果冲突时，必须进入冲突/核查状态；
9. 超预算、授权过期或需要人工确认时，SDK自动重试不得绕过策略；
10. 所有决定必须可回放到原授权、Agent身份、订单、支付请求、付款证明和状态观察。

近期公开安全研究已指出x402实现中存在跨资源替换、并发重复履约、动态价格/额度问题、免费获取资源、资产或Gas滥用等风险。这些问题与本项目的Binding、Replay、Runtime Gate、Finality和Conflict Fact直接对应，应转化为本地可重复攻击样品，而不是只写成行业资讯。

### 阶段C：生产数据只读观察

在不发起真实交易的前提下，保存x402scan或链上快照：

```text
facilitator
交易哈希
付款方 / 收款方
金额 / 资产 / 网络
时间
资源或服务标识（可获得时）
重复频率
买卖方集中度
统计窗口与抓取时间
```

该层只做市场与集中度观察，不把链上结算自动标注为正确授权、正确交付或真实用户采用。

### 阶段D：外部沙盒和行业合作

测试网与本地故障注入稳定后，再形成协议中立的测试包，用于申请或沟通：

```text
授权范围
Agent身份与代理链
Intent / Order / Payment持续绑定
付款证明重放
同步 / 异步 / 查询冲突
人工确认
退款 / 争议
审计回放
禁止副作用
```

可用于后续关注Mastercard Proto、Natural开发者环境、EPAA工作组或支付机构联合沙盒。未取得明确接入资格、接口和责任边界前，不把这些机构写入本项目实现依赖。

### 阶段E：小额主网实验（暂不启动）

只有测试网闭环、故障注入、预算控制、停止开关和证据回放均稳定后，才讨论极低金额主网实验。必须使用专用低余额钱包、固定商户/API、禁止自动充值、禁止长期无限授权，并逐笔留存证据。当前P4—P6验证不需要真实资金。

## 6. 建议进入主计划的顺序

```text
P7：能力优先UI
  ↓
P8：x402测试网一致性闭环
  ↓
P9：x402攻击与故障注入
  ↓
P10：生产链上只读观察
  ↓
再评估Natural、Mastercard、FCA或行业工作组合作
```

P8第一版只接一个协议、一个测试网facilitator、一个本地卖方API、一个买方Agent和约十个确定性测试。不得同时接FluxA、Coinbase、Natural、Visa、Mastercard等多个项目，否则会重新退化成外部项目清单。

## 7. P8建议的最小目标

> 在不使用真实资金、不改变现有支付业务内核的前提下，建立一个可重复的x402测试网适配与一致性测试闭环，证明现有授权、绑定、可信上下文、重放、状态最终性和统一评测能力能够处理真实协议对象。

边界：

- 不接主网和真实资金；
- 不申请企业生产权限；
- 不把SDK成功运行当作安全通过；
- 不复制完整x402框架到业务内核；
- Adapter只把外部对象映射到现有协议中立事实；
- 外部调用必须单独授权，测试必须可在离线fixture下回放。
