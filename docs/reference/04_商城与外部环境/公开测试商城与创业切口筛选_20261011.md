### 官方样例的两个容易误判点

- 商家文档中的 `--require_signatures` 默认 `false`，缺签或无效签名仍可通过请求。跑通 happy path 不能证明强制验签；若以后测真实性，必须固定配置并加入负例。文档中的 localhost profile 例外也会改变网络保护边界，只能在隔离测试条件下评估。
- 文档示例协议版本为 `2026-04-08`；不得直接把它当作任意最新规范的兼容性证明。正式任务应固定仓库 commit、依赖、双方 profile 版本、mock handler 和允许端点，再检查执行前拦截、订单变化、重复/未知状态及证据对应关系。

这些仅是公开文档核查结果，没有证明本项目已接入 UCP 商家或取得第二支付服务方凭证。

商城提供商品、订单和交易动作；本仓提供围绕这些动作的授权、绑定、执行前控制、恢复与证据。复用现有演示是把已验收能力讲清楚；新 UCP 样例是潜在外部协议适用性验证，两者都不自动等于新增支付真实性证据。

展示建议限定为三段：正常授权路径；确认后商品/金额变化的判定；超时或重复请求下的处理。每段必须使用真实存在且已验收的案例；没有现成证据的段落标为待接入设计。明确区分固定脚本、历史回放与实时 Agent 运行，并同时展示用户授权、实际动作、判定理由和结果证据。

## 创业切口：先验证交付痛点

“技术能演示”不等于“市场已成熟”，但“用户尚未大规模采用”也不能单独推出没有商业机会。本轮没有建立总体采用率或市场规模证据。更可检验的假设是：已有交易型 Agent 项目的团队，是否正在为接入、异常恢复和上线验收耗费可观的人力。

已有 UCPPlayground 的工具检查/回放/评测，以及 ShopGym 等公开环境，说明“再做一个通用商城测试平台”不能直接当差异化。候选首个交付应缩为：一个客户、一个工作流、一个付款执行点，复现两三个客户真实关心的失败条件，给出正常路径对照、原因、回归材料及最小修复建议。先证明能节省交付或排障成本，再决定是否做软件。

Human 当前没有直接客户渠道。下一商业动作建议是利用公开开发仓库、商家应用生态与集成商案例，筛选确实正在交付购物/采购/付费工具的团队；目标是找到具体项目、技术/预算负责人和近期交付卡点。演示用来解释能力，不用点赞或试用人数代替预算证据。本次未收集私人联系人或发送消息。

两周可尝试筛选 10–15 个对象、争取 5 次问题访谈、1–2 条可安全复现的外部测试流程，再讨论固定范围收费。数字是实验目标，不是转化率预测。官方配置已能解决时不发明自建模块；有首单但全是定制时仍属服务业务；第二客户能复用主要机制且交付成本下降，才支持产品化判断。
