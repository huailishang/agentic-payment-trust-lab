# 支付域与可信执行域模块边界

## 1. 当前关系

两个域已经位于同一仓库、同一 Python 包体系中，但职责必须继续分开：

```text
agentic_payment_experiment
├── 支付域
│   └── 委托 / 订单 / 支付 / 履约 / 退款 / 争议 / 恢复 / 适配器
└── trusted_execution
    └── 规范化 / 哈希 / 绑定 / 身份 / 幂等 / 状态验证 / 审计
```

允许的依赖方向：

```text
支付域
    -> 可信执行域
    -> 获得确定性验证事实
    -> 支付域决定业务动作
```

可信执行域不反向导入支付域的业务模型，不定义支付生命周期政策。

## 2. 如何判断能力属于哪个域

| 问题 | 所属域 |
|---|---|
| 用户到底授权了什么 | 支付域 |
| 订单涨价后是否需要重新确认 | 支付域 |
| 支付状态未知（UNKNOWN）后是等待、查询还是人工介入 | 支付域 |
| 已授权对象和最终对象是否是同一个绑定对象 | 可信执行域 |
| 查询结果是否可靠绑定原交易 | 可信执行域 |
| 请求（request）/交易（transaction）/幂等（idempotency）关系是否一致 | 可信执行域 |
| 某个状态迁移在给定状态机规则下是否合法 | 可信执行域 |
| 退款或争议在业务上是否应该发起 | 支付域 |

一句话判断：

```text
“接下来业务应该做什么？”
    -> 支付域

“给定对象、状态和证据，能否证明它们一致、唯一、未被替换、可追溯？”
    -> 可信执行域
```

## 3. 返回值边界

可信执行域可以返回：

```text
有效（VALID）
无效（INVALID）
证据缺失（MISSING_EVIDENCE）
冲突（CONFLICT）
重复风险（DUPLICATE_RISK）
```

或等价的结构化验证结果。

它不直接返回：

```text
允许（ALLOW）
拒绝（DENY）
需要确认（CONFIRMATION_REQUIRED）
安全重试（RETRY_PAYMENT）
退款（REFUND）
发起争议（OPEN_DISPUTE）
```

这些属于具体支付业务裁决。

## 4. 当前实际接口

当前稳定实现已经覆盖 TE01—TE04：

```python
canonicalize(value) -> JSON-compatible value
canonical_json(value) -> str
canonical_hash(value, algorithm="sha256") -> str
verify_hash(expected_hash, value) -> bool
verify_binding(expected_digest, actual_object)
    -> VALID / INVALID / MISSING_EVIDENCE
verify_execution_identity(...) -> VerificationResult
validate_status_observation(...) -> VerificationResult
check_idempotency(...) -> IdempotencyFact
verify_declared_identity_binding(...) -> VerificationResult
verify_confirmation_binding(...) -> ConfirmationBindingFact
execute_with_confirmation_gate(...) -> PaymentGateOutcome
verify_payment_execution_binding(...) -> PaymentExecutionBindingFact
verify_agent_executor_identity(...) -> IdentityAssuranceFact
execute_with_payment_binding_gate(...) -> PaymentExecutionGateOutcome
evaluate_context_policy(...) -> ContextPolicyResult
```

真实 `Order` / `OrderItem` 已可直接规范化和计算摘要；P1 的 `ConfirmationRecord`、授权版本引用和执行前确认绑定已接入 S09 与主验证路径；P2 连续支付绑定已接入 S10—S12，S12 原有状态观察与幂等事实保持不变；S13 已真实消费声明标识绑定事实。P3 候选实现的 `verify_agent_executor_identity()` 只输出 `VALID / INVALID / MISSING_EVIDENCE`、原因和 `DECLARED / BOUND / VERIFIED` 保证等级；支付域把它映射为业务动作，并在回调前同时消费 P2/P3。

S13 的 `verify_declared_identity_binding()` 只比较给定标识引用，**不是身份核验或认证**。P3 的离线确定性绑定最多达到 `BOUND`；`credential_ref` 只是引用，没有 credential validity、possession、provider attestation、PKI 或 federation verifier 时不得产生 `VERIFIED`。P3 当前为执行者候选、等待独立评估，不按编号进入 S14，也不提前重构主 UI。

支付域对 P3 事实的映射固定为：

```text
P3 MISSING_EVIDENCE 或低于 BOUND
    -> INDETERMINATE
P3 INVALID
    -> DENY
P3 VALID 且至少 BOUND
    -> 仍需上游 ALLOW + P2 VALID + P4 VALID，全部成立才允许模拟 callback
```

P4 的可信执行接口只返回来源矩阵核验、applied/blocked paths 和不可变合并事实。支付域映射固定为：

```text
P4 MISSING_EVIDENCE，或缺 policy_version/current_action
    -> INDETERMINATE
P4 INVALID，或未授权改写实际进入可信状态
    -> DENY
P4 VALID，越权尝试已安全阻断且可信状态未污染
    -> 不单独改变原 ALLOW 路径
```

### 4.1 Evidence → Uncertainty → Risk → Action（证据到动作）

支付场景不新增模型自报的 `confidence=0.x`。可信执行域继续只产出可验证事实及其状态，例如 `VALID / INVALID / MISSING_EVIDENCE / CONFLICT`；支付域在 Runtime Authorization Gate（运行时授权门禁）前统一消费这些事实、关键证据覆盖情况和动作风险。

稳定规则：

- 任一**关键支付事实**处于 `MISSING_EVIDENCE / CONFLICT / UNKNOWN` 时，不满足直接 `ALLOW` 条件；
- 证据不足本身不自动等于 `DENY`：没有确定性违规事实时，支付域按业务策略进入 `INDETERMINATE` 或 `CONFIRMATION_REQUIRED`；
- 只有确定性 `INVALID` 或明确业务策略命中时，才映射到对应拒绝路径；
- 不把多个事实做平均分，也不允许“模型整体很自信”覆盖某个关键事实缺失；
- 首版验证重点是：**上游即使已经给出 ALLOW，只要 Binding / Identity / Context Policy 中任一关键门禁证据不完整，就不得触发支付 callback / 副作用。**

因此这里的 Uncertainty（不确定性）首先是**证据状态与未决原因**，而不是语言模型主观概率；后续只有形成可复现实验与 Calibration（校准）数据后，才考虑数值置信度。

`SourceType` 是声明的规则输入，不是来源认证。`PAYMENT_PROVIDER_OBSERVED` 可更新支付状态，但不能改授权、付款请求或执行身份；未声明的来源 × 事实域组合默认阻断。

## 5. 推荐的跨域接入顺序

### 第一处：S09 订单绑定

```text
支付域
已授权订单（Authorized Order）
    -> 可信执行域 canonicalize/hash
    -> 保存摘要

最终订单（Final Order）
    -> 可信执行域 verify_binding
    -> 返回有效（VALID） / 无效（INVALID） / 证据缺失（MISSING_EVIDENCE）

支付域
    -> 根据实际变化字段和用户委托
    -> 决定继续 / 重新确认 / 拒绝
```

哈希不同只说明规范化后的对象发生变化，不自动等于 `DENY`。

### 第二处：S12 支付恢复【已接入】

已从 `payment_recovery.py` 抽出：

```text
verify_execution_identity()
validate_status_observation()
check_idempotency()
```

可信执行域验证原交易绑定、幂等边界和同请求相关尝试；支付域继续决定等待、查询、安全重试候选或人工介入。

## 6. 不做的耦合

- 不让可信执行域导入 AP2 / ACP / UCP 的业务模型作为核心依赖。
- 不把支付域的四态决策写入可信执行模块。
- 不把哈希相同等同于“业务合法”。
- 不把签名有效等同于“授权范围正确”。
- 不把状态迁移合法等同于“该金融动作应该执行”。
- 不为了未来可能复用，提前创建没有真实消费者的通用平台接口。

## 7. 何时抽成独立开发工具包（SDK）

当前不拆仓、不发公共开发工具包（SDK）、不做远程服务。

只有满足下面条件才重新评估：

1. 除支付域外出现第二个独立金融智能体（Agent）场景。
2. 至少两个可信能力被两个消费者真实复用。
3. 独立版本、发布和安全治理的收益明显高于同仓维护成本。

在此之前，“一仓两域”比“两个独立项目”更适合当前学习和实验阶段。
