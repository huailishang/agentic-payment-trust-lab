# x402 离线一致性验证方案 v1

## 1. 目的

本方案不是接入真实 x402 支付，而是先回答一个更基础的问题：

> x402 的请求、付款要求、付款证明、facilitator 验证/结算和资源交付观察，能否在不修改现有支付业务内核的前提下，转换为项目已有的授权、绑定、幂等、原交易、最终性、冲突和回放事实。

验证链路：

```text
合成 HTTP 请求
  ↓
合成 402 付款要求
  ↓
合成付款证明引用
  ↓
x402 Adapter
  ↓
协议中立的授权 / 订单 / 请求 / 支付 / 状态 / 履约事实
  ↓
现有 Binding / Idempotency / Original Transaction / Finality / Conflict / Replay
  ↓
ALLOW / BLOCK / CONFLICT / INDETERMINATE / UNSUPPORTED
```

全程仅处理本地 JSON fixture，不调用网络，不创建钱包，不签名，不结算，不支付，也不实际交付资源。

## 2. 边界

### 2.1 支持范围

当前仅支持用于离线验证的最小语义：

- HTTP 方法与稳定资源标识；
- `exact` 付款方案；
- `base-sepolia`、`solana-devnet` 两个测试网络名称；
- 资产、金额、收款方；
- 付款要求标识与确定性摘要；
- 付款证明引用；
- facilitator 验证、结算和异步观察；
- 资源交付观察；
- 请求、付款和原交易引用；
- 重复/并发使用观察。

### 2.2 明确不支持

- x402 SDK 或完整协议实现；
- 密钥、签名生成与密码学验证；
- Coinbase/CDP 账户或 API Key；
- facilitator HTTP 调用；
- 钱包、测试币、Gas 或链上交易；
- 主网或测试网付款；
- 生产商户正确性、安全性或合规性判断。

不支持的方案、网络、版本或字段语义会返回 `UNSUPPORTED` 或 fail-closed，不会静默猜测。

## 3. Fixture 模型

Fixture 文件：

```text
samples/protocols/x402/x402_offline_cases_v1.json
```

根节点必须包含：

```json
{
  "fixture_version": "x402-offline-fixture-v1",
  "synthetic": true,
  "cases": []
}
```

每个案例包含八个区域：

| 区域 | 用途 |
|---|---|
| `http_request` | 请求方法、资源、请求引用和时间 |
| `payment_requirement` | 付款要求、金额、资产、网络、收款方和确定性摘要 |
| `payment_proof` | 提交的证明引用及其声称绑定的对象 |
| `facilitator_verification` | facilitator 验证观察 |
| `facilitator_settlement` | 主动查询/结算观察 |
| `facilitator_async_observation` | 异步状态观察 |
| `resource_delivery` | API 或资源交付观察 |
| `project_context` | 本项目用于连接授权事实的本地桥接字段 |

`project_context` 明确属于项目本地字段，不宣称是 x402 线上报文字段。

Fixture 全部使用合成引用，不含真实客户身份、卡数据、私钥、助记词、生产凭据或真实资金交易。

## 4. 字段到协议中立事实的映射

| x402/fixture 字段 | 协议中立事实 | 说明 |
|---|---|---|
| HTTP method + resource | `Order.service_id`、证据中的资源对象 | 资源必须与付款证明保持一致 |
| requirement id | `Order.order_id`、原交易引用 | 作为本地稳定交易对象引用 |
| amount | `Order.total_amount`、`TransactionRequest.amount`、`PaymentExecutionRecord.amount` | 由现有连续绑定校验金额变化 |
| asset | `currency` | 由现有连续绑定校验资产变化 |
| payee | `Order.payee`、请求/执行收款方 | 由现有连续绑定校验偷换收款方 |
| scheme + network | `Order.candidate_rails` + adapter 协议边界校验 | 不向支付内核引入 x402 专用字段 |
| request ref | `TransactionRequest.request_id`、执行对象引用 | 绑定请求与付款证明 |
| proof ref | `PaymentExecutionRecord.payment_id`、`idempotency_key` | 用于重复/并发使用检查 |
| settlement observation | `PaymentStatusObservation` | 仅表示支付状态观察 |
| async observation | `PaymentStatusObservation` | 与主动观察共同形成冲突事实 |
| resource delivery | `FulfillmentRecord` | 与支付状态分离，不把结算成功当作业务成功 |
| project authorization context | `IntentMandate` | 项目本地桥接，不是 x402 协议声明 |

付款要求摘要使用项目已有 `canonical_hash`，覆盖：

```text
HTTP方法 + 资源 + 请求引用 + 要求标识
+ 方案 + 网络 + 资产 + 金额 + 收款方
```

该摘要只用于本项目确定性离线验证，不宣称与官方 x402 签名规范一致。

## 5. 六个确定性案例

| 案例 | 预期结果 | 核心验证 |
|---|---|---|
| C01 正常绑定 | `ALLOW` | 付款要求、证明、资源、支付状态和交付一致 |
| C02 偷换收款方 | `BLOCK` | 现有连续绑定发现请求收款方与订单不一致 |
| C03 修改金额/资产/网络 | `BLOCK` | 金额和资产由现有绑定发现；网络由 adapter 边界发现 |
| C04 跨资源复用证明 | `BLOCK` | 同一证明不能从东京资源换到大阪资源 |
| C05 重复/并发使用证明 | `BLOCK` | 同一 proof/idempotency key 只允许形成一个成功交付观察 |
| C06 结算/异步/交付冲突 | `CONFLICT` | 结算成功、异步失败和资源交付失败必须显式冲突，不能显示业务成功 |

案例的 `expected` 只作为测试 Oracle。实际结果由适配器和现有事实函数计算；如果修改 `expected` 而实际事实不变，测试结果会变成 `FAIL`。

## 6. 结果与证据

每个案例输出：

- `status`：`PASS`、`FAIL` 或 `UNSUPPORTED`；
- `expected_outcome` 与 `actual_outcome`；
- 原因码；
- 是否出现重复/并发复用；
- 成功交付观察数量；
- 是否确认完整业务成功；
- 资源、付款要求、付款证明、facilitator、交付、绑定、幂等、最终性、冲突和回放证据。

证据能够回答：

```text
哪个资源要求付款？
付款要求绑定了什么金额、资产、网络和收款方？
哪个证明被使用？
是否发生重复或跨资源使用？
facilitator 观察到了什么？
资源是否交付？
为什么最终允许、阻断、冲突、未决或不支持？
```

## 7. 运行方式

```powershell
python -m unittest tests.test_x402_adapter tests.test_x402_conformance -v
```

当前环境没有 `python` 命令时：

```bash
env PYTHONPATH=src python3 -m unittest tests.test_x402_adapter tests.test_x402_conformance -v
```

也可以在 Python 中读取完整结果：

```python
from pathlib import Path
from agentic_payment_experiment.x402_conformance import run_x402_conformance

report = run_x402_conformance(
    Path("samples/protocols/x402/x402_offline_cases_v1.json")
)
print(report.to_dict())
```

## 8. 结论边界

离线 fixture 全部通过，只能证明：

> 在当前有限字段和合成观察范围内，x402 对象可以映射到现有协议中立事实，且六类确定性风险能够被本项目显式识别。

它不能证明：

- 官方 SDK 安全；
- facilitator 生产安全；
- 商户实现正确；
- 密码学签名有效；
- 监管合规；
- 测试网或主网可上线；
- 链上结算一定对应正确资源交付。

真实测试网互动必须作为后续独立任务重新授权网络/API、钱包和资金边界。
