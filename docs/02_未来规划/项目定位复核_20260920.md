## 定位裁决

**当前准确定位：面向企业执行型 Agent，以支付为高风险场景的交易授权、执行控制与证据验证实验室。**

**待客户验证的产品假设：为交易型 Agent 开发商及实施团队提供可嵌入的执行控制组件、上线验证工具和故障取证能力。**

**长期可选方向：只有多个独立场景反复需要同样机制，且存在采购与复用证据，才抽取企业智能体控制平面。**

三层不能合并：仓库已有技术资产，不等于已有生产 SDK、持续运营服务、完整托管平台或商业壁垒。测试数量、协议数量和文档数量不是客户价值指标。

## 应修正的旧表述

1. “我们做信任、大厂做支付”不成立：ACT/APASS 与我们在授权、核验、证据方面明显重叠。
2. “协议中立天然形成壁垒”不成立：ACT 也声明开放/兼容；中立只有在客户实际跨供应商、且原方案存在可测成本时才可能有价值。
3. “验证整个支付安全”过宽：我们只能在取得可信输入、接入指定执行点的范围内判断；没有执行闸门接入，就只能审计，不能阻止副作用。外部身份、签名、资金处理和支付最终性仍需对应证据。
4. “几十人公司缺开发能力，所以会买”不成立：采购取决于自建维护成本、可替代性、接入成本、风险和预算，不取决于员工数量。
5. “企业智能体控制平面是必然商业终点”不成立：需求可能由云、支付平台、ERP、客户内部团队或集成商吸收。

## 可能值得付费的最小问题

候选客户不是全部中小企业，而是已经交付或运行交易型 Agent、有重复集成/故障成本、有预算负责人的软件团队。

优先验证一个具体假设：客户的 Agent 在多个工具/业务系统间执行时，需要保持同一授权、交易对象和结果证据连续；官方单一支付接入仍留下企业内部策略映射、异常恢复和跨系统取证工作。

可交付切片示例：接入一个现有 Agent 和一条测试交易链，测出并修复订单替换、授权变化、未知状态重试等真实失败，交付可复跑测试与证据。指标采用集成/排障工时、重复或越权动作、问题可复现率和客户验收结果，不承诺赔付、认证或法律责任裁决。

若客户用官方 SDK 加少量配置即可满足需求，则停止该产品切口；不能为了维护定位而增加中间层。

## 与项目组合的关系

| 资产/项目 | 当前作用 | 不能代替什么 |
| --- | --- | --- |
| long-term-strategy | 审查产业机制、价值由谁获得、反例和退出条件 | 不代替客户订单和利润 |
| asset-cognition | 提醒投入要有边界、机会成本和退出余地 | 不证明某创业方向值得做 |
| payment-trust-lab | 高风险交易控制与证据压力测试 | 不代替生产支付平台 |
| data-warehouse-agent 等业务项目 | 独立场景验证公共机制是否真正重复 | 不因名称不同就算第二消费者，必须有实际接入证据 |
| Control Plane 候选 | 对已重复验证的机制做复用 | 不提前建设通用 Agent Runtime |

创业投入可借用“必要性、总成本、机会成本、最坏情景、重审条件”的决策方法；这里不提供家庭资金配置建议，也不推断 Human 的财务承受能力。

## 后续条件

- 工程：先完成 H-39 证据修订；H-38 live 授权入口问题单独修复；保持沙箱、零真实资金和预算约束。

- CONTINUE：客户愿提供真实场景及预算，交付能量化改善；第二客户重复使用主体能力且交付成本下降。
- STOP/SWITCH：只得到兴趣表态、现有官方产品已足够、每客户都需重写、持续运维责任超出交付能力。
- 抽公共层：跨领域第二消费者有实际复用及负向测试，再考虑回抽；两个支付协议不自动等于跨领域复用。
