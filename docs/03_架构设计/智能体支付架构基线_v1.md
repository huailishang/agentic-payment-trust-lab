# 智能体支付架构基线 v1

> 日期：2026-07-28
> 定位：架构重新定标文档。用于约束后续研发方向，避免继续以案例数量、S 编号或局部任务完成度替代项目主目标。

## 1. 为什么需要重新定标

过去一段时间已经完成了大量实现：内部场景、统一评测、PayBench、AP2、Attack Overlay、Canonicalization、Hash、Binding、Execution Facts、幂等与 UNKNOWN 恢复等。

问题不是这些实现本身都没有价值，而是研发过程中逐渐出现了一个偏差：

~~~text
增加一个异常案例
    -> 增一个测试
    -> 增一个字段
    -> 增一个 UI 入口
    -> 再解释这个案例
~~~

如果长期沿这条路推进，项目容易变成“异常案例集合 + 大量 if/else”，而不是一个有清晰技术主线的智能体支付实验室。

因此，从本版本开始，项目回到第一性原理：

> **成熟支付行业已经解决什么？Agent 进入交易链路后新增了什么主要矛盾？本项目只对真正新增的问题做实验和能力建设；成熟支付机制优先学习、复用和对齐，不重复造轮子。**

## 2. 项目的主要矛盾

传统支付中，人通常直接参与关键环节：选商品、确认订单、确认付款、处理异常。

智能体支付把大量决策前移给 Agent：

~~~text
用户说出目标
    -> Agent 理解意图
    -> Agent 找商品 / 服务
    -> Agent 比较与选择
    -> Agent 生成订单
    -> Agent 调用支付
    -> 用户只在部分边界点重新出现
~~~

因此，项目真正需要解决的问题不是“金额 560 是否大于 550”这类基础判断本身，而是：

~~~text
1. 用户到底授权 Agent 做什么？
2. 当前发起动作的 Agent 是谁？
3. 当前订单 / 请求是否仍然绑定原授权与原交易对象？
4. 网页、工具、LLM 输出等不可信内容能否改写可信支付事实？
5. 当前交易到底处于什么状态？
6. 哪些变化 Agent 可以自主处理，哪些必须重新找用户确认？
7. 一旦超时、状态未知或后续退款，如何安全恢复而不重复执行？
8. 最后能否回放“谁、基于什么事实、为什么执行了什么动作”？
~~~

这八类问题构成当前项目的主要矛盾。

## 3. 第一层：成熟支付交易底座

成熟支付市场已经积累了大量稳定机制。项目不把这些能力包装成“Agent 新创新”，而是尽量参考银联、卡组织、支付服务商等成熟设计。

当前本地银联资料已经提炼出的稳定主线包括：

~~~text
用户授权 / 交易意图
    -> 形成明确交易对象
    -> 唯一标识
    -> 请求交易
    -> 交易处理
    -> 状态确认
    -> UNKNOWN 时查询原交易
    -> 退款 / 撤销 / 冲正绑定原交易
    -> 同步应答 / 异步通知 / 查询 / 对账
    -> 最终证据与责任确认
~~~

重点继承以下成熟机制：

| 机制 | 项目原则 |
|---|---|
| 请求身份与交易身份分离 | request_id != transaction_id/payment_id |
| 幂等 | 多次请求不等于多笔业务交易 |
| UNKNOWN 一等状态 | UNKNOWN 不等于 FAILED |
| 安全恢复 | UNKNOWN 先查询原交易，禁止盲目重扣 |
| 原交易绑定 | 查询、退款、撤销、冲正、争议显式引用原交易 |
| 状态最终性分层 | 通讯成功、受理、处理中、业务成功、对账/清算不是同一概念 |
| 同步 + 异步 + 查询 + 对账 | 共同形成结果确认链，而不是只看一次 HTTP 应答 |
| 完整性与签名 | 验证确定对象和调用上下文是否被改写，但签名有效不等于业务合法 |

参考入口：

- docs/reference/unionpay/银联规范借鉴与项目架构分析-20260720.md
- 本地忽略目录 local_sources/third_party/unionpay/ 中的银联规范原件

## 4. 第二层：Agent Trust Control Plane

Agent 时代真正新增的能力，应叠加在成熟支付交易底座之上，而不是重新发明支付清算体系。

~~~text
              Agent Trust Control Plane
       ┌────────────────────────────────┐
       │ 用户意图 / Delegated Authority │
       │ Agent 身份与执行主体           │
       │ Intent / Order / Payment 绑定  │
       │ Trust Boundary                 │
       │ 自主度与 Human-in-the-loop     │
       │ Agent 行为审计与 Replay        │
       └───────────────┬────────────────┘
                       ↓
                 成熟支付交易底座
       ┌────────────────────────────────┐
       │ Order / Payment                │
       │ Transaction State             │
       │ Query / Idempotency            │
       │ Refund / Reversal / Dispute    │
       │ Reconciliation / Evidence      │
       └────────────────────────────────┘
~~~

这个控制面回答的不是“钱怎么清算”，而是：

> **Agent 为什么有权触发这笔交易，以及在缺少人工逐步确认时，系统如何证明这次执行仍然忠实于用户授权。**

## 5. 当前代码如何重新归位

现有实现不全部推翻，而是重新判断其长期定位。

| 当前能力 | 所属主线 | 结论 |
|---|---|---|
| Canonicalization | 通用可信执行基础 | 保留 |
| Hash | 完整性基础 | 保留，但不把 Hash 相等写成业务合法 |
| Binding | Agent Control Plane + 支付对象绑定 | 核心能力，继续强化 |
| Execution Identity | 交易执行身份 | 保留 |
| Idempotency | 成熟支付底座 | 保留并继续对齐真实交易身份模型 |
| UNKNOWN 状态恢复 | 成熟支付底座 | 保留，不作为 Agent 独有创新 |
| Original Transaction Binding | 成熟支付 + Agent 可审计 | 强化 |
| Declared Agent Identity Binding | Agent Control Plane | 保留，但当前不是完整身份认证 |
| AP2 Adapter | Agent 协议入口 | 保留 |
| Attack Overlay | Agent Trust Boundary | 核心能力，继续强化 |
| M5 Evaluator | 测试基础设施 | 保留 |
| 超预算 / 品类 / 商户 / 过期等基础案例 | Policy 基础规则测试 | 降级为单元/回归测试，不再作为项目价值主角 |
| S 系列 | 场景测试集 | 保留，但只是测试，不再驱动架构 |
| PayBench | 外部挑战 | 保留，用来暴露真实缺口 |

## 6. M / S / PayBench / AP2 的正确关系

这些名字都不是业务架构本身，而是验证方式或输入来源。

~~~text
                  真正的支付 + Agent 可信能力
                             ↑
       ┌─────────────────────┼─────────────────────┐
       │                     │                     │
    S / M2                PayBench              AP2 / M4
内部固定回归            外部挑战题            外部协议对象
       │                     │                     │
       └────────────── Adapter / Harness ─────────┘
                             ↓
                     同一业务与可信能力
                             ↓
                            M5
                         统一评测
~~~

Attack Overlay 则从不可信环境输入角度攻击同一能力：

~~~text
可信支付状态 + 不可信网页 / 工具 / LLM 内容
                  ↓
        尝试越权修改可信事实
                  ↓
           Trust Boundary
~~~

因此：

- S 系列不是产品能力。
- PayBench 不是另一套业务逻辑。
- AP2 不是另一套支付系统。
- M5 不是业务模块，而是裁判。
- Attack Overlay 不是异常大全，而是 Trust Boundary 的压力测试。

## 7. 不再以“异常数量”衡量项目价值

异常案例理论上可以无限扩张：超预算、币种变化、拆单、多次支付、订单涨价、退款错误、身份变化、状态乱序、网络超时等。

如果每种情况都变成一项独立功能，项目会退化成规则枚举。

以后案例只承担两个作用：

1. 验证稳定能力是否正确。
2. 暴露当前能力模型确实覆盖不了的新问题。

只有第二种情况才允许推动架构新增。

## 8. 后续每轮开发必须先过“第一性原理门禁”

任何新开发任务开始前，必须先回答五个问题。

### Q1. 当前项目的主要矛盾是什么？

本轮改动与“Agent 替代人参与交易后，授权、身份、绑定、状态、恢复和审计如何保持可信”有什么关系？

### Q2. 这是成熟支付已有问题，还是 Agent 真正新增的问题？

- 成熟支付已有：优先参考行业规范和成熟机制。
- Agent 新增：才进入本项目的创新实验主线。

### Q3. 如果成熟行业已经解决，我们参考什么？

必须给出明确来源方向，例如银联交易规范、卡组织 / EMVCo、PSP / 收单 / 支付接口实践、既有状态机 / 幂等 / 对账机制。

不得因为“自己写更快”就重复造轮子。

### Q4. 这是新增基础能力，还是只新增一个案例？

如果答案只是“多一个异常案例”，默认不开发，只把它加入现有能力的测试集。

### Q5. 做完以后，如何证明它真的增强了？

至少有一个可重复验证方式：内部回归、外部 Benchmark、协议样例、Attack / Adversarial Test、状态机 / 性质测试。

没有可验证增益的能力，不进入主线。

## 9. 当前开发暂停点

从本基线生效后，暂时暂停：

~~~text
继续增加 S14 / S15 / S16 ...
继续扩大异常矩阵案例数量
继续为了展示 M 系列修改 UI
继续因为一个新案例增加大量字段
继续马上实现 M3-C2 D1
~~~

这里不是取消 D1，而是把它从“默认下一任务”降级为一个待验证案例。

只有架构校准完成后确认“数据最小化 / 隐私披露”确实对应 Agent Trust Control Plane 的独立能力缺口，才继续实现。

## 10. 下一阶段：Architecture Rebaseline

下一阶段不是代码重构，而是先完成行业基线映射。

### A. 梳理成熟支付底座

至少覆盖：交易身份、请求身份、状态模型、幂等、UNKNOWN / PROCESSING、查询、退款 / 撤销 / 冲正、原交易引用、同步 / 异步、对账、完整性 / 签名、最终性。

输出：成熟行业主干，以及当前项目对应实现情况。

### B. 梳理 Agent 真正新增的能力

至少覆盖：Delegated Authority、Agent Identity、Intent Binding、Order / Payment Binding、Autonomy Level、Human-in-the-loop、Untrusted Context Boundary、Agent Audit / Replay。

输出：哪些是传统支付没有直接解决、需要 Agent Control Plane 补充的问题。

### C. 现有代码重新映射

每个当前模块标记：属于成熟支付底座、属于 Agent 新增、只是测试工具、只是案例，以及最终的保留 / 强化 / 降级 / 暂停结论。

完成这三步之后，才决定：

1. 是否需要重构当前代码目录或接口。
2. UI 应该如何教学展示。
3. 下一项真正值得开发的能力是什么。

## 11. UI 的新原则

当前 UI 暂不继续迭代。

UI 不是架构思考工具，而应该是架构结论的呈现层。

未来 UI 不以 M2 / M3 / M4 / M5、S01 / S02 / S03 或异常案例数量作为第一层。

应优先帮助初学者理解：

~~~text
一笔 Agent 交易如何从用户意图走到最终支付？
        ↓
传统支付系统本来负责什么？
        ↓
Agent 介入后新增了哪些信任断点？
        ↓
当前系统用什么机制证明授权、对象、状态和执行仍可信？
        ↓
失败时如何安全恢复？
        ↓
测试案例只是如何攻击和验证这些机制。
~~~

## 12. 当前项目的一句话定义

> **Agentic Payment Trust Lab 研究如何在成熟支付交易基础设施之上，把来自用户、Agent、商户、协议和支付机构的异构事实，组织成一条可授权、可绑定、可恢复、不可被不可信上下文随意改写、并且能够审计回放的智能体支付执行链。**

这句话作为后续架构、测试、UI 和功能开发的最高层约束。
