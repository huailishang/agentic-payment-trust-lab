源码复核：
- `src/agentic_payment_experiment/adapters/webshop.py`：确定性映射固定 WebShop fixture；锁定源 commit/fixture/hash，保持用户自然语言指令与授权分离。
- `src/agentic_payment_experiment/webshop_runtime_gate.py`：明确 `offline_interception_only`、`no_real_buy_now_execution`、`checkout_callback_is_injected_test_seam`；不能表述成现已控制任意实时商家。
- `src/agentic_payment_experiment/trusted_execution/governed_action.py`：当前动作词表为 `EXECUTE_PAYMENT` / `PAYMENT_EXECUTION`，不能声称已泛化治理所有创建购物车/订单/取消动作。
- `src/agentic_payment_experiment/models.py`：已有 IntentMandate / Order / TransactionRequest / PaymentExecutionRecord 等中立对象，可作为候选复用基础；是否足够需实测。

结论：不替换原商城，不为了画面再建一套业务系统。UCP 是外部协议适用性候选，展示需求自身不足以让它成为工程第一瓶颈。

## 二、候选接入步骤（设计，未执行）

1. **先做就绪测量。** 固定官方 samples commit、依赖、双方 profile/协议版本、模拟 handler、允许端点；检查本地启动、数据初始化/恢复、哪些端点产生状态变化、密钥发现与 webhook 的网络行为。先用脚本客户端，避免同时引入新模型、前端和身份框架。Context7 本轮库解析失败，改读官方样例文档，不据记忆给安装或 API 保证。
2. **检查对象能否诚实映射。** 把商家返回的 checkout ID、商品/规格/数量、金额/币种、商家身份、最终 order/payment 关联和来源记录映射到现有模型。用户授权从独立可信入口来，不从网页、商品标题或选中商品反推。checkout ID 不冒充 order ID；缺商家/收款方/支付事实就保留未知。若只有 checkout 而没有最终订单/支付证明，明确证据等级。
3. **确认执行接缝，再决定最小适配。** 复用中立校验/动作绑定/恢复原语，不伪造 WebShop fixture 来复用硬编码门禁。拟在模拟 complete checkout 前检查授权和最终交易快照；同时先识别 create/update/cancel 是否有持久状态、库存占用等副作用，分别确定授权范围。不存在原子版本/条件提交保证时，不能用一次 GET 后校验声称已经消除检查到执行之间的竞态。Agent 不能保留可绕过控制的写入通道；如只能拿日志则只能审计。
4. **测同一基线下的有限差异。** 候选代表路径为正常交易、确认后对象/金额变化、重复请求、响应丢失后未知状态查询。数据与脚本、商家配置保持一致，分别测原生样例与接入后的行为；不是故意关掉官方保护再宣称我们更好。只有可重复共同断点才形成 capability package；无新增信息则 STOP。
5. **最后复用展示消费者。** 适配后的权威事件进入现有 Trace / Read Model，再评估 Player 可消费性；不能假设外部字段一接就已兼容。界面明确固定脚本、实时交互、历史回放、模拟付款和来源等级。

完成后最多可声明“现有交易控制在指定 UCP 模拟商家链路可用”，不能声明生产支付安全或 B-06 关闭。上述步骤尚未冻结为 H47；Human 本轮只调整 CURRENT/地图中的项目优先级，没有新增执行权限。

官方依据：[samples](https://github.com/Universal-Commerce-Protocol/samples)、[Python 商家说明](https://github.com/Universal-Commerce-Protocol/samples/tree/main/rest/python/server)、[脚本客户端](https://github.com/Universal-Commerce-Protocol/samples/tree/main/rest/python/client/flower_shop)。Apache-2.0。文档中 `--require_signatures=false` 默认允许缺失/无效签名，强制验签和网络配置须单独固定；签名有效也不自动证明用户授权或交易对象正确。

## 五、我们可以怎样争取一个窄切口

当前有本地已验收的授权、绑定、未知状态恢复和证据资产，这是交付起点；没有数据证明安全性、性能、价格或采用程度优于这些公司，也没有生产运营、客户渠道和赔付能力优势。先承认这些限制，比制造“巨头不做的空白”更可靠。

更可检验的初始交付假设：客户已经选择支付服务和 Agent 框架，但在一条具体的交易链路上线前，仍需要确认后订单变化、未知状态重试或业务记录对账的排障/验收工作。以该问题的可复现案例、最小修复和回归材料收费，不要求客户更换支付网络或先采纳通用信任平台。

实例（假设而非客户已发生事故）：Agent 建立购物结算链接→用户确认→最终订单变化；或者请求已在商家完成、应用超时→第二次创建→应用与商家状态不一致。支付服务可以正确执行每笔合法请求，应用整体仍可能没有满足用户意图。是否真的存在，以及服务方现有配置是否足够，必须在客户允许的样例上验证。

避开正面投入的方法：限定一个客户类型和流程；消费官方身份/支付事实；优先解决客户已有系统、审批与业务记录之间的接入工作；先交付固定范围服务。不能宣称大厂永远不做这些工作。只有客户所需工作对通用产品难以标准化、我们能更低成本完成且重复复用时，才有机会。

可积累资产：经许可且脱敏的重复故障类型、可复跑回归库、具体系统适配经验、稳定交付关系。它们需要真实项目积累，不由“协议中立/开源/个人敏捷”的标签自动产生。

首轮访谈优先顺序建议：Filtmall（中文实际应用）→ AgentCard / Henry（明确交易工作流）→ Rye 生态应用。Nekuda/Skyfire/Crossmint 先作为竞品和潜在渠道研究；排序表示场景适配/可解释程度，不是成交概率预测。各方规模、人员、预算与沟通可达性未独立核验。

只问三件事：最近一条真实交付流程卡在哪；官方能力和自建脚本为何还不足；能否提供安全测试样例并明确负责人/验收与预算。若没有痛点就停止推销；若认可问题但不愿采购，继续验证而不是提前搭 SaaS。第二个客户主要机制可复用、交付成本下降后才考虑产品化。
