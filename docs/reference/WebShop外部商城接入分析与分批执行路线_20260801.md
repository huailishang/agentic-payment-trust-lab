# WebShop 外部商城接入分析与分批执行路线

> 日期：2026-08-01  
> 适用仓库：`agentic-payment-trust-lab`  
> 决策：不再优先自建 MiniShop；优先复用 WebShop 外部模拟商城，在购买动作前接入本项目 Trust Control Plane，并只补 WebShop 缺失的支付、状态和履约侧车。

## 1. 结论

WebShop 已经提供商品、搜索、页面导航、商品属性选择、购买动作、任务奖励和轨迹环境。本项目没有必要重新建设商品库和购物网站。

本项目真正需要建设的是：

```text
WebShop 商品与购物环境
        ↓
Commerce Adapter
        ↓
把 instruction / product / options / price / buy-now
转换成 User Intent / Order / Payment Request
        ↓
P1—P6 Runtime Authorization Gate
        ↓
Payment / Fulfillment Sidecar
        ↓
M5 状态差异与禁止副作用评测
```

第一阶段不修改 WebShop 上游源码，不运行完整大模型，不接真实电商、真实支付、钱包或资金。

## 3. 最关键的购买接点

WebShop 的 `END_BUTTON` 是：

```text
Buy Now
```

当前上游处理方式：

```text
click[buy now]
    ↓
SimServer.receive()
    ↓
SimServer.done()
    ↓
直接计算 reward
    ↓
session.done = true
```

这说明原始 WebShop 把“点击购买”直接当作任务终点，没有独立表达：

- 用户授权；
- 订单版本和确认；
- 支付请求；
- 付款前闸门；
- 支付执行；
- PENDING / UNKNOWN；
- 异步通知；
- 履约；
- 退款或争议。

因此最合理的集成缝隙是：

```text
WebShop准备执行 click[buy now]
        ↓
先转换为 PurchaseIntent / OrderCandidate
        ↓
调用本项目 Runtime Authorization Gate
        ↓
ALLOW
    -> 才进入模拟 Payment Sidecar

DENY / CONFIRMATION_REQUIRED / INDETERMINATE
    -> 不调用 WebShop done()
    -> 不产生购买完成或支付副作用
```

## 4. 为什么第一阶段优先使用文本环境

第一阶段选择：

```text
WebAgentTextEnv-v0
observation_mode = text
num_products = 1000
```

理由：

1. 文本环境直接提供 `reset / step / get_available_actions`；
2. 不需要 ChromeDriver；
3. 不需要浏览器版本匹配；
4. 更容易记录动作序列和做确定性回放；
5. 更容易在 `click[buy now]` 前插入拦截器；
6. 可先验证业务集成，不把浏览器自动化问题混入支付可信问题。

HTML / 浏览器模式后置，用于验证真实页面交互，而不是第一阶段必需条件。

## 6. 依赖隔离原则

WebShop 必须作为外部环境运行，不成为主项目依赖包。

建议目录：

```text
local_sources/third_party/webshop/
```

该目录已被 `.gitignore` 的 `local_sources/` 规则覆盖，不把第三方源码、商品数据、索引和轨迹提交到本仓库。

本仓库只保留：

```text
docs/reference/                 上游版本、许可证和接入分析
scripts/validation/webshop/     获取、检查、启动和 smoke test 脚本
src/.../adapters/               后续 Commerce Adapter
samples/external/webshop/       后续最小任务清单或归一化结果，不复制大数据
```

## 7. 不直接修改上游源码

首选集成方式：包装或组合 WebShop 环境，而不是直接在第三方仓库里长期打补丁。

```text
WebAgentTextEnv
      ↓ wrapper
WebShopTrustWrapper
      ↓
PurchaseIntent Interceptor
```

原因：

- 可以固定上游提交；
- 上游更新时容易比较；
- 本项目业务规则留在自己的仓库；
- 避免把 P1—P6 写入第三方环境；
- 更容易写独立测试；
- 可以替换为其他商城环境。

只有无法通过 wrapper 拦截购买动作时，才允许生成一个最小补丁文件；补丁必须单独保存和说明，不直接把修改后的第三方源码纳入主仓。

## 8. 分批执行路线

### P9-A1：上游固定与接入缝隙预检

目标：固定官方仓库版本，验证许可证、必需文件和 `click[buy now]` 接点，没有数据下载和依赖安装。

产出：

- 忽略目录中的官方仓库浅克隆；
- 固定提交清单；
- 上游完整性检查脚本；
- 购买动作接点检查；
- 本地工具链和阻塞项报告。

### P9-A2：独立环境与 small 数据启动

目标：使用现有 Windows Conda 创建独立 `webshop38` 环境，安装 WebShop 依赖，下载 1,000 商品 small 数据并运行官方文本 smoke test。

环境决策：

```text
不修改 agent 环境
优先创建 webshop38
目标 Python 3.8.13
环境路径由现有 Conda 统一管理
```

产出：

- 可重复的 Conda 环境创建和安装脚本；
- `webshop38` 环境清单与 Python 版本证据；
- 依赖锁定或兼容补丁记录；
- `WebAgentTextEnv-v0` 可 reset；
- 至少执行 search / click / reset；
- 不接本项目业务逻辑。

### P9-B1：Commerce Adapter

目标：把 WebShop instruction、商品、选项、价格和购买动作映射到协议中立对象。

建议映射：

```text
instruction_text        -> User Intent
session / goal          -> Task Context
asin + options          -> Order Item / Selection
product price           -> Order Amount
click[buy now]          -> Purchase Intent / Payment Request Candidate
```

不得把 WebShop reward 当作支付安全结论。

### P9-B2：购买动作拦截与 Runtime Authorization Gate

目标：在任何购买完成副作用前消费 P1—P4。

```text
P1 授权与确认
P2 Order → Payment Request → Execution 绑定
P3 Agent / Executor Identity
P4 Web 页面和工具内容来源
```

非 `ALLOW` 时不得调用上游 `done()`。

### P9-C1：支付与履约 Sidecar

目标：补 WebShop 不具备的支付状态和履约状态。

```text
SUCCESS / FAILED / PENDING / UNKNOWN
异步通知
查询原交易
重复付款防护
履约成功 / 失败
```

消费 P5、P6 和 M5。

### P9-C2：外部环境异常与攻击

覆盖：

- 结账前涨价；
- 商品或选项变化；
- payee / merchant 变化；
- 页面提示注入；
- 支付 UNKNOWN；
- 重复购买；
- 支付成功但履约失败；
- 不必要个人信息请求。

### P9-D：任务集和对比评测

比较：

```text
原始 WebShop task reward
Trust Control Plane 后任务完成率
错误购买率
错误拒绝率
漏确认率
重复支付率
禁止副作用
```

### P9-E：购买轨迹可视化 UI

目标：在基础购买链路、可信闸门、支付履约状态和评测轨迹稳定后，复用现有交互实验台，增加 WebShop 专属轨迹回放页面。

```text
真实轨迹 JSON
  ↓
用户任务 / 搜索 / 候选 / 点击商品
  ↓
Commerce Adapter / Order / TransactionRequest
  ↓
可信检查 / 四态决策
  ↓
支付 / 履约 / 补救 / 最终结果
  ↓
逐步回放 UI
```

边界：

- UI 只读取并展示真实轨迹，不重新运行 WebShop 或计算决策；
- 每个展示字段必须能回指原始证据；
- 第一版支持上一步、下一步、自动播放和回到起点；
- 必须区分 `DETERMINISTIC_SMOKE / FIXED_REPLAY / AUTONOMOUS_AGENT`；
- 在真正接入自主决策 Agent 前，不得把固定脚本轨迹表述成自主购物。

详细规划：

- `docs/02_未来规划/WebShop购买轨迹可视化UI规划_20260802.md`

## 9. 第一任务为什么只做 P9-A1

当前已有 Windows Conda，但现有 `agent` 环境是 Python 3.12.13；WebShop 依赖固定在 Python 3.8 和较老版本。虽然可以创建独立 `webshop38` 环境，但如果在第一包同时克隆、建环境、装依赖和下载数据，会同时混入：

```text
上游下载问题
Python版本问题
Java / Pyserini问题
依赖冲突
搜索索引问题
本项目适配问题
```

第一包先回答三个最小问题：

```text
1. 我们固定的是哪一个官方版本？
2. 官方购买动作能否被稳定识别和拦截？
3. 下一包安装环境前，具体缺少什么？
```

只有 P9-A1 通过，才允许进入 P9-A2。

P9-A2 已形成以下事实：

- 使用独立 Windows Conda 环境 `webshop38`，Python 3.8.13、环境内 OpenJDK 11；共享 `agent` 环境未被修改；
- 原 Google Drive 公开链接失效后，按照评估者修订合同，从固定 Hugging Face revision 获取三份 `checksum-verified mirror copies of the WebShop small assets`；

- 真实 `WebAgentTextEnv-v0` 已完成两次 reset、搜索和商品点击，并到达 `Buy Now` 可用状态；
- 没有执行 `click[buy now]`，购买计数为 0；
- 为兼容 Windows 上的 Pyserini 0.17 / Faiss 1.7.4，最终环境采用 NumPy 1.23.5、MKL 2021.4、Transformers 4.19.2 和 ONNX Runtime 1.12.1；这些属于外部旧项目运行兼容层，不进入主项目产品依赖。

P9-B1 离线 Commerce Adapter 已通过独立复核：它只把既有 pre-Buy-Now 证据中的 `instruction_text`、当前商品、选项、价格和显式实验上下文映射为协议中立 `Order + TransactionRequest`。适配器保留“cargo pants 指令”与“Vhomes console table 商品”不匹配这一事实，不推断商品满足指令，不创建 `IntentMandate`、授权结论、购买或支付副作用。

P9-B2 已形成离线 Buy Now Runtime Gate 候选：显式消费 P1 授权、P2 连续绑定、P3 Agent / Executor 身份和 P4 上下文来源事实；只有最终 `ALLOW` 才调用一次本地注入回调。限制性授权、需确认、信息不足以及 P2/P3/P4 失配均零回调；回调异常只尝试一次并返回 `INDETERMINATE`，不自动重试或声称结账成功。

P9-B2-R 已补齐共享 Runtime Gate 的因果原因：非 `ALLOW` 分支除原始事实 reason 外，还会给出稳定的阶段原因，例如 `p4:current_action_mismatch` 和 `p4:source_coverage_value_mismatch`。决策和 callback 次数没有改变，WebShop outcome 只透传共享 RuntimeGateRecord reason，没有复制 P4 规则。

P9-C1 已形成离线支付与履约 Sidecar 候选：它消费已通过的购买闸门、显式支付/履约记录以及可选查询、异步观察和已知支付尝试，复用现有恢复、原交易绑定、状态冲突和生命周期规则，输出初始/有效支付状态、重复付款阻断、离线重试候选、履约、任务与补救状态。所有记录均为本地 fixture，没有执行真实查询、异步回调、重试、支付或履约。

当前结论仍然是：WebShop 只是外部验证场地。P9-C1 等待独立复核；P9-C2、P9-D 和 P9-E 尚未开始，真实 WebShop、真实 Buy Now、真实支付、履约和 UI 仍不进入本包。
