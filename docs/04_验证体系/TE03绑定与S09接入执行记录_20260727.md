## 2. 新增可信执行接口

新增：

```text
verify_binding(expected_digest, actual_object)
    -> BindingResult
       ├─ VALID
       ├─ INVALID
       └─ MISSING_EVIDENCE
```

`BindingResult` 同时保留：

- `reason_code`
- `expected_digest`
- `actual_digest`
- `algorithm`

当前原因代码包括：

```text
binding_match
binding_mismatch
expected_digest_missing
expected_digest_invalid
actual_object_missing
actual_object_not_canonicalizable
```

边界：

> `verify_binding()` 只回答“实际对象是否重新计算出预期摘要”，不返回 `ALLOW`、`DENY` 或 `CONFIRMATION_REQUIRED`。

## 3. S09 如何接入

`order_validation.py` 现在执行：

```text
授权订单
    -> canonical_hash()
    -> authorized_order_digest

最终订单
    -> verify_binding(authorized_order_digest, final_order)
    -> order_binding_status / reason / actual_digest

绑定事实
    + 原有字段级订单比较
    -> Payment Domain 继续决定
       ALLOW / CONFIRMATION_REQUIRED / DENY / INDETERMINATE
```

新增证据：

```text
authorized_order_digest
final_order_digest
order_binding_status
order_binding_reason
```

订单规则版本由 `order-change-rules-v0.2` 升级为 `order-change-rules-v0.3`。

## 4. 最关键的边界验证

### 4.1 完全相同快照

```text
授权订单 == 最终订单
-> Binding = VALID
-> Payment Domain = ALLOW
```

### 4.2 仅版本字段变化

TE02 已冻结 `order_version` 进入摘要，因此：

```text
v1 -> v2
其他业务字段不变
-> Binding = INVALID
-> 原有字段级比较认为没有需要重新确认的业务变化
-> Payment Domain = ALLOW
```

这条测试是本轮最重要的负向边界：

> **绑定无效不等于支付拒绝。**

### 4.3 S09 主样品涨价

```text
480 -> 490
order_version v1 -> v2
-> Binding = INVALID
-> 字段比较识别：总额变化 + 单价变化
-> Payment Domain = CONFIRMATION_REQUIRED
```

因此绑定事实只是说明对象快照不同；真正决定为什么不同、需要重新确认还是拒绝，仍由支付域负责。
