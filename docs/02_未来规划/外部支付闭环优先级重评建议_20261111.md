# 外部支付闭环优先级重评建议（供 Evaluator 独立审阅）

- 日期：2026-11-11
- 来源：Human 对 H66、H67 与反复虚拟验证的项目级质疑；以下为候选建议，不是评估结论。
- 状态：**PROPOSAL / PENDING_EVALUATOR_REVIEW**
- 关联入口：`CURRENT.md`；`docs/01_项目现状/PROJECT_BOTTLENECK_MAP.md`（目前 r109）
- 责任边界：本文件不冻结新 H 包、不授权网络或支付、不更改已有验收和任务优先级；由 Evaluator 独立裁决。

## 1. 核心结论

当前项目的突出矛盾不是缺更多攻击种类、支付规则或模拟案例，而是**已经有不少本地可信执行与恢复证据，却缺少能够独立核验的外部支付执行、状态恢复和资源交付闭环**。

持续新增静态协议检查、模拟攻击及外部轨迹整理，可以提高局部证据质量，却不必然提高产品在外部环境中的适用性。建议 Evaluator 将当前 **B-20/H67（静态 ACP 幂等键契约差异）** 与 **F 阶段最小外部支付测试环境** 重新比较，明确选择前者作为首要瓶颈的项目级收益，避免“任务数量增长，真实适用性证据未增长”。

“外部闭环”只指：使用公开协议的实际 SDK/外部测试服务或测试网络，以**测试凭证、测试资产**执行受限流程，取得不由本仓单方面伪造的证据。它不等于生产支付、真实用户、银行卡、真实资金安全或合规性已获证明。

以 `CURRENT.md` 和项目瓶颈地图 r109 为准；Evaluator 审阅时必须重新检查本地 HEAD 和状态：

| 事项 | 当前已有事实 | 不能据此声称 |
|---|---|---|
| A–D | 本地代表性验证已阶段关闭 | 生产安全已证实 |
| E | 受控本地身份/凭据验证闭合 | 真实强认证/签名信任源已覆盖 |
| F | 外部协议、SDK、消费者适用性为当前阶段 | 已有真实商户/支付服务/网络全链闭环 |

| H63–H65R/CartTrace | 静态外部轨迹取得部分金额、确认、令牌关联线索；当前六例视图停止 | 本仓控制在真实外部交易中有效或无效 |
| H66/IronClaw | 官方固定有界研究找到了通用审批、执行、凭据机制；限定视图未找到金融消费者，PASS/REFERENCE_ONLY/STOP_VIEW | IronClaw 全仓不存在金融能力 |

特别强调：**schema 接受 ≠ RPC 成功 ≠ 资金结算 ≠ 服务交付 ≠ 用户任务完成**。每层需独立证据与状态。

## 3. H67 为什么被定义，能带来什么

### 决策逻辑

H66 没有获得具体金融执行消费者后，评估者选择了更容易独立证伪、成本有限的 B-20：ACP 原始 REST POST 必填 `idempotency_key`，转换到 MCP/OpenRPC 工具 `meta` 描述时，内部键或许并非必填。若下游执行没有补强，存在重复副作用风险。

H67 冻结在官方固定提交，检查五个 checkout 工具（四写一读）各两组“仅增删幂等键”的对照探针，加五条官方示例观察，以标准库离线判断**元数据契约**差异。此测量本身有价值，不是无意义工作。

### 证明范围及局限

- 能检验：REST 规则与 MCP meta schema 对缺键输入的接受要求是否一致；GET 工具作为阴性对照。
- 不能检验：MCP/HTTP 服务实际是否接受；服务端是否自动补键、是否有持久化去重；Agent 是否会触发多笔付款；本仓对这一外部风险是否具备拦截效果。
- 合同禁止启动 RPC/MCP/HTTP、安装上游、运行产品、调用钱包/签名/支付服务，因此 H67 属于 **measurement-only / interface contract**，不是产品能力升级或外部 E2E 验证。
- 建议 Evaluator 检查：即使确认元数据弱化，是否已有合法、可运行的下一步消费者和可测保护目标？若没有，是否按已存在的 STOP 条件结束，而不是继续生成 H68/H69 静态研究包？
- H67 当前为 `CONTRACT_FROZEN`、`H67_FROZEN_NOT_EXECUTED`；本建议不得改变冻结合同、预算、L2/L3、授权与历史证据。是否收尾或重排须 Evaluator 按正式流程处理。

## 4. H66 与六类 x402 攻击应当如何定位

H66 暂停 IronClaw 接入是合理的：通用 Agent Runtime、审批和凭据机制本身，不足以证明真实金融支付执行。继续深挖通用宿主容易偏离项目目标；已取得的通用机制保留为 REFERENCE_ONLY。

SoFi 工程师 Ishween Kaur 对 x402 的六类攻击（价格篡改、重复付款、未完成结算提前交付、凭证跨资源复用、伪装商户、提示注入引导追加付款）可作为**外部交互后的最小风险检查清单**。若现在只是再生成六份模拟 JSON 与本地评分，不能突破“自己设置情境、自己执行、自己判卷”的证据局限。

建议：`H66=REFERENCE_ONLY/STOP_VIEW`；`六类 x402 攻击=REFERENCE_ONLY`；在获得外部付款、查询、交付接口前，不因此批量增加 S 编号或六个静态执行包。

## 5. 候选突破路径：最小外部支付闭环

### 方案 A：先打通真实测试网结算与受控服务（优先资格研究）

```text
用户明确的测试授权（任务、金额上限、商户/资源、次数）
    ↓
本仓付款前 Trust Gate（授权、订单、金额、payee、资源绑定）
    ↓
基于官方 x402 SDK 的受控付费 API（服务由我们控制）
    ↓
外部 Facilitator 的 verify / settle 与支持的测试网络
    ↓
独立查询结算状态 / 交易凭证
    ↓
获取真实交付资源、验证目标内容、记录服务端收据
    ↓
断网/超时恢复、重复调用防护、审计证据
```

这仍不代表“真实第三方商户”，但至少把结算事实移出本仓自制模拟。不能把链上交易成功等同于业务履约或 Agent 任务完成。

在立项前必须重新确认：官方 SDK 版本、Facilitator 对指定测试网络/资产的实时支持、测试资产取得方式、网络手续费、服务调用权限、许可证与安全约束。**当前提议不声称环境已经可用或可付款。**

### 方案 B：再接独立第三方付费 API

方案 A 可重复、可独立核验后，选择一个不受本仓控制、明确支持测试环境与付费资源交付的外部 x402 服务。读取陌生商户报价、实际付款条件和服务响应，再验证我们的 Trust Gate 是否仍能正确执行。找不到合格外部服务就报告 INPUT_LIMIT，不得伪造成功轨迹。

### 当前不建议

- 开发钱包、清算平台、DeFi/发币、通用 Agent Runtime 或第二个模拟商城。
- 在未接外部链路时继续铺开六类攻击/新增大量本地假设 Case。
- 使用生产密钥、真实银行卡、真实客户数据和实际资金进行实验。

## 6. 三项硬验收：从“模拟通过”转向“外部证明”

| 验收目标 | 需要独立可核对的证据 | 不充分的替代证据 |
|---|---|---|
| E2E-1 外部支付 | 受限测试授权下出现唯一外部结算事实，金额、币种、收款者、网络、资源与用户授权绑定 | 本仓模拟 `SUCCESS` |
| E2E-2 状态恢复 | 故意制造响应中断，重查外部原交易；同一业务请求未发生第二笔外部结算 | 内存变量记录“付款一次” |
| E2E-3 资源交付 | 实际付费 API 交付产物，产物标识/内容哈希、业务请求、结算收据可关联；支付、履约、任务完成分别判定 | 链上成功或单个 HTTP 200 |

初始负向对照足够限定为：正常付款、价格或收款方变化、重复请求、付款后交付失败四种，不以案例数为成功指标。

取证至少应保留：业务任务及请求 ID、授权摘要、报价/订单摘要、收款方、金额币种网络、幂等键/操作号、外部 verify/settle 凭证与可查询结果、交付收据/产物摘要、异常恢复与禁止副作用。无法观察的维度保持 `UNKNOWN` 或 `NOT_MEASURED`，不可用“链上已成功”填充履约缺失。

## 7. 权限、风险与治理

目前 `authorization_api_call=false`，B-06 为 `HUMAN_DEFERRED`，本提议**不授权也不执行**网络 API、钱包、签名、测试币转移、服务启动或安装。

Evaluator 应先做**零副作用的可行性评估**，然后向 Human 明确申请范围有限的授权，写清：
- 允许访问的官方服务/测试网络与确切端点、运行范围和时间；
- 用于实验的隔离钱包与测试资产来源、单次和总额上限、异常停止条件；
- 允许记录的去敏证据、钱包/密钥保管、凭证不落仓与不出现在日志中；
- 故障后查询优先、不盲目重试、禁止生产系统和真实客户数据；
- 投入成本、预期信息增量、失败时的 STOP / SWITCH 路由。

安全与合规仍按原项目限制执行。不得通过口头建议或本文绕过冻结合同与中央 Git/安全门禁。

## 8. 请 Evaluator 独立作答的六个问题

1. 项目当前第一瓶颈是否应从 B-20 重新比较为“外部可执行支付闭环缺失”？依据项目主指标、零容忍风险、置信度、成本和授权依赖说明。
2. H67 即便完成元数据测量，是否存在能继续复核的消费者？如无，如何按原合同正常 STOP，而不是继续静态任务？
3. x402 官方 SDK/Facilitator/测试网究竟能否形成合法、可运行、可查询的最小闭环？先核官方资料，独立标识未核实条件。
4. 上述三项 E2E 验收能够获得外部独立证据吗？不能的话是否承认 INPUT_LIMIT？
5. 是否值得向 Human 申请仅测试网受限授权？请列出精确授权清单与风险上限，不恢复真实资金权限。
6. 有何真实 Agent 开发者或消费者会使用此能力？技术闭环通过不自动等于商业可行。

**建议阶段性分类**：
- H66：REFERENCE_ONLY / STOP_VIEW，不重启相同接入视图。
- H67：尊重冻结合同，评估后按既有 CONTINUE/STOP/SWITCH 条件裁决。
- 六类 x402 攻击：REFERENCE_ONLY，后续用于真实链路的对照而非独立开发主线。
- 最小外部支付闭环：**PROPOSED_FOR_EVALUATION**，不自动成为 ACTIVE，也不自动取得 API/测试网/钱包权限。

最后应把内部回归成绩、协议契约成绩、外部结算/履约成绩、第三方消费者验证和商业价值分别记账，避免以某一层的 PASS 替代整个项目目标。
